## 2. 原则

review、改代码、写文档都按下面十条。改原则要作者点头，并在文末留一笔。

1. **先懂，再改。** 一段代码讲不清「谁调用、做什么、为什么这样写」，就不许借着重写蒙混过去。
2. **白皮书用白话，写翔实。** 每段机制写清：职责、为什么这样设计、运行时怎么走、依赖谁。这是视频教程的底稿，也是作者自己的底稿。
3. **代码自说明。** 命名用完整词，有一点 C 基础的人能顺着读。注释不复述语句，专写为什么、谁调用、前后文。看完注释要能回答「为什么这么写」。
4. **对表业界，实现可以薄。** 分层、接口、设备与驱动的关系跟常见做法对齐。用薄实现把主路径讲清楚。最短路径若形状是错的，记成债，懂了再改。
5. **债在路过时还。** 技术债、难读、缺注释，记在当段记录里，能小改的当段改完。不单开一轮只还债、不学习的扫荡。
6. **大模块要能拆能换。** 驱动、GUI 等要有清楚边界：同学能写模块替换；新硬件能加进去。核心少焊死某一种板卡或某一种设备。
7. **syscall 与 ABI 当合同。** 用户态靠它写程序。改合同必须写进白皮书，并说明旧程序会怎样。
8. **QEMU 是每天的试金石，真机是加分项。** 改完主路径要能在 QEMU 里启动。真机支持按模块加，不因手头没有某块板就塞进核心。
9. **0.1.0 由作者拍板。** 网络、商店、各个 GUI 程序要加强到满意。能开机、能冒烟，都不等于 0.1.0。
10. **问答落纸。** 作者问过的问题，收成问答条目。同一问不散落在多次聊天里。

### 4.1 从 OVMF 上电到 `UefiMain`

本段只讲到我们自己的 `UefiMain` 被调用为止。`UefiMain` 里面的六步（串口、显卡、装内核、ACPI、xHCI、跳内核）下一节再拆。

#### 职责

QEMU 上电后，先跑的是 **OVMF**（虚拟机里的 UEFI 固件，出厂软件，不是我们写的）。它把磁盘上的 `BOOTX64.EFI` 装进内存，当成一个普通 UEFI 应用程序调用。这个 EFI 才是我们的 Boot。

Boot 的职责：在固件还愿意提供服务的时候，把屏幕、内核文件、少量硬件信息备好，然后向固件告别，跳进内核。

#### 为什么要有这么一截

PC 的开机合同是 UEFI：固件只认 `EFI/BOOT/BOOTX64.EFI` 这种路径，不认我们的 `Kernel.elf`。所以 X64 必须有一个「固件听得懂的小程序」当加载器。Arm64 / RiscV 在 QEMU 里通常由 QEMU 直接把 ELF 放进内存，没有这一截。

EDK2 是英特尔那套 UEFI 开发包。我们用它的两样东西：

| 用它干什么 | 会不会进虚拟机 |
| ---------- | -------------- |
| `BaseTools`：把 C 源码编成、打包成 `.efi` 的机床 | 不会。只在编译这台机器上跑 |
| `MdePkg`：UEFI 的类型、协议声明，以及 `Boot.dsc` 点名的十几个库 | 只有链进 `BOOTX64.EFI` 的那一小部分会进虚拟机 |

`Boot.dsc` 写明只链这些库：`BaseLib`、`BaseMemoryLib`、`BaseDebugLibNull`、`BasePcdLibNull`、`BasePrintLib`、`UefiDevicePathLib`、`RegisterFilterLibNull`、`BaseStackCheckLib`、`UefiLib`、`UefiBootServicesTableLib`、`UefiRuntimeServicesTableLib`、`UefiApplicationEntryPoint`、`UefiMemoryAllocationLib`。磁盘上的 `MdePkg/Library/` 已经只剩这 13 个目录。

编出来的 `Boot/Build/BOOTX64.EFI` 大约 **15KB**。旁边的 `Boot/EDK2/` 大约 **59MB**。体积差在机床和头文件，不在会跑起来的程序。

#### 运行时怎么走

`Runtime/run.sh` 把两块 pflash 交给 QEMU：

- 只读代码盘：系统里的 `OVMF_CODE_4M.fd`（固件本体）
- 可写变量盘：`Runtime/Fw/OVMF_VARS.fd`（固件记住的启动项之类）

同时挂两块 AHCI 硬盘：`Esp/X64`（disk0，上面有 `EFI/BOOT/BOOTX64.EFI`），`RootFs/X64`（disk1，上面有 `Kernel.elf`）。`bootindex=0` 让固件先从 ESP 启动。

固件找到 EFI 之后，调用的**不是** `UefiMain`，而是 EDK2 的 `_ModuleEntryPoint`（`MdePkg/Library/UefiApplicationEntryPoint/ApplicationEntryPoint.c`）：

1. 若应用要求的 UEFI 版本比固件新，直接返回 `EFI_INCOMPATIBLE_VERSION`。我们没抬高这个版本号，这步会放过。
2. `ProcessLibraryConstructorList`：各库的构造函数。`UefiBootServicesTableLib` 在这里把固件传来的 `SystemTable` 存进全局 `gBS` / `gST`，后面才能写 `gBS->...`。
3. `ProcessModuleEntryPointList`：这是编译时生成的 `AutoGen.c`，里面只有一句 `return UefiMain(...)`。
4. 从 `UefiMain` 返回之后，再跑库的析构函数，然后 `_ModuleEntryPoint` 把状态码交回固件。

所以读 Boot 时，第一行自己的代码是 `BootPkg/Boot.c` 的 `UefiMain`。它前面那一层是 EDK2 规定的应用程序壳，我们不改它。

`UefiMain` 拿到两个参数：`ImageHandle`（固件给这个程序的句柄，用来查「我是从哪个文件加载的」）、`SystemTable`（固件服务总表）。六个步骤的节目单写在 `Boot.c` 顶部，下一节按这个顺序看。

#### 依赖

| 依赖 | 谁提供 | 我们碰不碰源码 |
| ---- | ------ | -------------- |
| OVMF | 系统安装的固件镜像 | 不碰，当黑盒 |
| `BOOTX64.EFI` 的打包格式 | `BaseTools` 里的 `build`、`GenFw` | 不逐行读；能编过即可 |
| `EFI_STATUS`、`gBS`、协议 GUID | `MdePkg` 头文件和上面那 13 个库 | 用到哪个协议再打开对应头 |
| 六步业务 | `Boot/BootPkg/*.c` | 这是要逐段读懂的自有代码（约 1700 行） |

### 4.2 `Serial.c`：COM1

`UefiMain` 里实际按顺序调用 8 次：`BootSerialInitialize`、`BootSerialBanner`、`GetVideoInfo`、`SetVideoMode`、`BootLoadKernel`、`BootFillRsdp`、`BootFillXhci`、`JumpToKernel`。文件头把前两次收成第 1 步「串口」，中间两次收成第 2 步「显卡」，所以节目单写成 6 步。辅助文件按这 6 步拆；显卡超过三百行，拆成 `Video.c` 加 `VideoScore` / `VideoEdid` / `VideoTheme`。

#### 职责

Boot 自己的第一件事：把主板上的第一个串口（COM1）设成 115200 8N1，供后面每一步打日志。QEMU 用 `-serial stdio`，这些字节出现在启动 `run.sh` 的那个终端里。不经过 UEFI 的 `gBS->...`，直接用 CPU 的 `in` / `out` 访问端口 `0x3F8`。内核 HAL 的 `Drivers/Serial.c` 用同一地址、同一分频，所以 Boot 打完，内核可以接着打。

探测失败就不改芯片、之后所有打印都变成空操作。Boot 此时还没设屏幕，串口是唯一的进度输出。

#### 函数

头文件 `Serial.h` 露出 5 个，其余是本文件内部的。

| 函数 | 谁调用 | 干什么 |
| ---- | ------ | ------ |
| `BootSerialInitialize` | `UefiMain` 第一句 | 探测 COM1，在则按 16550 的常规顺序配好 |
| `BootSerialBanner` | 紧接着初始化 | 打两行字：`Blocks Boot`，以及 `COM1 Serial OK` |
| `BootSerialWrite` | 横幅，以及 `Printf` | 把一串字符送出去。看见裸 `\n` 就先补 `\r` |
| `BootSerialPrintf` | 后面各文件的失败/进度 | 先用 EDK2 的 `AsciiVSPrint` 格式化到栈上 256 字节，再 `Write` |
| `BootSerialPresent` | 只有横幅在用 | 返回探测结果 `sSerialOk` |
| `BootSerialOut8` / `In8` | 内部 | 一条 `outb` / `inb` |
| `BootSerialProbe` | 初始化 | 往暂存寄存器写 `0x55`、`0xAA`，读回对得上才算有芯片 |
| `BootSerialWaitBit` | 发字节、行尾 | 看线路状态寄存器的某一位，最多空转约一百万次 `pause` |
| `BootSerialPutChar` | `Write` | 等「发送保持寄存器空」，再把这一字节写出 |

`BootSerialPrintf` 必须标 `EFIAPI`。X64 上 EDK2 的 `PrintLib` 按微软调用约定取可变参数；这个函数若走 System V，`%d` 一类会读错栈，严重时缺页。

#### 初始化做了什么

COM1 是一块 16550 兼容串口，基址 `0x3F8`。加 0 到加 7 是八个寄存器。加 0 在「分频锁存」打开时是波特率低字节，平时是数据口。

1. **探测。** 加 7 是暂存格，不参与收发。写入 `0x55` 再读、写入 `0xAA` 再读。两次都对，才认为这里有 UART。QEMU 的串口会通过。没有芯片时读回常常是 `0xFF`，探测失败，`sSerialOk = 0`，函数返回，后面的寄存器一个都不写。
2. **关中断。** 加 1（中断使能）写 `0x00`。Boot 只用轮询，不接 IRQ。
3. **打开分频锁。** 加 3（线路控制）写 `0x80`，最高位 DLAB=1。此后加 0、加 1 暂时表示波特率除数，不是数据和中断。
4. **波特率 115200。** 加 0 写 `0x01`，加 1 写 `0x00`。PC 上这块芯片的参考钟是 1.8432 MHz，波特率 = 115200 / 除数，除数 1 就是 115200。和内核同一套。
5. **8N1，并关上分频锁。** 加 3 写 `0x03`：8 个数据位、无校验、1 个停止位，DLAB 回到 0。加 0 重新是发送数据的口。
6. **打开并清空 FIFO。** 加 2 写 `0xC7`：使能 FIFO、清空收发队列、触发水位 14 字节。这是 16550 上常见的「把硬件缓冲用起来」写法，避免每字节都要等移位寄存器。
7. **把口子打开。** 加 4（调制解调器控制）写 `0x0B`：DTR、RTS、OUT2。OUT2 在 PC 上是「允许这块 UART 的中断线接到中断控制器」。本阶段中断使能仍是 0，所以只是把口置于常规工作态，并不真的进中断。

发一个字节时，先看加 5（线路状态）的 bit5：发送保持寄存器空了才 `out` 到加 0。注释写明曾经用 2000 次空等，真机和 USB 串口桥上来不及发完就被下一字节盖掉，所以改成约一百万次 `pause`。每遇到换行，再等 bit6（发送移位寄存器也空了）才继续，避免真机上两行粘成一行。

换行还有一层格式约定。`AsciiVSPrint` 会把格式串里的 `\n` 先扩成 `\r\n`。`Write` 若再对 `\n` 补一个 `\r`，线上就是 `\r\r\n`：QEMU 多空一行，真机终端却会粘行。所以 `Write` 丢掉已经存在的 `\r`，只在看见单独的 `\n`（横幅那种直接 `Write` 的字符串）时补 `\r`。

#### 依赖

只依赖端口 `0x3F8` 上的 16550，以及 `PrintLib` 的 `AsciiVSPrint`。不调用引导服务。`ExitBootServices` 之后 CPU 的 `in`/`out` 仍然可用；真正不能再用的是 `gBS`。串口选在告别固件之前建好，是为了装内核、退出引导服务时还能打日志。

### 4.3 `Video.c`：GOP 选模式、设模式

串口绕开了固件。显卡反过来，全程问 UEFI。`UefiMain` 先 `GetVideoInfo`，再 `SetVideoMode`。主文件是 `Video.c`；打分在 `VideoScore.c`，显示器首选分辨率在 `VideoEdid.c`，`THEME.CFG` 在 `VideoTheme.c`。

#### 职责

在告别固件之前，确定一块线性帧缓冲：基址、大小、宽、高、每行像素数，写进 `UEFI_BOOT_CONFIG.VideoConfig`。内核以后自己往这块内存里画，不再调固件的画图函数。同时把固件列出的分辨率去重，最多 32 条，留给以后的设置界面。

用到的协议：

| 协议 | 干什么 |
| ---- | ------ |
| `EFI_GRAPHICS_OUTPUT_PROTOCOL`（GOP） | 列出显示模式、切换模式、拿到帧缓冲地址，还能整屏填色 |
| `EFI_EDID_ACTIVE_PROTOCOL` | 真机上读显示器自己声明的首选分辨率 |
| `EFI_SIMPLE_FILE_SYSTEM_PROTOCOL` | 读 `THEME.CFG` 里的 `mode=宽x高` |

`LocateHandleBuffer` 之后只用 **第一个** GOP。有多块显卡时，后面的不看。

#### `GetVideoInfo` 在选什么

1. 打开第一个 GOP。
2. `TryLoadDisplayPref`：先在带 `BLOCKS.ID`（或旧的 `TOYOS.ID`）的卷上找 `THEME.CFG`，再找其它卷。行是 `mode=1440x900` 这种。`mode=auto` 或太小的值不当成目标。
3. `IsVirtualMachine` 看 CPUID.1 的 ECX 最高位（管理程序存在位）。QEMU 上这一位是 1。虚拟机里**不读 EDID 协议**；真机才读。EDID 是显示器 ROM 里的 128 字节，偏移 `0x36` 起有四段 18 字节的详细时序，像素时钟非 0 的第一段就是首选宽高。
4. **没有 `mode=`，并且固件当前模式已经 ≥ 640×480**：就锁定当前模式，分数写成 60 亿。后面枚举到的模式分数都是 0，抢不走它。注释里的原因是：别为了「EDID 原生或像素最多」再去 `SetMode`，4K 切换很贵。
5. **有 `mode=`**：精确相等给 50 亿。没有精确模式就按「同宽高比优先、否则曼哈顿距离近的优先」在 GOP 列表里找最近的（`ScoreModeNative`）。
6. 既没有 `mode=`，固件当前模式又不可用：虚拟机走一张固定偏好表（`ScoreModeQemu`，1280×720 最高）；真机对着 EDID 打分，没有 EDID 就挑面积最大的（上限 7680×4320）。
7. 枚举时丢掉 `PixelBltOnly`（没有线性帧缓冲，只能调固件 `Blt`，告别固件后内核画不了）和小于 640×480 的模式。相同宽高只留一条，记入 `VideoModes[]`。
8. `SortVideoModesForSettings` 把这份列表再排一次，给设置界面用。虚拟机按那张偏好表排；真机按 EDID 排。这个顺序和「这次启动最终用哪一档」不是同一件事。

选出的模式号、宽高先放在 `Video.c` 的静态变量里，因为 `UefiMain` 是单线程、先 Get 再 Set。

#### `SetVideoMode` 经常不切模式

QEMU 窗口在客人里改分辨率时，GTK 会把虚拟机复位一次。复位后固件又按**启动时**的 EDID 回到旧模式，于是来回重启。所以：

- 当前宽高已经等于选中的：所有机器都跳过 `SetMode`。`run.sh` 会按 `THEME.CFG` 把 EDID 交给 QEMU，固件起来往往已经是这个分辨率。
- 当前不等于选中的，但是虚拟机：仍然跳过 `SetMode`。要改分辨率得退出 QEMU，让 `run.sh` 用新的 EDID 再启动。
- 只有真机、并且当前分辨率不同，才调用 `Gop->SetMode`。

无论切没切，写进 `VideoConfig` 的都是 **GOP 此刻的真实模式**，不是打分选中、却被跳过的那一档。所以串口上可能先看到 `Pick 1920x1080`，后面清屏却是另一组宽高。

然后把 GOP 指针和魔数 `UEFI_GOP_HANDOFF_MAGIC`（`GON1`）放进交接包。内核 `VideoGop.c` 写明：`ExitBootServices` 之后再调 `SetMode` 是未定义的，真机上会缺页或非法指令。这个指针只用于「已经是目标分辨率时同步帧缓冲视图」。真机改分辨率靠下次启动前的 `THEME.CFG`，不靠运行中切模式。

最后 `Blt` 把整屏填黑。

#### 依赖

GOP、EDID、文件系统都是 `gBS` 上的引导服务，只能在 `ExitBootServices` 之前用。帧缓冲物理地址本身在告别之后仍然指着那块显存，内核映射它来画。`FsHasOsMarker` 放在 `VideoTheme.c`，装内核时还会再用，用来认出带 `BLOCKS.ID` 的那块盘。

### 4.4 装核、填 ACPI 与 xHCI、退出固件

`UefiMain` 在画面定下来之后调用四个函数：`BootLoadKernel`、`BootFillRsdp`、`BootFillXhci`、`JumpToKernel`。前三个只往栈上的 `UEFI_BOOT_CONFIG` 里填字段。第四个拿着同一块结构告别引导服务，再把这块结构的地址交给内核入口。`SystemTable` 是 `UefiMain` 自己写进去的，不在这四个文件里。

#### 职责

在还能调用 `gBS` 的时候做完三件事：把 `Kernel.elf` 按它链接时的物理地址放进内存，记下 ACPI 根表和 xHCI 的基址，拍下固件的内存地图。然后 `ExitBootServices`。这一步之后 `gBS` 不能再调，串口的 `in`/`out` 还可以用，但本文件成功跳转之后不再打印。

#### 函数

| 函数 | 谁调用 | 输入 | 改了什么 | 为什么这样 |
| ---- | ------ | ---- | -------- | ---------- |
| `FsHasOsMarker` | `ReadKernelFile`、`ScanOsMarkerVolumes`，定义在 `VideoTheme.c` | 一个简单文件系统 | 不改交接包。打开卷根的 `BLOCKS.ID`，没有再试 `TOYOS.ID` | 认的是系统盘，不是启动盘。主题文件先用了它，装核复用，所以人还放在 `VideoTheme.c` |
| `OpenKernelOnFs` | `ReadKernelFile` | 已经选定的一卷 | 分配 `EfiLoaderData` 页，把文件读进去。写出缓冲区地址和读到的字节数 | 卷内四条路径见 Q10。页数是 `(文件字节 >> 12) + 1`，整页大小也会多留一页 |
| `ReadKernelFile` | `BootLoadKernel` | 本 EFI 的 `ImageHandle` | 选出一卷并读出内核。成功时释放句柄数组 | 三遍：有标记的卷、其它非启动卷、启动卷兜底。避免 ESP 上的旧 `Kernel.elf` 抢先 |
| `CheckKernelFile` | `BootLoadKernel`，文件已在内存 | ELF 缓冲区和长度 | 不分配。写出装载下界 `LoadLow` 和页数 | 只收小端 64 位、机器类型 `EM_X86_64`（`0x3E`）的 `PT_LOAD`。下界是这些段物理地址的最小，上界是「物理地址 + 内存中大小」的最大 |
| `LoadKernelFile` | 只在检查成功之后 | 下界和页数 | `AllocatePages(AllocateAddress, EfiLoaderCode, …)` 钉在 `LoadLow`，整段清零，再按段拷贝。`EntryAddress` 写成 ELF 头里的 `Entry` | 内核用 `-fno-pie` 链在固定物理地址。文件里比内存短的那一截是 BSS，再清一次零 |
| `ScanOsMarkerVolumes` | `BootLoadKernel` 装入成功之后 | 无 | `OsIdSeen` 置 1 或 0 | 再扫一遍所有卷。表示「有没有见过标记」，不是「内核是从那一卷读的」 |
| `BootLoadKernel` | `UefiMain` | 交接包 | 填 `EntryAddress`、`OsIdSeen` | 读、查、装三步分开。任一步失败就返回，后面的 ACPI 和跳转不做 |
| `GetRsdpAddress` | `BootFillRsdp` | 无 | 无 | 先问 ACPI 2.0 的配置表 GUID，没有再问 1.0 |
| `BootFillRsdp` | `UefiMain` | 交接包 | `RsdpAddress`。找不到就写 0 并继续 | 没有 ACPI 也能把内核跑起来，内核自己决定怎么降级 |
| `GetXhciBaseAddress` | `BootFillXhci` | 无 | 写出一个 MMIO 基址，或失败 | 在 PCI 配置空间里找类 `0x0C`、子类 `0x03`、编程接口 `0x30`。BAR0 的类型位是 `10` 时再拼上 BAR1，得到 64 位地址 |
| `BootFillXhci` | `UefiMain` | 交接包 | `XhciBaseAddress`。找不到写 0 | 只记地址，不改命令寄存器，不开总线主控 |
| `JumpToKernel` | `UefiMain` 最后一句 | `ImageHandle` 和填好的交接包 | 成功时不再返回。`MemoryMap` 指向刚分配的描述符数组，然后调用入口 | `GetMemoryMap` 和 `ExitBootServices` 之间不能再调别的引导服务，否则地图钥匙作废。所以失败就重新取图，最多 8 次 |

#### 运行时怎么走

1. `ReadKernelFile` 用 `LoadedImage->DeviceHandle` 认出「这次 EFI 从哪块盘来」。QEMU 上那是 ESP。系统盘是另一块，根上有 `BLOCKS.ID`。
2. 读到的文件先放在任意物理页（`AllocateAnyPages`）。这还不是内核的运行地址。
3. `CheckKernelFile` 确认魔数 `0x7F 'E' 'L' 'F'`、64 位、`EM_X86_64`，程序头没有伸出文件，`PT_LOAD` 的物理范围没有回绕。页数用 `(跨度 + 4095) >> 12`，跨度大到加 4095 会回绕时拒绝。
4. `LoadKernelFile` 向固件要「正好从 `LoadLow` 开始」的页。固件已经占用这段时分配失败，串口打出 `AllocatePages` 失败，启动停在这里。成功后按每个 `PT_LOAD` 从文件偏移拷到 `PAddress`。入口数字来自 ELF 头，不来自段的起始。
5. `OsIdSeen` 再扫标记。然后 `BootFillRsdp`、写入 `SystemTable`、`BootFillXhci`。
6. `JumpToKernel` 先用空缓冲区调用 `GetMemoryMap`，固件返回 `EFI_BUFFER_TOO_SMALL` 并给出所需字节。多留 16 条描述符再分配。循环里取图、立刻 `ExitBootServices`。成功后把地图放进交接包，把 `EntryAddress` 转成函数指针调用。参数是交接包指针。注释写明 X64 上 UEFI 把第一个参数放在 `RCX`，内核入口先读 `RCX`。调用后面是 `__builtin_unreachable`：入口不该返回。

xHCI 有多颗时，代码意图是：厂商 `0x1B36`、设备 `0x000D`（QEMU 的 `qemu-xhci`，键鼠挂在这颗上）立刻采用；否则扫完取最后一颗。设备号的读法见 Q11，这项目前不能当成已经生效。

#### 依赖

文件系统、分配页、PCI I/O、ACPI 配置表、取内存图、退出引导服务，全部是 `gBS` 或 `UefiLib`，只能在退出之前用。退出之后内核只能使用交接包里的数字：入口、帧缓冲、RSDP、xHCI 基址、系统表指针、内存图。Boot 和内核各有一份 `UefiBootConfig.h`，互不包含，布局用 `_Static_assert` 钉死。本段写入的字段是 `EntryAddress`（偏移 72）、`RsdpAddress`（80）、`XhciBaseAddress`（96）、`OsIdSeen`（632），以及 `MemoryMap`（32，在跳转时写入）。

#### 本段改动

本段只读。

#### 仍欠着

- `GetXhciBaseAddress` 用宽度 `Uint32`、偏移 `0x02` 读设备号，再右移 16 位。配置空间偏移是字节。这一读跨过设备号和命令寄存器，右移后是命令寄存器，不是 `0x000D`。只有一颗 xHCI 时「最后一颗」仍然是对的。多颗时「优先 qemu-xhci」可能没起作用。本段没有改固件读法，也没有在 OVMF 里单步。
- 读文件失败时，`OpenKernelOnFs` 已经 `AllocatePages` 的缓冲没有 `FreePages`。这些页留在固件地图里，类型是 `EfiLoaderData`。内核收不收这类页，留到内存那一段看。
- `CheckKernelFile` 不检查 `Entry` 是否落在某个 `PT_LOAD` 里，也不检查字节 5 的小端标志。机器类型写死 `EM_X86_64`，因为这份 Boot 只编成 `BOOTX64.EFI`。
- `UefiBootConfig.h` 文件头仍写内核副本在 `Kernel/CodeA-HAL/X64/`。实际在 `Kernel/BringUp/X64/UefiBootConfig.h`。
- `VideoScore.c`、`VideoEdid.c`、`VideoTheme.c` 除了 `FsHasOsMarker` 以外，还没有逐函数写进白皮书。`GetVideoInfo` 的打分在 §4.3 有步骤。全库函数所在文件见 `Archive/柱规格/函数表.md`。

### 4.5 交接：`KernelEntry` → `KernelMain` → 模块表

### 4.6 十三份 `Initialize*`

六路同时读完：物理页、虚拟内存、`HAL/Init`、驱动框架、文件系统初始化、以及 Gui / 网络 / 控制台 / 调度的入口。本段只读。函数表仍以 `Archive/柱规格/函数表.md` 查名字和行号。

模块表把「返回值不是 0」当成失败并停住。下面这十三份里，会因此停表的只有：物理页没有 `BOOT_INFO` 区域、`HalPageKernelSetup` 失败、`HalInitialize` 失败（x86 上自 IPI 没计数到）、`HalNetInitialize` 失败。串口、视频、USB、文件系统、Gui、调度、控制台失败了也返回 0，表继续往下走。

#### 物理页

`InitializePhysicalMemory` 转到 `PhysicalMemoryInitialize`。空闲来自 `BOOT_INFO`：先按全部区域把 1GiB 段的页数撑开，位图先当成占用，再把 `Free != 0` 涂成空闲，然后把 `Free == 0` 涂回占用。内核末尾到引导分配器挖走的位图页再标占用。默认政策是段号从小到大、段内 first-fit，只从低于 4GiB 的段里给出页。`TOY_MEM_BESTFIT` 才换成学生的最短空洞。锁、段表、`PmmLookup` 留在框架里，学生只换 `MEMORY_OPS` 五件套。文件头仍写模块名 `"Memory"`，表上的名字是 `PhysicalMemory`。

4GiB 以上的页会被记进 `PageCount`，分配时直接跳过。涂占用时不写引用计数，所以保留页是「位占用、引用 0」。`FreePagesLocked` 在引用不大于 1 时会把这种页清回空闲。

#### 虚拟内存

`InitializeVirtualMemory` 调用 `HalPageKernelSetup(4096)` **新造**内核根，不接 `EarlyIdentityRoot`。x86 上早先那张静态恒等表在打开分页时被换掉，代码里没有释放它。然后按物理地址恒等映射帧缓冲（只有存在位和可写位），x86 再映射 LAPIC、IOAPIC、可选 xHCI 和已记下的 Runtime 区间。Arm64 / RiscV 的 `HalPlatformMapMmio` 是空函数。最后 `HalPagingEnable`。

用户拷贝不在初始化里。从用户读是逐字节，先要求当前页表上有 PRESENT 和 USER。写到当前用户地址时，碰上 COW 且不可写就新分配一页、拷满、映成可写、释放旧页。写到另一个地址空间不换页表，页必须已经可写，否则失败，不拆 COW。

#### 串口、CPU、多核、USB、视频

`InitializeSerial` 固定返回 0。x86 上 16550 的写入顺序与 Boot 相同，FIFO 控制字不同：Boot `0xC7`，内核 `0x07`（与 Q3 一致）。接收中断要等 IRQ4 路由成功才写 IER。

`InitializeCpu` 装 GDT/IDT、系统调用入口，并做 FPU 自检。FPU 失败只打日志。x86 的 `HalTimerInitialize` 是空函数，定时器不是在这里启动的。

`InitializeSmp` 拉应用处理器。一个都没起来也返回 0，单核继续。

`InitializeUsb` 只在全量表。x86 上它转到 `InputXhciInit`，里面是 `ToyDriverProbeClass(INPUT)`。没有键鼠也返回 0。非虚拟机才武装输入中断、把鼠标交到屏幕中心、排空积压报告。USB 串口认领不在这里。

`InitializeVideo` 用 `BOOT_INFO` 装分辨率，把字体号重置成 2、主题重置成默认，登记 `Gfx` 的画点和填矩形，打开串口镜像。核显和 HDA 的探针返回值丢掉。没有全屏清屏。

#### 驱动框架

`InitializeDriver` 清空设备表，x64 扫 PCI 配置空间填节点，然后 `HalDriverRegister`，**只** `ToyDriverProbeClass(BLOCK)`。不 Probe 全部，避免没有 8042 时 PS/2 在这里死循环。有匹配表的驱动，第一台 Probe 成功就 `break`，所以这一轮一个驱动只绑一个实例。`TOY_DRIVER_MAX_INSTANCES` 是 20，是全部驱动共用的槽，不是每驱动 20 台。Input / Net / 显示要等后面的模块再 Probe。块后端和网络后端都是单个指针，后挂上的覆盖先挂上的。

#### 文件系统

不读 `BLOCKS.ID`。最多扫 4 块盘上的 FAT，根目录有 `TOYOS.ID` 才把该卷标成系统卷；没有就用 `HELLO.ELF`、`Kernel.elf` 或 `TOYOS.DB` 能不能读到来挑默认卷。`FileSystemInitialize` 的每条返回都是 0，没有卷也算这个模块成功。本文件包含 `Store.h` 但没有调用；包含 `ShellCommands.h`，成功时 `ShellCommandsRegisterFs`。USB MSC 自动挂载和 USB 串口认领在这条函数里，不在 USB 模块里。

#### 桌面、网络、控制台、调度

`InitializeGui` 装数据库、点阵字体、`CJK.TTF`、主题和语言，失败照样返回 0。进桌面的提交在 `GuiInitialize` 调用的 `GuiRedraw` 末尾：`HalVideoPresentFlush`。语言默认中文，`TOYOS.DB` 的 `lang` 以 `en` 开头才改英文。非 x86 的 `FontTtfInit` 固定返回 -1。

`InitializeNetwork` 是 `HalNetInitialize`、极简 UDP 清队列、教学 `TcpInitialize`（状态清成 `TCP_CLOSED`）。这里不调用 `lwip_init`。lwIP 要等套接字、DHCP、商店或 shell 再懒初始化。x86 上网卡探测失败也不会让 `NetInit` 返回非 0，所以这条在 x86 上不停表。

`InitializeConsole` 再做一次 `LocaleInitialize`，注册内建命令。x86 的 `HalConsoleOnly` 恒为 0，所以总是全量 shell 命令。欢迎语不在这里打。

`InitializeScheduler` 把任务表清零，默认注册时间片轮转，并把「I/O 呼吸」登记给驱动。呼吸函数在关中断期间调用 `HalInputPoll` 和 `GuiPollMouseMotion`。这里不创建空闲任务，也不把调度器标成已上线。谁先跑见 §4.7。

### 4.7 谁先跑、第一帧、盘和系统调用

#### 谁先跑

多核桌面（x86 就是这条）：`SchedulerStart` 给每颗核造一个 idle，再把名字以 `sh`/`gu` 开头的任务钉到 CPU1，`wo` 钉到 CPU0。BSP 不等定时器，直接进入 **worker**。各 AP 进入自己的 idle。shell 和 gui 要等 CPU1 的定时器第一次摘队列。CPU 多于 2 时，CPU1 队头是 shell，后面是 gui，input 在 CPU2。正好 2 颗核时没有 input，CPU1 队头是教学任务 `KernelTaskDemo`，然后才是 shell、gui。单核时 BSP 直接进 shell，下一拍定时器先到 demo。

### 4.8 xHCI：从 BAR 到键鼠算就绪

x86 全量表里的 USB 模块会走到这里，QEMU 也走。本段只读。看的是 `TryXhciAt` → `Init` → `InitHw` → `EnumAndBind`，以及 Probe 怎样决定 `gXhciReady`。描述符、Hub、键盘队列没有往下读。

#### 两个成功不是一回事

`TryXhciAt` 先把 BAR 映成不可缓存的 MMIO。基址是 0 或低于 1MiB 返回 0。`Init` 返回 0 也返回 0。`Init` 成功就返回 1，这里不看有没有键鼠。

`Init`（`Xhci.c`）只做两步：`InitHw` 失败返回 0；成功则 `UsbHostControllerOffer`，返回值等于 `EnumAndBind`。`EnumAndBind` 找到键盘返回 1；三轮都没有键盘时再逐口试鼠标，然后仍然 `gXhciStarted = 1` 并返回 1。所以「控制器已经在跑、口上没有 HID」时，`Init` 仍是成功。

`gXhciReady` 不在 `Init` 里写。`InputXhciProbe.c` 的 `DriverProbe` 在 `TryXhciAt` 返回 1 之后，只有 `HidKeyboardReady()`（`gSlotId != 0`）或 `MousePresent()`（`gMouseSlotId != 0`）才把它写成 1。两个都没有就打 `XHCI up (no HID), try PS/2`，再走回退 BAR。键盘队列 `gKbdQ` 和槽位 `gSlotId` 都在 `Xhci.c`。`gXhciReady` 定义在 `UsbHid/InputXhci.c`，`DriverRemove` 清 0。

`AbandonNoHid` 会停 Run、撤回主机控制器、清槽位和 `gXhciStarted`。全仓库只有声明和定义，Probe 和 `Init` 都不调用它。注释写「无 HID 时放弃再试下一颗」，实际没有这条路。

#### 控制器怎么跑起来

`InitHw`：已经 `gXhciStarted` 且已有键或鼠，返回 1。已经启动但没有 HID，返回 0，避免把这次当成已经起来。因此第一颗控制器无 HID 把 `gXhciStarted` 置上之后，回退 BAR 再进 `Init` 会在这里直接失败，第二颗不会被复位。基址低于 1MiB 或没按 16 字节对齐也返回 0。

真机先 `InitHwRealPcDmar`（关翻译失败只记 `gXhciTe`，不因此失败），再 `InitHwMapCap`、读 HCSPARAMS1 得到槽数和口数，然后 `InitHwStartCtrl`。`TakeLegacy` 找不到 USB Legacy 能力就直接返回，不当成失败。真机接着 `HaltOnly`（只清 RS、等 HCH，不做 HCRST；注释写这台真机热复位后再写 RS 会挂），再 `StartController`。QEMU 走 `ResetController`（清 RS、写 HCRST、等 CNR）再 `StartController`。任一步失败返回 0。

`StartController` 建命令环和事件环并写 RS。真机沿用固件的 DCBAA（快照为 0 只打日志，仍继续），命令环用内核的 `gCmdRing`。QEMU 自建 DCBAA。`InitRing` 把最后一项做成指回环头的 Link TRB；它只用于命令环，事件环是另写的清零。写 RS 后等 HCH 清掉，超时返回 0。

`PowerConnectedPorts` 给已连接但没上电的口补 PP；一个连接都没有时给最多 32 个口上电。没有 CCS 也不让 `InitHw` 失败。`InitHwSurveyPorts` 只数连接口并打日志。

#### 口上的设备

`EnumAndBind` 最多 3 轮，每轮端口 1 到 `min(gMaxPorts, 32)` 调 `EnumTryRootPort`。没有键盘时真机等 50ms 再来一轮。然后按上一节：没有键盘就试独立口鼠标，两种结果都返回 1。

`EnumTryRootPort`：没有 CCS 返回 0。`ResetPort` 失败返回 0。真机上该口已经 PED 且 CCS 时不再写 PR。`AddressDevice` 或读设备描述符失败就 `DisableSlot` 并返回 0。Hub 走 `TryHubOnRootPort`。普通设备 `ParseConfig` 找不到 HID 中断端点就记入 `gPortNoHid`、关掉槽、返回 0。像鼠标的接口在真机上改走鼠标认领，本口不当键盘，返回 0。`SetConfig` 或真机的 `ConfigureIntr` 失败返回 0。成功则 `gUseGetReport = 0`，返回 1。

`EnumBindMouseAfterKbd` 在键盘之后找鼠标（Hub 子口、其余根口、键盘同一槽上的鼠标接口）。这些调用的返回值被丢掉。鼠标没绑上也不改 `EnumAndBind` 的返回 1。

`TryXhciAt` 在 QEMU 且已经有键或鼠时才开中断。真机要等 `InputXhciArmIrq`。这一截没有往下读。

### 4.9 块后端、换映像、上屏、iwl 认领

四段同时读。本段只读。

#### 谁留下块后端

换后端的只有 `BlockRegisterBackend`，它无条件改全局 `gBackend`。调用点在驱动 Probe 返回 0 之后的 Bind，不在块层自己的 Probe 里。Probe 返回非 0 就不 Bind，已有后端不动。

`HalDevices.c` 的注册顺序是 AHCI、ATA、NVMe。后一次成功的 Bind 盖掉前一次。同文件注释写「NVMe > AHCI > ATA」，和这个顺序不一致：ATA 排在 AHCI 后面，ATA 一旦 Bind 就会盖掉 AHCI。已经 Bound 的驱动会跳过，所以 `HalBlockInitialize` 再 Probe 一次不会把已绑的再绑一遍。

`Runtime/run.sh` 用 `ich9-ahci`，两块盘在 `ahci.0` / `ahci.1`，没有 NVMe 设备。NVMe 的匹配是 PCI `01/08/02`，对不上就不会进 Probe，也不会 Bind。AHCI 对得上 `01/06/01`。ATA 的 `Match` 是空的，框架总会拿空总线上下文去 Probe。`AtaProbe` 只看状态口 `0x1F7`：盘号大于 1、一直忙、或读到 `0xFF` 才返回 0，这时不 Bind，AHCI 留下。状态不是 `0xFF` 且 BSY 能清掉就返回 1，随后 Bind 把后端换成 ATA，哪怕还没读过扇区。仓库里没有 q35 上未接线 `0x1F7` 的实测字节，所以不能从「没挂 IDE 盘」断定 ATA 一定失败。OpenBox 的 `run-split.sh` 默认 `TOY_DISK=ide`，盘在 `ide.0`，能绑上的是 ATA。

`PortXfer` 对一块已经 Ready 的 AHCI 口做 512 字节 DMA。盘、缓冲或扇区数为 0 返回 0。每段先等 TFD 的 BSY 和 DRQ 清掉，填 64 字节 FIS 和一条 PRDT，把命令槽 0 的 CI bit0 置 1，再轮询。TFES、超时或事后 TFD 带 ERR 都返回 0，这一段改过的寄存器留在端口上。读成功才把 Bounce 拷回调用方缓冲。NVMe 的 `CtrlInit` 和 `Xfer` 没往下读。默认 `run.sh` 不加 `usb-storage`，MSC 认领失败时不装 Mux。

#### execve

`ProcessExecve` 不新建任务。它要求当前任务已经是用户任务。先在旧页表里把用户 `argv` 拷进内核，最多 8 条、每条 64 字节。`UserEnvp` 被丢掉。然后另建地址空间：拷内核根，按 `PT_LOAD` 映射。主程序只接受 `ET_EXEC`，偏置为 0。可写段加写权限；`PF_X` 不参与标志。栈是 16KiB，全 0。栈顶往下排字符串，再放 `argc`、各指针、一个空指针、再一个空指针当作 `envp`。新栈指针指着 `argc`。这些字节按新空间的物理页直接写，不切 CR3。

换上之后：任务的页表根和 `Brk` 换成新的，文件描述符和任务号留着。切到新页表，毁掉旧空间。`HalFrameSetUserEntry` 把整帧清零，再写入 ELF 的 `e_entry` 和这个栈指针。`SYS_EXECVE` 成功时不改返回槽，帧已被清零，返回寄存器是 0。x64 的 `syscall` 用 `sysretq` 离开，`int 0x80` 用 `iretq`，Arm64 用 `eret`，RiscV 用 `sret`。第一条用户指令就是 `e_entry`，通用寄存器是 0，`argc` 在栈上。

`ProcessExec` / `ProcessRunDemo` 是另一条路：装完后 `SchedulerCreateUser`，不走这次的 `sysret`。共享库自己的重定位表不处理，只重定位主程序。`COPY` 重定位直接失败。文件上限 512KiB。页表项怎么拆用户槽，这次没读。

#### 上屏和窗口

绘制只把矩形并进脏框，不立刻上屏。内容一块、光标一块，互并不并。`VideoPresent` 只把这两块 blit 到前缓冲。没有脏区就返回。它不调用 `VideoPresentFlush`。内容刷到一半就先返回，这一轮不刷光标。`VideoPresentFlush` 最多 8192 次调用 `VideoPresent`；仍脏才把整屏并进脏区再刷 8192 次。这是唯一的强制整屏入口。未缩放、脏块至少 64 像素、核显 Present 就绪时走一次 GPU 拷贝，失败再按行 `memcpy`。缩放路径是最近邻，不整缓冲拷贝。

窗口协议只在 `GuiInitialize` 里 `WindowOpsRegister` 一次。`SysCreateWindow` 走到 `WindowOpenUser`，再进 `GuiOpenUser`：占槽、画窗、`HalVideoPresentFlush` 一次，返回窗号。改字和贴像素不在自己的函数里 Present。轮询顺序是关、按钮、键、客户区点击；没有新输入返回 0；已经没有活动用户窗返回 1。

#### iwl 认领

x86 的 Worker 在图标扫完之后只调用一次 `HalIwlClaim`，返回值丢掉。它先打开 `gIwlBootClaimAllowed`，再 `IwlSetup`。认领只消费早先 Probe 经 `IwlAccept` 留下的总线号和 BAR：做 PCI 命令、映射 BAR、写一块本地 MAC（`02:54:4F:59` 加总线号和设备号），不读网卡 NVM，也不读约 2.4MB 的 `FW/IWL8265.UCODE`。没有待认领设备或 BAR 为 0 时返回 0。映射失败仍把 `gIwlReady` 置 1 并返回 1，只是不挂后台。两种结果都不停开机。

固件和关联在同一条 Worker 循环里的 `HalIwlBgPump`。`IwlBgStep` 拆成两圈：相 0 只读固件文件就返回，把 Worker 还回去；下一圈相 1 才跑 `IwlBringUpSta`。起站失败也被标成 `bg=done`，不再重试。芯片 MAC 要等起站里的 `IwlReadHwMac`，读失败就一直用本地地址。关联且 WPA2 成功后才把 8265 挂到无线槽。

### 4.10 页表用户槽、NVMe 传输、键盘报告

三路同时读。本段只读。

#### 用户页表根

`HalPageRootCreate` 只分配一张空白 PML4，不接早期恒等根。内核映射是 `HalPageRootCopy` 从 `HalPageKernelRoot()` 整表抄来的，抄完后下一级表仍和内核共享。

x86 的用户地址和恒等映射都在 PML4[0]，所以 `HalPagePrepareUserRoot` 必须把这一支拆开。先私有化 PML4[0] 指向的 PDPT。再把 PDPT[0] 指向的那张 PD 抄成私有的一份，避免以后改大页时改到内核的恒等表。用户区从 `0x40000000` 起，落在 PDPT[1]；这段覆盖到的 PDPT 槽被写成 0，后面的用户映射自己建表。失败返回 -1。槽里已经是大页时直接返回 0，不再往下拆。`HalPageTableLoad` 只写 CR3，不检查根。

Arm 只私有化 L0[0]，用户区从 `0x100000000` 起，和低 4GiB 恒等不在同一级表项。RiscV 的 `PrepareUserRoot` 是空函数，固定返回 0；用户区同样从 `0x100000000` 起，和内核巨页槽不重叠。

#### NVMe 传输

`CtrlInit`（`NvmeInitialize.c`）成功返回 1，任一步失败返回 0，只有全部成功才写 `C->Ready`。它映射 BAR 16KiB，一次分配 6 页（Admin 和 IO 的提交/完成队列、Identify 缓冲、bounce），等控制器 RDY，Identify NSID=1，再建 QID=1 的 IO 队列。LBA 大小指数不在 9 到 12 就改成 9。不写全局 `gReady`。

`Xfer` 只往这一个 IO 队列投命令。`C->Ready` 未置、或 `LbaShift` 不是 9（只要 512 字节扇区），返回 0。每次最多 8 个扇区，经 bounce。完成状态非 0 或超时返回 0，不把 `C->Ready` 清掉。读到一半时目标缓冲里可能已经有前几块。

#### 从 Address 到键盘队列

`AddressDeviceOnPort` 成功返回 1，失败返回 0。Enable Slot 失败、slot 为 0、或 Address Device 完成码不成功，都返回 0。失败时它不 `DisableSlot`，调用方拆槽。命令门铃只敲命令环。设备门铃要到 `QueueIntr` 才敲键盘中断端点。

`GetDesc` / `GetDeviceDesc` 成功返回 0，失败返回 -1。`SetConfig` 同样是 0 / -1。`ParseConfig` 找到中断 IN 返回 1，没有返回 0。`ConfigureIntr` 成功 1，失败 0。同一层里，描述符是「0 成功」，配端点是「1 成功」。

`ParseConfig` 给 boot 键盘打最高分，找到就立刻返回，这时不写 `gKbdParseScore`。`SetProtocolBoot` 和 `SetIdle` 的失败被忽略。

根口上的 hub 先拆掉刚才的普通 slot，再按 hub 重新 Address。子口扫到键盘返回 1。子设备自己又是 hub 就拆掉，不做第二层。

键盘报告：完成码是成功或短包才把 `gReportBuf` 推进 `gKbdQ`。队列 16 格，写指针再走一格就会追上读指针时，`KbdPush` 直接丢掉这份报告。完成路径入队不拿 `gHidQueueLock`，出队和 GET_REPORT 那条旁路拿锁。枚举成功后 `gUseGetReport` 清 0，旁路默认不走。`InterruptQueue` 不用调用方的缓冲，长度夹到最多 8 字节。

### 4.11 用户入口、无线握手、绘制、收包

四路同时读。本段只读。

#### 用户程序从哪读 argc

三套 CRT 都从用户栈顶读 `argc`，不是从寄存器。x64 是 `mov rdi, [rsp]`，Arm64 是 `ldr x0, [sp]`，RiscV 是 `ld a0, 0(sp)`，然后 `argv` 指向栈上 `+8`。`HalFrameSetUserEntry` 把通用寄存器清零，所以首入时寄存器里的参数是 0，CRT 马上用栈上的值盖掉。

栈布局和 `ProcessSetupArgvStack` 一致：`argc`、各 `argv` 指针、一个空指针、再一个空指针当作 `envp`。`ProcessRunDemo` 不铺这个栈，页是清零的，读出来的 `argc` 是 0。

第一次进用户任务（`ProcessExec` / `ProcessRunDemo`）走 `SchedulerCreateUser`。它把帧放在该任务的内核栈顶，`Started=0`，只记下页表根，不加载。真正切页表的是 `ActivateTask`。x64 时钟看到「第一次进用户」才走 `UserEnter`，用 `iretq` 离开，用户 `RSP` 指着 `argc`。Arm64 / RiscV 的抢占不跳这个函数，直接 `eret` / `sret`。`execve` 仍不走这条，它改当前帧并 `sysret`。

`CwdResolve` 只改调用方的路径缓冲，不改任务里的当前目录。绝对路径、空当前目录、或第一段带 `:` 的卷名，原样返回 0。相对路径把当前目录接在前面。装不下返回 -1，缓冲保持原样。

#### 扫描和四次握手

`IwlScanCollect` 最多 8000 轮收扫描帧。信标里的 SSID 对上 `gIwlSsid` 返回 1，并填 `gIwlTarget`。轮次用尽返回 0。

`IwlEapol.c` 的文件头仍写「GTK 解包略」。`IwlEapolHand.c` 在 M3 校验通过后调用 `IwlInstallGtk`，把组密钥解进 `gIwlGtk`。解失败只打日志，握手仍可返回 1。装进固件的只有 PTK。`IwlStaKeysInstall` 失败打 `key=soft`，不让握手失败。

固件 TLV 从偏移 88 走。类型 19 进运行时镜像，类型 20 进 INIT 镜像。两段都有内容才算解析成功。`IwlRxInit` / `IwlTxInit` 成功返回 1，分配或锁失败返回 0。

#### 绘制记账和 EHCI 键盘

没有叫 `VideoFill` 的函数。`VideoFillRect` 把裁剪后的整块矩形并进脏区。`VideoDrawPixelRaw` 记 1×1。字形自己不记一块，每个画上的像素各记 1×1。滚屏记整块裁剪区，`ScrollScreen` 记整屏。

`IgpuPresentRect` 成功返回 1，失败返回 0。函数体内没有 CPU 回退。它往 BCS ring 提交 `XY_SRC_COPY`。返回 0 之后，`PresentRectRows` 才走 `memcpy`。

EHCI 的 Probe 在 `InputEhci.c`，成功返回 0，和 xHCI 的 Probe 约定一样。`Setup` 成功返回 1。只要 PCI 上有 EHCI，就算 `InitOne` 失败也把 `gEhciReady` 置 1。键盘不走 `UsbHid/`，出队是 EHCI 自己的 `HidKeyboardDequeue`。两边都挂上输入后端，实现是两套。

#### 收包和商店

virtio-net 没有收包中断处理函数。Shell 循环里轮询。`gLwIpRx` 为 0 时，教学栈里目的 IP 不是本机就丢掉，帧仍挂回接收环。为 1 时整帧交给 `ToyNetifInput`，不再进 `HandleIpPacket`。这个标志只在 lwIP 的 netif 绑定成功后置 1。绑定失败就继续进教学 TCP。x86 PCI virtio 和 MMIO virtio 各有一份 `gLwIpRx`。

开机扫商店在 Worker 的 `DesktopEnsureIconsLoaded`，读的是内存里 `TOYOS.DB` 的 `si.*`。清单失败时图标为空，仍把图标标成已加载，不挡后面的 ready。`StoreJobStep` 只在商店窗正在干活时才跑。

`VfsServiceReadFile` 注册的是 `FileSystemReadFile`，挂的是 FAT 时最终进 `FatReadFile`。`make FS=ram` 时同名入口改指向内存桩。

### 4.12 EHCI：复位、第一只键盘、Bulk

本段只读。Probe 仍在 `InputEhci.c`，成功返回 0。这里补控制器起来之后。

`InitOne` 不建队列。BAR 太低或映射失败才返回 0。停跑超时被忽略。HCReset 等到超时只打日志，然后仍然写 `CONFIGFLAG`、扫连接、`C->Up = 1` 并返回 1。队列和调度在后面的 `SchedStart`。

`HidBringup` 先把 HID 就绪和队列清掉，再对每只已经 Up 的控制器 `SchedStart`，然后 `EnumHid`。找到第一只 HID 就 `HidArmIntr`，记下 `gHidCtrl`，`gEhciHidReady = 1`，返回 1，不再看后面的控制器。一只都没有则返回 0。

键盘环 8 槽，在 `HidPoll.c`。qTD 仍 Active 就跳过。Halted 则重挂中断，不入队。长度至少 3 且协议是键盘时，把报告前 8 字节交给 `PushKbd`。`(tail+1)%8 == head` 时丢掉新报告，不覆盖旧的。`HidKeyboardDequeue` 空队返回 0。

Bulk 的 `WaitQtd`：Active 已清，且 Halted、Buffer Error、Babble、事务错误都没有，返回 1。任一错误位，或大约 800 万次仍 Active，返回 0。`BulkXfer` 在 `WaitQtd` 失败或随后关异步失败时返回 -1，两步都过才返回 0。

### 4.14 商店作业和字形

本段只读。

#### 商店作业

`StoreJobStep` 忙的时候每次只推一个相位，返回 0。空闲或这一趟结束返回 1。相位是计划、包、字体、重载、结束。

计划不写盘。安装、卸载、同步、拉取会写文件，并改 `TOYOS.DB` 里的 `si.` / `sd.`。安装拷贝没完就留在包这一相，不记错。失败把错误码放进 `gJobErr`。结束时抄到 `gJobLastErr`，状态行是 `installed`、`removed`、`fetched`、`sync ok`，或对应的 fail。计划长度是 0 的安装写成 `already installed`。

取消把错误码设成 -100，相位跳到重载。取消前已经写入的文件这一步不删。

#### 一个字怎么变成像素

ASCII（码点小于 128）用当前 Terminus 字模，1 位一个像素。16×32 是默认，10×18 是另一张。字模指针空就什么都不画，不画缺字框。

其余码点先看 TTF 缓存，命中则 8 位深。否则 `FontCjk32Lookup`：18×18，4 位深，7445 字。`Font.h` 写的是「默认 16×16×4bpp」，和 `CJK32_DIM` 的 18 不一致。查找失败才画缺字框，边长是 18 乘缩放，四边各一条像素。

4 位深时一字节两个像素，高半字节是偶数列。小于等于 4 当透明，大于等于 10 当实心。

### 4.17 EHCI 调度和枚举入口

本段只读。

`SchedStart` 成功返回 1，并置 `C->Sched`。失败只返回 0，不改 `C->Up`。控制器没 Up 就返回 0。已经 `Sched` 则直接返回 1。DMA 三页申请失败、地址不在 4G 内、映射失败、或 ASE 握手超时，都返回 0，`Sched` 保持 0。超时前可能已经把 Run 和 ASE 写进命令寄存器，控制器继续跑。

异步队列是一个回收头水平链到控制 QH，控制 QH 再链回头。周期帧表 1024 项都指向中断 QH。这一步把周期表基址写上，但不开周期调度使能。开周期在同文件的 `SchedEnablePeriodic`，`SchedStart` 不调用它。

`EnumHid` 要求已经 `Sched`，否则返回 0。只走有设备连接的口。某一口 `EnumRootPort` 成功就立刻返回 1，不再看后面的口。类是 hub（`0x09`）才在这里发 SET_ADDRESS。普通设备的地址、端点和协议在没读的 `EnumDevice` 里。

### 4.18 命令登记和 MIC

本段只读。

命令进表的入口是 `InitializeConsole`。先登记五个内置：`help`、`clear`、`echo`、`alias`、`unalias`。完整启动再经 `ShellCommandsRegister` 挂上 `list`、`execute`、`net`、`tcp` 等一级名。文件系统就绪后 `ShellCommandsRegisterFs` 再挂文件命令。`ls` 和 `dir` 是 `list` 的别名。`exec` 是 `execute` 的别名。命令函数类型是 `void`，失败不把状态交回分发。

`help` 只按表打名字和帮助，没有失败分支，不改当前任务。`ls` 成功时由文件系统按项打行，命令自己不打 `ok`。失败打 `ls: ` 加错误串，不换当前任务。`exec` 成功时停掉除当前任务以外的用户任务，再 `SchedulerCreateUser` 另起一个用户任务，不替换正在跑这条命令的任务。失败时 `ProcessExec` 返回的 `-1` 被丢掉，错误字在内部已经打过。

`IwlEapolMic` 没有成败返回。KCK 只读。算完总会把 16 字节 MIC 写进调用方的缓冲，并写回 EAPOL 里从第 81 字节起的 16 字节。版本 3 走 AES-CMAC，其余走 HMAC-SHA1。

`IwlAesUnwrap` 成功返回 1，并写出明文。失败返回 0，发生在拷进输出缓冲之前，所以调用方的明文缓冲和长度保持原样，KEK 也不改。`IwlInstallGtk` 在调用前把 GTK 长度置 0。解包失败就返回，不写新的 GTK。

### 4.19 EHCI 普通设备

本段只读。

### 4.30 物理页、地址空间和装载

本段只读。

### 4.31 教学 TCP 入站

本段只读。

这几条入站路径不主动发 RST。段短于 20 字节或首部长度不合法，直接返回，状态不动。出站 RST 只在重传次数到顶时，由 `TcpRetransmit` 发出。

`SYN_SENT` 要同时看到 SYN 和 ACK 才进入已建立。不核对本端序号。对端 RST 也停在 `SYN_SENT`，不回包。`SYN_RECEIVED` 要有 ACK，且确认号等于 `gSndNxt`，才进入已建立。

已建立之后，对端 RST 把状态改成 `TCP_CLOSED` 就返回。接收缓冲和序号留着，不回 RST。数据序号中间有洞，只回纯 ACK，序号不动。服务端回显先把接收序号按整段前移再发送。发送失败时接收序号已经前进，发送序号不前进。

FIN 只有序号刚好接上已收数据才推进。服务端这次应答带 FIN，状态变成已关闭。客户端状态仍是已建立，只记下对端已关。

### 4.32 两边的陷阱

本段只读。

Arm64 用户态系统调用从向量表的低异常级同步槽进 `HalExcLowerSync`，再进 `HalExceptionLower`。系统调用号在 `x8`，交给 `SyscallDispatch`。内核同步异常只认取指和数据中止。probe 置位时跳过故障指令。否则调用 `VirtualMemoryHandlePageFault`，写位算出来后丢掉。不是中止、或没人接的缺页，串口打一行后 `wfi` 停住，没有共用的停机函数。

RiscV 内核和用户共用 `HalTrapVector`。用户 `ecall` 的 cause 是 8，号在 `a7`，同样交给 `SyscallDispatch`，并且先把 `sepc` 加 4。内核只认 cause 12、13、15 的缺页。S 态 `ecall` 不走用户路径，直接停。不是定时器的中断只打一行，然后返回，不停机。

两边自测的 `SYS_EXIT` 都不进 `SyscallDispatch`。调度返回值的低 2 位用来决定是 `eret`/`sret` 回原帧，还是直接跳进内核。

### Q3. 16550 的常规顺序是什么？

芯片手册没有规定「必须第几行」，但寄存器有两处硬件约束，软件就都收成了同一套顺序。PC 早期启动和 OSDev 上的串口示例都是这套；Boot 的七步就是它，前面多了一次暂存格探测。

基址 `0x3F8` 起八个寄存器。线路控制寄存器（+3）的最高位叫 DLAB：

| 偏移 | DLAB = 0（平时） | DLAB = 1（改波特率时） |
| ---- | ---------------- | ---------------------- |
| +0 | 发送/接收数据 | 除数低字节 |
| +1 | 中断使能 IER | 除数高字节 |
| +2 | FIFO 控制（只写） | 同左 |
| +3 | 线路控制：数据位、校验、停止位、DLAB | 同左 |
| +4 | 调制解调器控制：DTR、RTS、OUT2 | 同左 |
| +5 | 线路状态：能不能发送、发送完了没有 | 同左 |
| +7 | 暂存格，不参与收发 | 同左 |

顺序和原因：

1. **先关中断（+1 写 0）。** DLAB 打开之后，+1 不再是中断使能，而是除数高字节。所以中断必须在打开 DLAB **之前**关掉，否则改波特率的途中关不掉中断。
2. **打开 DLAB（+3 写 `0x80`）。** 不打开，写到 +0 的是「发出去的字节」，不是波特率。
3. **写除数。** PC 上参考钟 1.8432 MHz，内部先除 16，得到 115200；再除以这个 16 位除数才是波特率。除数 1 = 115200。低字节写 +0，高字节写 +1。
4. **写帧格式并关掉 DLAB（+3 写 `0x03`）。** `0x03` 是 8 数据位、无校验、1 停止位。最高位是 0，DLAB 关上。若不关，下一字节会写进除数，波特率被改掉，线上也发不出字符。
5. **启用并清空 FIFO（+2）。** 16550 相对更老的 8250 多了 16 字节硬件缓冲。教学示例常写 `0xC7`：使能、清空收发、接收触发水位 14 字节。Boot 用的就是这个值。
6. **最后拉起口线（+4 写 `0x0B`）。** DTR、RTS 告诉对面「我准备好了」；OUT2 在 PC 上把这块芯片的中断接到中断控制器。放在最后，是等波特率和帧格式已经稳定再让对面看见这个口。`0x0B` 并不打开 UART 自己的中断使能（那是第 1 步已经写 0 的 IER）。

OSDev 的示例在第 6 步之后还会把芯片放进环回、自发自收一个 `0xAE` 做自检。Boot 没有做这一步，改用第 0 步的暂存格读写（`0x55` / `0xAA`）判断芯片在不在。内核 `Drivers/Serial.c` 的探测和前五步与 Boot 相同；FIFO 它写的是 `0x07`（触发水位 1 字节），注释写明不用 14 字节水位，因为离收满只剩 2 字节。Boot 仍是教学示例里的 `0xC7`。Boot 只发送，这个水位几乎不影响日志。

### Q4. UART 是什么？`0x55` / `0xAA` 是魔法数吗？为什么和 BIOS 最后两个字节一样？

**UART** 是 Universal Asynchronous Receiver-Transmitter：通用异步收发器。它把 CPU 的一个字节变成线上按固定波特率逐位送出的波形，对面再装回一个字节。中间没有共享时钟线，所以两边必须事先说好波特率和帧格式（Boot 里是 115200、8N1）。16550 是这类芯片里 PC 最常见的一款；COM1 是主板上第一路 UART 的传统名字，端口基址 `0x3F8`。

`0x55` 和 `0xAA` 当时是源码里的魔数（字面量，旁边没有名字）。JX 之后起名为 `UART_SCRATCH_A` / `UART_SCRATCH_B`，含义不变。它们**不是** 16550 手册规定的「我是 UART」身份证。手册只说偏移 +7 是一块可读写的暂存格，写什么读回什么。Boot 用这两个值做存在性测试：写进去，读出来，两次都一致才相信这里有芯片。没有芯片时，读口常常得到 `0xFF`（线被拉高），测试失败。

这两个值本身是交错的位：`0x55` = `01010101`，`0xAA` = `10101010`。卡在全 0、卡在全 1、或者数据位之间短路，都很难两次都碰巧读对。内存检测、寄存器探测里到处用这对图案，原因相同。

和「BIOS 最后两个字节」是同一对图案，不是同一个约定。主引导扇区 512 字节的最后两字节（偏移 510、511）固定放 `55 AA`，BIOS 用它判断「这一扇区是可启动的」。扩展 ROM 则把 `55 AA` 放在开头。那边是相邻两字节组成的签名，照这个顺序出现才算数。串口这里是对同一格写两次、各读一次，`55` 对上且 `AA` 对上即可，并不检查「55 后面紧挨着 AA」。选中它们，是因为位图案好用，又是人眼熟的两个数。

### Q5. Boot 的串口没有借助 UEFI 的串口能力？

没有。`BootPkg` 里搜不到 `SerialIo`、`ConOut`、`LocateProtocol`。EDK2 里有现成的 `EFI_SERIAL_IO_PROTOCOL`（`MdePkg/Include/Protocol/SerialIo.h`），固件若提供这个协议，应用程序应 `LocateProtocol` 拿到它，再调用上面的 `SetAttributes` / `Write`。那样波特率、有没有这块口，都由固件回答。

Boot 绕开了这层，自己对 `0x3F8` 做 `in`/`out`。QEMU 的 `-serial stdio` 接的正是这块传统 COM1，所以终端里看得到字。OVMF 自己多半也在用同一块芯片；Boot 初始化时会按 16550 的顺序把它再配一遍。

这样写有一个直接好处：和内核 `Drivers/Serial.c` 是同一块芯片、同一套波特率，日志从 Boot 接到内核不用换口。`in`/`out` 在 `ExitBootServices` 之后仍然合法；UEFI 的串口协议在告别固件之后就不能再调了。

代价也明确。有些机器没有 `0x3F8` 这块传统口，串口只存在于固件给出的协议后面（USB 转串口、别的 PCI 口）。那种机器上，走协议能打字，Boot 现在的探测会失败，然后全程静默。这是最短路径：为了和内核、和 QEMU 对齐，没有走 UEFI 给应用程序规定的那条路。教学上先保持这样，把「绕过固件」写在注释里；真要照顾没有 COM1 的机器，再加一条协议路径，而不是换成只靠协议、把现在这条删掉。

### Q6. `BootSerialIn8` 这种叫内联汇编吗？是什么语法？

是。这是 **GCC 扩展内联汇编**（GNU C extended asm）。Clang 在 x86 上认同一套。微软编译器的 `__asm { }` 是另一种写法，这里不是那种。Boot 用 EDK2 的 GCC 工具链，所以写成这样。

`static inline` 是另一件事：请编译器把这个函数贴进调用处，不要真的 `call`。贴进去之后，里面仍是一条汇编。

整句的骨架是：

```text
__asm__ volatile ( "指令模板" : 输出 : 输入 : 被破坏的寄存器 );
```

`BootSerialIn8` 没有第四段（没有额外搞坏的寄存器）。

| 片段 | 这一句里 | 含义 |
| ---- | -------- | ---- |
| `__asm__` | 关键字 | 即使开了严格 C 标准，也承认这是汇编。`asm` 在某些编译选项下会被收成普通标识符 |
| `volatile` | 紧跟在后 | 这条指令有硬件副作用。编译器不许把它删掉，也不许和别的 `volatile` 访问随便对调 |
| `"inb %1, %0"` | 指令模板 | AT&T 语法：源在前，目的在后。`inb` 从端口读一个字节。`%0`、`%1` 是操作数编号 |
| `: "=a"(Value)` | 输出 | `=` 表示只写。`a` 表示结果放在 `AL`（8 位时就是累加器的低字节），并写回 C 变量 `Value` |
| `: "Nd"(Port)` | 输入 | 端口放进这个约束允许的地方 |

编号先数输出、再数输入。这里只有一个输出，所以 `%0` 是 `Value`，`%1` 是 `Port`。模板写成 `inb %1, %0`，就是「从端口读进 `AL`」。

`"Nd"` 是 x86 上给 `in`/`out` 用的标准约束，两个字母是两选一：

- `N`：编译期就能看出、并且小于 256 的端口号，直接编进指令（`inb $端口, %al`）。
- `d`：放进 `DX`。端口大于等于 256 时，立即数形式放不下，必须走 `DX`。

COM1 在 `0x3F8`，超过 255，所以实际会先把端口送进 `DX`，再执行 `inb %dx, %al`。函数是 `inline`，调用处若是 `BOOT_COM1 + 5` 这种常数，编译器在贴进来之后才做这个选择。

上面的 `BootSerialOut8` 是同一语法，只是没有输出：`"outb %0, %1" : : "a"(Value), "Nd"(Port)`。`%0` 这时是第一个输入 `Value`（在 `AL` 里），`%1` 是端口。

### Q7. UEFI 能发现 USB 转串口吗？能不能靠它把早期日志打出来？

固件多半能在 USB 总线上看见这根棒，但通常**不会**把它变成一把可以写的串口。Boot 因此不能靠问固件，在内核起来之前就把日志送到 FTDI 一类的棒上。

UEFI 给应用程序的串口协议是 `EFI_SERIAL_IO_PROTOCOL`。固件只有在自己带了对应驱动时才会安装它。主板自带的 16550（COM1）经常有。USB 转串口要看芯片：

| 棒 | 固件通常怎么对待 |
| -- | ---------------- |
| FTDI、CH340、CP2102、PL2303 | 厂商私有协议。家用主板和 OVMF 几乎都不带这些驱动。总线上看得到设备，没有 `SerialIo` 可写 |
| USB CDC-ACM（标准串口类） | 规范上能写驱动。消费级固件和当前这份 OVMF 裁剪树里没有这份驱动 |

Boot 若自己在 `ExitBootServices` 之前用 `EFI_USB_IO_PROTOCOL` 去说 FTDI 或 CDC，等于在 EFI 里再写一遍内核已有的认领程序。告别固件时这套 USB 栈作废，棒立刻停。16550 不一样：它是端口上的芯片，`in`/`out` 不依赖固件，告别之后字节还在走。

内核这边，USB 串口故意排在文件系统认盘之后。`KernelModulesInit.c` 写明：更早去扫 FTDI 会复位还没认领的 hub 根口，NUC 上 U 盘批量传输随之超时，桌面读壁纸图标时像卡住。认领本身在 `HalUsbUartClaim`：先 xHCI 上的 FTDI，再 EHCI，最后 CDC。所以「滞后」是为了不拆掉 U 盘，不是还没写到。

因此：有 COM1 的机器，早期日志继续走现在的 16550。只有 USB 棒的机器，Boot 阶段和内核认领之前会有一段空白；把认领提前要先解决 hub 复位，而不是改问 UEFI。

### Q8. `JumpToKernel.c` 里的 `Entry` 改成 `KernelEntry` 会冲突吗？

不会。它是 `ExitBootServices` 成功之后的局部变量，类型是函数指针 `KERNEL_ENTRY_FN`，不进符号表。

旁边这些同名东西不和它抢：

| 名字 | 在哪 | 为什么不冲突 |
| ---- | ---- | ------------ |
| `KERNEL_ENTRY_FN` | 同一函数里的 typedef | 标识符不同 |
| `BootConfig->EntryAddress` | `UEFI_BOOT_CONFIG` 的字段 | 结构体成员有自己的名字空间 |
| `ELF_HEADER_64.Entry` | `LoadKernel.c` | 另一个文件里的结构体成员 |
| 汇编符号 `KernelEntry` | `Kernel/HAL/X64/KernelEntry.S`，`link.ld` 的 `ENTRY` | 在 `Kernel.elf` 里。`BOOTX64.EFI` 不和内核链在一起，只跳到 `EntryAddress` 那个数 |
| `TOY_BOOT_CONFIG.KernelEntry` | 内核侧 `BootHandoff.h`，偏移 72 | 和 Boot 的 `EntryAddress` 是同一格，但是内核那份头。`JumpToKernel.c` 包含的是 `UefiBootConfig.h`，看不到这个字段名 |
| `CDROM_DEVICE_PATH.KernelEntry` | EDK2 的设备路径 | 也是结构体成员，本函数用不到 |

改名只影响读代码的人：这个局部变量会和「内核入口函数 `KernelEntry`」以及「交接包里那个入口地址字段」用同一个词。编译和链接都过。

### Q9. 交接包里的入口地址用的是什么词？

同一格，偏移 72，两边用词不同。

| 侧 | 结构体 | 字段 |
| -- | ------ | ---- |
| Boot，权威布局 | `UEFI_BOOT_CONFIG`（`UefiBootConfig.h`） | `EntryAddress` |
| 内核那份副本 | `TOY_BOOT_CONFIG`（`BootHandoff.h`） | `KernelEntry` |

都是 `UINT64`，存的是入口地址这个数，不是函数名。内核头注释写明 `KernelEntry` 是历史名字，与 Boot 的 `EntryAddress` 同偏移。

随后名字收成一套：字段叫 `EntryAddress`，结构体叫 `UEFI_BOOT_CONFIG`。文件名也一样，是两份内容相同的 `UefiBootConfig.h`（`Boot/BootPkg/` 与 `Kernel/HAL/X64/`），互不包含，以便各自单独编译。`KernelEntry` 只留给 `KernelEntry.S` 里的函数。

### Q10. `LoadKernel.c` 里那四条路径是在读双盘吗？`Blocks` 是盘符吗？

不是盘符。UEFI 打开文件没有 `C:` 这种盘符。`OpenKernelOnFs` 拿到的是**已经选定的一卷**，再按顺序试这四条卷内路径：

| 路径 | 是什么 |
| ---- | ------ |
| `\Kernel.elf`、`\KERNEL.ELF` | 卷根上的内核文件。QEMU 的 `RootFs/X64/Kernel.elf` 走第一条 |
| `\EFI\Blocks\Kernel.elf` | 该卷里一个叫 `Blocks` 的目录，不是名叫 Blocks 的盘 |
| `\EFI\ToyOS\Kernel.elf` | 旧目录名，注释写了兼容 |

选哪一卷在 `ReadKernelFile`，不在这四条字符串里。固件列出所有简单文件系统之后分三遍：

1. 卷根有 `BLOCKS.ID` 或旧的 `TOYOS.ID`（`FsHasOsMarker`）。QEMU 上这是 disk1，`RootFs/X64`。
2. 其它不是「本次 EFI 从哪块盘加载」的卷。
3. 启动卷兜底，也就是放着 `BOOTX64.EFI` 的 ESP（disk0）。

所以双盘是：先认系统卷上的标记文件，再在该卷里找 `Kernel.elf`。标记认对了，就不会去加载启动盘上可能过期的那份内核。

### Q11. `FillXhci.c` 里优先 qemu-xhci 的比较，比的是设备号吗？

意图是。注释写优先厂商 `0x1B36`、设备 `0x000D`。厂商号来自偏移 `0x00` 的 32 位读的低 16 位，这是配置空间里的厂商号。

设备号不是。同一次风格的读放在偏移 `0x02`、宽度 `Uint32`，再取高 16 位。`Pci.Read` 的偏移是字节。从字节 2 起的 4 字节是：设备号高字节、命令寄存器低字节、命令寄存器高字节，以及再往后一字节。小端拼成 32 位后右移 16 位，得到的是命令寄存器，常见值是「存储器空间 / 总线主控已打开」那几位，不是 `0x000D`。

类、子类、编程接口的那一次读在偏移 `0x08`，移位和 PCI 配置空间布局一致，xHCI 的 `0x0C / 0x03 / 0x30` 这条判断是对的。BAR0 在偏移 `0x10`，64 位 BAR 再读 `0x14`，也是对的。

因此：能找到 xHCI。只有一颗时，扫完取最后一颗，基址仍然对。有多颗时，可能没有提前停在 `qemu-xhci` 上。本段只读，不改。

### Q12. xHCI 的 `Init` 返回 1，是不是键鼠已经能用？

不是。`Init` 返回 1 只表示控制器跑起来了，并且枚举走完了。没有键盘、也没有鼠标时，`EnumAndBind` 仍然返回 1，`gXhciStarted` 置 1。键鼠能不能用看 `gXhciReady`，它只在 Probe 里、`gSlotId` 或 `gMouseSlotId` 非 0 时才置 1。两个槽都空时日志是 `XHCI up (no HID), try PS/2`，输入改走 PS/2。

### Q13. 块后端是按注释里的 NVMe、AHCI、ATA 覆盖吗？

不是。`HalDevices.c` 先登记 AHCI，再 ATA，再 NVMe。覆盖发生在 Bind 成功时，后一次成功换掉 `gBackend`。ATA 排在 AHCI 后面。日常 `run.sh` 没有 NVMe 设备，NVMe 不会 Bind。ATA 只有状态口一直忙或读到 `0xFF` 才放弃；否则会盖掉 AHCI。这块读数仓库里没有记录。

### Q14. `VideoPresent` 会再调 `Flush` 吗？

不会。`VideoPresent` 只刷已经记下的内容脏框和光标脏框，刷完就停。`VideoPresentFlush` 循环调 `VideoPresent`。8192 轮后仍脏，才把整屏并进脏区再刷。

### Q15. `execve` 会新建一个任务吗？

不会。它换掉当前用户任务的地址空间和中断帧。成功之后返回寄存器是 0，离开内核的第一条用户指令是 ELF 的 `e_entry`。`argc` 在用户栈顶，不在参数寄存器里。环境变量被丢掉。`ProcessExec` 那条才会 `SchedulerCreateUser`。

### Q16. Worker 里的 `HalIwlClaim` 会读固件、关联无线吗？

不会。这一次只映射 Probe 留下的 BAR，并写一块本地 MAC。固件文件和起站在后面的 `HalIwlBgPump`，而且拆成两圈，避免在认领时卡住。没有卡或映射失败都不停开机。起站失败标成做完，不再重试。

### Q17. 用户页表是从早期恒等根接过来的吗？

不是。`HalPageRootCreate` 是一张空白 PML4。内核映射从当前内核根整表抄来。x86 上用户地址和恒等映射同在 PML4[0]，所以还要把这一支私有化，并把 `0x40000000` 所在的 PDPT 槽清掉，避免用户映射改到内核的表。Arm 和 RiscV 的用户区从 `0x100000000` 起，和低 4GiB 不在同一槽。

### Q18. USB 键盘报告会不会把队列里的旧键覆盖掉？

不会覆盖。队列 16 格，还剩最后一格空位时 `KbdPush` 直接丢掉新报告。完成路径入队不拿锁，出队拿锁。

### Q19. 用户程序的 argc 是内核放进寄存器的吗？

不是。三套 CRT 都从用户栈顶读。内核把通用寄存器清成 0。`ProcessRunDemo` 不铺参数，清零的栈读出来就是 0。

### Q20. iwl 的文件头写 GTK 解包从略，代码是这样吗？

不是。`IwlEapolHand.c` 会调用 `IwlInstallGtk`，把组密钥放进主机缓冲。装进固件的只有 PTK。解 GTK 失败不让握手返回失败。

### Q21. EHCI 键盘和 xHCI 共用 UsbHid 吗？

不共用。EHCI 的出队在 `Ehci/HidPoll.c`。`UsbHid/Keyboard.c` 只给 xHCI 设灯。两套都挂到输入后端。有 PCI EHCI 时，就算初始化失败，`gEhciReady` 也会置 1。

### Q22. EHCI 复位超时，这只控制器还算起来了吗？

算。`InitOne` 在 HCReset 超时后只打日志，仍然 `C->Up = 1` 并返回 1。队列不在这一步建，在后面的 `SchedStart`。键盘环 8 槽，满了丢新报告。

### Q23. 开机时核显和声卡的初始化，是在认卡之后吗？

不是。全量表里 Video 在 Driver 前面。`InitializeVideo` 末尾就调 `IgpuMmioInit` 和 HDA。`IgpuMmioInit` 看到还没 Probe 就返回 0。这个函数没有第二个调用点，认卡之后不会再做一次。`InitializeVideo` 固定返回 0，模块表不停。桌面画面仍走 GOP 帧缓冲。

### Q24. 汉字点阵是 16×16 吗？

不是。`cjk32.c` 里是 18×18、4 位深。`Font.h` 仍写「默认 16×16×4bpp」。ASCII 缺字不画框；汉字查找失败才画 18 乘缩放的空心框。

### Q25. 用户程序 `free` 之后，堆会缩回去吗？

不会。`free` 把指针丢掉，不调用 `brk`。`malloc` 只把断点往后移。`toy_brk` 就是 `SYS_BRK`。

### Q26. 删文件和删空目录都会把簇还回去吗？

删空目录会。`FatRmdir` 先 `FatFreeChain`，再把目录项标成 `0xE5`。删文件不会。`FatDeleteFileOnce` 只标 `0xE5`，注释写这是为了避开 QEMU vvfat 在释放簇后的断言。真盘上这些簇不再被分配。

### Q27. EHCI 的 `SchedStart` 失败，会把这只控制器关掉吗？

不会。失败只返回 0，`C->Up` 保持 1，`C->Sched` 保持 0。ASE 握手超时前，Run 位可能已经写上。周期帧表在这一步填好，周期调度使能要等后面的 `SchedEnablePeriodic`。

### Q28. `exec` 会把当前这条 Shell 换成新程序吗？

不会。`exec` 是 `execute` 的别名。成功时另起一个用户任务放进就绪队列，正在跑这条命令的任务还在。失败时返回码被丢掉，错误字在 `ProcessExec` 内部已经打过。

### Q29. GTK 解包失败，会把上一把组密钥清掉吗？

长度会清。`IwlInstallGtk` 在解包前把 GTK 长度置 0。`IwlAesUnwrap` 失败返回 0，不把新明文写进 GTK 缓冲，缓冲里原来的字节还在，但长度已经是 0。

### Q30. EHCI 设了地址之后失败，会把地址号还回去吗？

不会。`gEhciNextAddr` 在 SET_ADDRESS 之前就自增。后面失败不发地址 0。boot 协议和空闲失败仍然算这只设备成功。

### Q31. 把文件写短，尾簇会放掉吗？

不会。`FatWriteExist` 缩短时不调用 `FatFreeChain`。删文件同样不放簇。删空目录才会放。

### Q32. 调度锁会罩住等盘吗？

不会。队列锁和 `gSchedulerLock` 都不跨磁盘或 USB 等待。关窗和拆地址空间在松锁之后。睡眠不拿这两把锁。

### Q33. 桌面双击图标，槽满了会怎么样？

画面不动。桌面只把动作交出去。开窗失败返回 -1，这个返回值被丢掉，不画错误，也不改已有窗口。

### Q34. 教学 `tcp listen` 和 lwIP 会抢同一个端口吗？

不会互相拒绝。Shell 在 lwIP 起来之后不再调用教学 `TcpListen`。直接调用时，教学栈恒返回 0，只改自己的状态。lwIP 的 `tcp_bind` 看不见这个端口。

### Q35. xHCI 批量传输出错，端点会复位吗？

不会。失败返回 -1，TRB 留在环上，认领标志不动。控制传输失败才会走 `RecoverEp0`。

### Q36. Arm 和 RiscV 的 virt 桌面会跑 USB 模块吗？

不会。`gModulesVirtDesktop` 里没有 USB。有帧缓冲时走这条表，成功后停在调度器里。CPU 模块里碰到的是 virtio 输入，不是 xHCI。

### Q37. 装 ELF 装到一半失败，已经映上的页会拆掉吗？

不会。`ElfLoadFromMemory` 中途失败留下已映页。`VirtualMemoryMapRange` 同样，失败返回 -1，前面的页留着。一个用户地址空间最多跟踪 128 页。

### Q38. 教学 TCP 收到 RST，会回一个 RST 吗？

不会。已建立时只把状态改成关闭，缓冲和序号留着。`SYN_SENT` 里见到 RST 连状态都不改。主动发出的 RST 只在重传次数到顶时。

### Q39. Arm 和 RiscV 的用户系统调用，号放在哪个寄存器？

Arm64 在 `x8`。RiscV 在 `a7`。两边都交给同一份 `SyscallDispatch`。没人接的缺页是串口打一行后停住，没有共用的停机函数。

### Q40. 拖动窗口时备份失败，窗会停在半路吗？

不会。`GuiDragUpdate` 要帧锁和备份都成功才改坐标。失败则窗停在原处。缩放在松手且尺寸变了之后才写入宽高，过程中只画预览框。

### Q41. 无线帧的 MIC 对不上，明文会留在帧里吗？

不会。CCMP 和 TKIP 解密是就地的。校验失败再跑一遍，把密文还原，然后返回 0。密钥返回前不清。

### Q42. 卸掉一段用户页，中间的页表会拆掉吗？

不会。`HalPageUnmapRange` 只把带用户位的叶子清成 0，总是返回 0。中间表留下。映射失败时目标叶子也不写，这一趟新建的空表同样留下。

### Q43. 不认识的系统调用，用户看到什么？

帧里的返回值是 -38，也就是 `-ENOSYS`。分发函数自己仍返回 0。用户指针不在这一层检查，拷贝时才看当前页表上每一页是不是用户页。

### Q44. 定时器上的待处理信号，写帧失败还会再试吗？

不会。`PendingKill` 一进分支就清成 0。写帧失败后任务接着被普通切片，信号不挂回去。x64 上指令指针和第一个参数可能已经改掉，栈指针还是旧的。

### Q45. lwIP 的 UDP 40000 会挡住教学栈的同号发送吗？

不会。两边各记各的端口。`LwIpUdpSend` 没监听时把发送端绑在 40000，教学栈没绑定时源端口也是 40000。登记不在同一张表上，发送都还能成功。

### Q46. 调度启动成功，还会回到 `KernelMain` 吗？

不会。`SchedulerStart` 停在进入调度的那一跳里。失败才打一行后停机。空闲任务建失败的句子是 `sched: idle create failed`。

### Q47. 商店目录里有一行写坏了，整表会失败吗？

不会。坏行丢掉，继续下一行。`StoreLoadCatalog` 成功返回的是条数，不是 `FAT_OK`。三处都没有可用行才返回 `FAT_ERR_NOENT`。
