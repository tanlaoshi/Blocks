# 01 · 启动链：上电 → 桌面出现（用户尚未操作）

> 读者画像：有 C 基础、没写过操作系统的人。
> 目标：**能照着代码顺序讲出「这一步用户看到什么、为什么非这么做不可」**。
>
> **范围**：固件上电到桌面可交互之前，**含全部模块初始化与全部日志**。
> **不含**：桌面出现之后的 Worker/后台任务；各模块内部算法（只讲到「它让用户看到什么」为止）。

## 1 · 一条时间线，三个界面

启动链有一个容易被忽略的事实：**用户同时在看三样东西**——屏幕、串口、输入设备。设计上是刻意让三者互补：屏幕给用户看进度，串口给开发者看原因，输入设备在最后才接通。

| 阶段 | 屏幕 | 串口 | 代码 |
| --- | --- | --- | --- |
| 1 固件 POST | 固件画面 | 无（或固件自己的日志） | OVMF / U-Boot |
| 2 BootPkg 起来 | 仍是固件画面 | `********************` + `Blocks Boot` | `Serial.c:139` |
| 3 选模设模 | **黑屏**（GOP 全屏填黑） | `Boot: GetVideoInfo Done (Pick …)` / `Boot: GOP Cleared` | `Video/Video.c:335` |
| 4 读盘装内核 | 黑 | `Boot: ReadKernelFile` → `Boot: Kernel Loaded, Entry=0x…` | `LoadKernel/` |
| 5 交接所有权 | 黑 | `Boot: ExitBootServices + Jump 0x…` | `JumpToKernel.c:43` |
| 6 内核入口 | 黑 | （换栈；ARM64 顺便降到 EL1、开早期串口） | `*/KernelEntry.S` |
| 7 交接包 | 黑 | `Boot: FB <宽>x<高>` | `*/KernelHandoff.c` |
| 8 挂串口与帧缓冲 | 黑 | `Boot: KernelMain Live` | `Kernel.c:100` |
| 9 模块表逐条 | **Logo 出现**，逐格下落 | `***** Module <名> *****` | `Modules.c:162` |
| 10 GUI 初始化末 | Logo 到 100%、合成、停约 1 秒 | `Boot: Logo Done` | `WindowManager.c:262` |
| 11 桌面绘制 | **桌面盖住 Logo** | — | `GuiDesktopInitialize` |
| 12 模块表结束 | 桌面 | ready，出现 `Blocks>` | `Kernel.c:104` |
| 13 调度启动 | 桌面（**此时才能操作**） | — | `Start.c: SchedulerStart` |

**第 11 步和第 13 步之间最容易讲错**：桌面在第 11 步就画出来了，但按钮要等到第 13 步 `SchedulerStart` 之后才响应——因为真正的事件循环跑在 `GuiTask` 里，而任务是在 `KernelMainCommon` 里 `Create`、在 `SchedulerStart` 里才被调度。**「看得见」和「点得动」之间隔着一次调度器启动**，这是启动链最实在的一个知识点。

## 2 · 十三个模块，各自让用户感受到什么

模块表的完整形态是 13 项（`Modules.c:64`）。下表按「用户能感受到什么」组织，而不是按代码顺序：

| 模块 | 位置 | 用户能感受到什么 | 硬脊（违反会怎样） |
| --- | --- | --- | --- |
| Serial | `BringUp/Initialize/Serial.c:12` | 串口有字了，后面所有日志都靠它 | — |
| PhysicalMemory | `Core/PhysicalMemory/PhysicalMemory.c:13` | 无感 | **必须紧挨 VMM 前**：VMM 建页表要拿页 |
| VirtualMemory | `Core/VirtualMemory/VirtualMemory.c:289` | 无感；之后一切指针才「正常」 | VMM 之后 Video 才能映射后缓冲 |
| Video | `BringUp/Initialize/Video.c:25` | **Logo 出现**（先铺黑后缓冲，再画格子） | 必须紧跟 VMM |
| Cpu | `BringUp/Initialize/Cpu.c:10` | 无感；决定后面能否处理中断 | 先于 Driver：绑 MMIO 前要有 IDT |
| Driver | `Core/Driver/Driver.c:192` | 无感；决定键鼠能否被找到 | 先于 Smp/USB |
| Smp | `HAL/*/SmpBoot` | 无感；多核后才有多 idle | 拉 AP 前 BSP 必须自检完（FPU 岛） |
| USB | `BringUp/Initialize/Usb.c:43` | **键鼠活过来**（Logo 期间也能动） | **必须在 FileSystem 前**：U 盘要被认领 |
| Scheduler | `Core/Scheduler/Scheduler.c:87` | 无感；登记调度槽 | 先于 Console/Gui：长画要让出 CPU |
| Console | `Services/Shell/Console/Console.c:366` | `Blocks>` 提示符、命令表可用 | 先于 FS/Gui |
| FileSystem | `Services/FileSystem/FileSystem.c:327` | 无感；但壁纸/字体/主题从这里来 | USB 之后 |
| Gui | `Services/Gui/WindowManager/WindowManager.c:238` | **桌面出现**、Logo 收尾 | 在 FS 之后，否则资源读不到 |
| Network | `Services/Net/Network/Network.c:17` | 一般无感（真机可能延后到 Worker） | — |

## 3 · Logo 是启动状态的唯一可视化

在没有串口的真机上，Logo 是用户判断「卡在哪」的唯一依据，所以它是被认真设计过的：

- **出现时机**：`VideoInitialize` 最后一行（`Video.c:46` 的 `DesktopBootLogoShow()`），清屏后停 280 ms（`LOGO_SHOW_DELAY_MS`）再画，避免和 GOP 铺黑撞帧；
- **推进方式**：由**模块名**决定百分比（`Modules.c:135` 的 `ModLogoPct`）：`Cpu`→20、`Driver`→35、`Smp`→50、`USB`→70、`FileSystem`→92；U 盘被认领时还会按口 `HalBootLogoBump` 落在 78..92 之间；
- **不会突跳**：`DesktopBootLogoSet` 把大跳拆成 1% 步进，每帧限速 22 ms（`LOGO_FRAME_MS`），所以即使早期模块瞬时跑完，视觉上也是匀速下落；
- **收尾**：`GuiInitialize` 先把 Logo 推到 95（读字体主题期间仍有进度），最后 100 → `DesktopBootLogoFinish()`，合成九格后再停到至少 1 秒（`LOGO_MIN_MS`）；
- **例外**：开了 `SCREEN_LOG` 时 `DesktopBootLogoFinish` 直接返回——屏幕正在当字符终端用，不能再画 Logo。

讲这块时最能打动人的一点：**进度条不是装饰，它是模块表的可视化投影**。改动模块顺序，Logo 的节奏会跟着变——这正是「表驱动」设计的好处。

## 4 · 四个关键取舍

### 4.1 为什么 Boot 自己写 16550 而不用 `EFI_SERIAL_IO_PROTOCOL`

日志必须跨过 `ExitBootServices` 这条线：协议属于 Boot Services，告别固件后不能再调；端口 I/O 永远合法。而且内核侧用同一地址、同一 115200 8N1，**日志才能从 Boot 一路接到内核不断线**（`Serial.c:1-12` 是全仓库注释的样板）。

### 4.2 为什么必须 `ExitBootServices` 之后再跳内核

固件活着时内存归固件管：一次 `AllocatePool` 就可能把你脚下的页挪走、把中断向量改掉。`ExitBootServices` 是**所有权移交**的那一刻，之后 `GetMemoryMap` 才是可信的。所以内核拿到的第一份数据不是「内存总量」，而是一张内存描述符表。

### 4.3 为什么内核自己写 PMM/VMM，不用 UEFI 的内存服务

UEFI 的内存服务没有分页、没有页表、没有内核/用户态隔离，而教学系统必须讲虚拟内存；况且那套服务在 `ExitBootServices` 之后本来就没了。Boot 只负责「把内核装到它要求的物理地址」，映射由 `VirtualMemoryInitialize` 建立。

### 4.4 为什么用模块表而不是一串固定函数调用

三个理由都能在 `Modules.c` 里验证：**三张表对应三种运行形态**（串口-only / virt 桌面 / 真机）；**顺序约束集中一处**，改顺序只改表；**失败即停并打印模块名**，真机无 COM1 时也能从屏上看出卡在哪个模块。表里一行就是一个可替换点，这是「学生能替换一个模块」的接口雏形。

## 7 · 01.1 BootPkg 五步：选模、装 ELF、告别固件

`Boot/BootPkg` 是 X64 专用的 UEFI 应用（`Boot/BootPkg/Boot.dsc:7` 写死 `SUPPORTED_ARCHITECTURES = X64`），入口 `UefiMain`（`Boot.c:14`）。它不长期驻留：把内核搬到内存、把该交代的地址填进交接包，然后交权。五步的调用顺序就在 `Boot.c:32-56`，任一步失败直接 `return`，不会带病往下走。

### 7.1 串口先活（`Serial.c:98-116`）

`BootSerialInitialize` 先探 0x3F8（`Serial.c:91-95` 用 scratch 寄存器做回读），再按 16550 的 DLAB 顺序设 115200 8N1、开 FIFO、拉 DTR/RTS（`Serial.c:103-115`）。探测失败就整段静默——后面 `BootSerialPrintf` 也写不出去。

紧接着 `BootSerialBanner` 打横幅（`Serial.c:130-141`）。为什么不用 `EFI_SERIAL_IO_PROTOCOL`、为什么同一地址能接到内核，见 §4.1；这里只强调结果：**从 Boot 到内核，串口日志可以不断线**。

### 7.2 可选交接：RSDP / XHCI / 启动盘 GUID（`Boot.c:36-38`）

三项都只读固件表或 PCI，不依赖 GOP，也不依赖 `Kernel.elf`；找不到就填 0 继续（`FillRsdp.c:24-28`、`FillXhci.c:125-133`、`Volume.c:100-155`）。其中 `BootDiskGuid` 是「加载本 EFI 的那块盘」的 GPT GUID，内核挂载时用它认系统卷；`OsIdSeen` 已废弃，保持 0（`UefiBootConfig.h:65-71`）。

### 7.3 选模与设模（`Video.c:17` / `Video.c:241`）

`GetVideoInfo` 只**选**不设：

- 有 `BLOCKS.DB` 的 `mode=` 就按它算分；没有就保留固件当前模式（`Video.c:86-104`），避免为「原生分辨率」多切一次 4K；
- 真机可读 EDID；虚拟机走 QEMU 友好的分值表（`Video.c:76-84`）；
- 所有可用模式去重后写进交接包，供设置页列表（`Video.c:126-140`、`182-192`）。

`SetVideoMode` 只在「当前不是目标分辨率」时切；虚拟机里即使目标不同也**故意不切**，因为 QEMU+GTK 改分辨率常触发整机复位，形成重启环（`Video.c:257-288`）。切完（或跳过）把 `FrameBufferBase/Size/Resolution/PixelsPerScanLine` 写进 `VideoConfig`（`Video.c:290-294`），最后 GOP 全屏填黑（`Video.c:334-346`）——内核的 Logo 是在后缓冲里画的，Boot 只负责给一块确定的黑底。

### 7.4 读盘、校验、按段装入（`Read.c:135-139`、`Elf.c:48-159` / `203-277`）

X64 的盘不是真盘：`Runtime/run.sh:6-7` 写明 disk0=`Esp/X64`（`BOOTX64.EFI`）、disk1=`RootFs/X64`（`BLOCKS.ID` / `Kernel.elf` / `Assets`），`run.sh:148-154` 用两块 AHCI + OVMF pflash 起 QEMU；Boot 的认卷顺序就在这两块盘上生效。Pi/Duo 的镜像摆放见 §8.2 / §8.3 的 `boot.cmd` 与 `boot.sd`。

读盘走 `BootSelectOsVolume` 的四档顺序：`ROOT.CFG` 指认的盘 → 同盘 `BLOCKS.ID` → 它盘 `BLOCKS.ID` → 启动卷兜底（`Volume.c:493-497`）。每块候选卷先过谓词：真的能读出 `Kernel.elf` 才算数；文件名依次试 `\Kernel.elf`、`\KERNEL.ELF`、`\EFI\Blocks\Kernel.elf`（`Read.c:135-139`）。

`CheckKernelFile` 只校验不分配：ELF64、`EM_X86_64`（`Elf.c:50-86`）、每个 `PT_LOAD` 的文件范围、地址回绕、**段与段不重叠**；任何一条不满足都点名段号与地址（`Elf.c:92-145`）。`LoadKernelFile` 再逐段 `AllocateAddress` 到它自己的 `PAddress`、`SetMem` 清零、`CopyMem` 拷文件内容（`Elf.c:246-272`），入口直接取 ELF header 的 `Entry`（`Elf.c:275`）。

**这里有个容易讲错的点**：它申请的是「每个 PT_LOAD 的页区间」，不是 `Low..High` 整跨度。X64 内核的 `.text/.data` 在 1MiB、`.bss` 在 32MiB（`Kernel/HAL/X64/link.ld:54-62`），中间是故意留的洞；整跨度申请会连洞一起要，必然失败。`Elf.c:1-6` 的注释就是这条教训。

### 7.5 ExitBootServices，然后跳（`JumpToKernel.c:40-86`）

先 `GetMemoryMap` 拿大小，再循环最多 8 次：每次重新取图（`MapKey` 随之更新），再调 `ExitBootServices`；`MapSize` 变化就重分配缓冲（`JumpToKernel.c:40-70`）。成功那一瞬间把 `MemoryMap` 写进交接包（`JumpToKernel.c:76`），按 MS ABI 把包指针放 RCX 调入口（`JumpToKernel.c:77-85`）；内核入口同时读 RCX 和 RDI，所以 SysV 侧也不会断（`KernelEntry.S:12-16`）。

如果入口返回，说明内核启动路径提前退出了：打一行 `Boot: Kernel Returned`，关中断，原地停（`JumpToKernel.c:23-31`、`85-86`）。**Boot 的交付物不是「一个 ELF 文件」，而是三样：按物理地址装好的段、一张 ExitBootServices 之后才可信的内存图、一个 656 字节的配置包。**

## 8 · 01.2 交接包：656 字节（X64）与 DTB（ARM64 / RISC-V）

X64 与 ARM64/RISC-V 的「交接」不是同一个东西，这点最容易讲混：X64 是 Boot 写一个固定布局的结构体；ARM64/RISC-V 默认是 U-Boot 把 DTB 指给内核，内核自己建交接块（Duo 的 `boot.scr` 是例外，见 §8.3）。

### 8.1 X64：`UEFI_BOOT_CONFIG` 656 字节

`UefiBootConfig.h:81-91` 用 `_Static_assert` 把大小和偏移全部钉死（656 字节，`VideoConfig` 在 0、`EntryAddress` 在 72、`GopProtocol` 在 624）。Boot/BootPkg 与 Kernel/BringUp/X64 各有一份内容相同的副本，`Boot/build.sh` 会先做一致性检查；内核侧对应断言在 `Kernel/BringUp/X64/UefiBootConfig.h:80-93`。

| 偏移 | 字段 | Boot 谁填 | 内核谁读 |
| --- | --- | --- | --- |
| 0 | `VideoConfig`（32 字节） | `SetVideoMode`（`Video.c:290-294`） | `FillHandoff`（`KernelHandoff.c:47-51`） |
| 32 | `MemoryMap`（40 字节） | `JumpToKernel`（`JumpToKernel.c:76`） | `FillHandoffRegions`（`KernelHandoff.c:104-130`） |
| 72 | `EntryAddress` | `LoadKernelFile` 取 ELF entry（`Elf.c:275`） | Boot 的 `JumpToKernel` 读；内核不读 |
| 80/88/96 | `RsdpAddress` / `SystemTable` / `XhciBaseAddress` | `Boot.c:30,36-38` | `FillHalPlatform`（`KernelHandoff.c:181`） |
| 104/112/624 | `VideoModeCount` / `VideoModes[32]` / `GopProtocol` | `GetVideoInfo` / `SetVideoMode`（`Video.c:126-140`、`328-331`） | `FillHandoff`（`KernelHandoff.c:59-71`） |
| 632/636/640 | `OsIdSeen` / `OsIdPad` / `BootDiskGuid[16]` | `BootFillDiskGuid`（`Volume.c:111`、`154-155`） | 挂载认盘（`MountOs.c:65-68`） |

生命周期比字段更要紧。这个结构体在 **`UefiMain` 的栈上**（`Boot.c:26`），不是全局：`ExitBootServices` 之后 Boot 的 BSS 不可信，栈仍有效；但内核一换栈或回收未登记页，这块栈随时可能被复用。所以 `KernelHandoff` 的第一件事是整包复制到 static 存储（`KernelHandoff.c:179`）；复制前只做不会破坏该栈的串口初始化，之后只准用副本（`KernelHandoff.c:167-182` 的长注释就是 PR-15 契约）。

复制完再翻译成 `BOOT_HANDOFF`：

- `FillHandoff` 只搬视频、模式表、`__kernel_start/__kernel_end`（`KernelHandoff.c:43-55`）；
- `FillHandoffRegions` 扫 UEFI 内存图，只把 `EFI_MEMORY_CONVENTIONAL` 记成可分配（`KernelHandoff.c:109-130`），再额外保留 0..4KiB、0x7000..0x9000、内核低端 `[start, data_end)`、高端 `[bss_start, end)`、配置包本身、内存图缓冲、帧缓冲（`KernelHandoff.c:133-158`）；
- **内核两段之间的洞不保留**：`[data_end, bss_start)` 留给 PMM 用（`KernelHandoff.c:135-149`）；
- 最后 `EnableEarlyIdentityMap()` 建早期恒等映射，`BootHandoffSet()` 交给后面（`KernelHandoff.c:184-185`）。

### 8.2 ARM64：没有 656 字节，只有 DTB

Pi 上标准引导器是 U-Boot，不是 UEFI 应用。`boot.cmd` 把 `Kernel.elf` 装到 0x20000000，把 FDT 搬到 0x02400000，再 `bootelf -p`（`Kernel/HAL/Arm64/Board/rpi-3b/scripts/boot.cmd:9-20`）。脚本头注释明说 `bootelf` 的 x0 不是 DTB（`boot.cmd:3`）——U-Boot 传的是 `argc`（`cmd/elf.c:24-34`）。内核入口仍把 x0 存进 x19（`KernelEntry.S:15`）、传给 `KernelHandoff`（`KernelEntry.S:122-123`）；无参数时 argc=0，`TryDtb(0, ...)` 直接失败，固定址 0x02400000 才是 Pi 的常路。

`KernelHandoff` 按顺序找内存信息：x0 指向的 DTB → 固定址 `BOARD_DTB_LOAD`=0x02400000 → QEMU virt 的 0x4a000000 → 树莓派 mailbox（`KernelHandoff.c:126-143`）。找到 DTB 就解析 `/memory`，找不到就回退 `BOARD_RAM_*`（`KernelHandoff.c:126-143`、`Kernel/HAL/Arm64/Board/rpi-3b/BoardConfig.h:28-33`）。然后只建**两段**：`[RamBase, FreeStart)` 保留、`[FreeStart, RamBase+RamSize)` 可分配（`KernelHandoff.c:206-221`）。

### 8.3 RISC-V / Duo：同一套 DTB 思路，多一个 `boot.sd`

RISC-V 入口注释按 `a0=hartid, a1=DTB` 取参（`Kernel/BringUp/RiscV/KernelEntry.S:20-22`）。这对 OpenSBI/`-kernel` 和 FIT `bootm` 成立：SDK U-Boot 的 `boot_jump_linux` 调 `kernel(gd->arch.boot_hart, images->ft_addr)`（`Source/DUO/sdk/duo-buildroot-sdk-v2-2.0.1/u-boot-2021.10/arch/riscv/lib/bootm.c:109`）。`bootelf` 则不是：它按 `entry(argc, argv)` 调（同树 `cmd/elf.c:24-34`）。`KernelHandoff` 用 `DtbMemoryRegion(DtbPhys, ...)` 解析内存；失败则回退 `BOARD_RAM_BASE/SIZE`（`Kernel/BringUp/RiscV/KernelHandoff.c:72-83`）。`FreeStart` 取 `__kernel_end` 页对齐，之后整段可分配（`KernelHandoff.c:91-94`、`108-116`）。

Duo 有两条上电路径，别讲成一条：

- **默认上电**：厂商 `bootcmd=run sdboot` → `bootm boot.sd#config-*`，`boot.sd` 是 FIT，默认把内核**内嵌**在其中（`scripts/README.md:12-18`；`mk-boot-sd.py:197-225`，`load/entry` 都是 0x80200000，见 `mk-boot-sd.py:213-214`）；
- **`boot.scr`**：抢在 autoboot 前 `source` 才跑；它 `fatload mmc 0:4` 把 `Kernel.elf` 读到 0x81800000、DTB 读到 0x81200000，再 `bootelf -p`（`scripts/boot.cmd:5-10`）。`scripts/README.md:18-20` 明确记了：改 `Kernel.elf` 不重打 FIT，上电仍跑旧的内嵌核。

这里有个容易照着注释讲错的地方：`boot.cmd:4` 写「a0=hartid a1=DTB via bootelf -p」，但 SDK 树里的 U-Boot 2021.10 源码显示 `bootelf` 传的是 `(argc, argv)`（`cmd/elf.c:24-34`），不是 hartid/DTB。所以 **`boot.scr` 路径下 a1 不是 DTB**；它能工作是因为 `boot.cmd` 先把 DTB 放到 0x81200000，内核再靠 `BOARD_DTB_LOAD` 固定址兜底（`BoardConfig.h:20`，`KernelHandoff.c:72`）。真正传 hartid/DTB 的是 FIT `bootm`（`arch/riscv/lib/bootm.c:109`）；这与 Pi 上 `bootelf` 的 x0≠DTB（`rpi-3b/scripts/boot.cmd:3`）是同一个原因。厂商 fip 是否逐字节同源于这棵树**未核对**，但两条路径的兜底都在。

两者最后都落到同一件事：`BOOT_HANDOFF.KernelEnd` 决定 PMM 的启动分配起点（`Seg.c:235`），`Regions[]` 决定哪些页可分配。X64 的 `KernelEnd` 在 32MiB BSS 之后；RISC-V/Pi 的 `KernelEnd` 是连续镜像末尾——**同一套 PMM 代码，吃的是两种形状的地址图**。

## 9 · 模块表 13 项逐条讲

每一项都按「干什么 / 用户看到什么 / 失败会怎样 / 为什么在这个位置」四段写。括号里是入口文件与行号。

### 9.1 Serial —— 让日志活下来（`BringUp/Initialize/Serial.c:12`）

干三件事：再调一次 `HalSerialInitialize()`（幂等，交接时已调过）、`HalSerialEnableRxIrq()` 开接收中断（后面串口输入要靠它）、`LibWriteRegister(HalSerialWrite)` 把「内核打印」接到串口。
**用户看到**：屏上无变化；从这一行起，后面所有日志才有出处。
**失败**：不会失败（恒返回 0）。串口不存在时日志静默丢失，启动继续——这是刻意的，见 `Serial.c:4` 的注释。
**位置**：必须第一个，因为后面每个模块的日志都依赖它。

### 9.2 PhysicalMemory —— 先把内存划成段（`Core/PhysicalMemory/PhysicalMemory.c:13`）

从交接包的 `RegionCount` 划段（`PmmSegmentInit`），登记分配器（编译期在 bitmap / bestfit 之间选），最后打印空闲与总量。
**日志**：`PMM: free=… / tracked=…`
**失败**：`RegionCount == 0` 直接返回 -1 → 模块表打印 `***** Module PhysicalMemory Failed *****` 并停机。
**位置**：**必须紧挨 VMM 之前**——VMM 建页表时就要拿物理页。

### 9.3 VirtualMemory —— 开分页，并把屏幕映射进来（`Core/VirtualMemory/VirtualMemory.c:289`）

`HalPageKernelSetup(IDENTITY_MB)` 建恒等映射 → 若交接包里有帧缓冲，按 `HalVideoFbMapFlags()` 把它映射进去（Pi 上是 Device 属性，注释说明**必须在开 MMU 前写 PTE**，否则先 Normal WB 再改 WC 会整屏闪）→ `HalPlatformMapMmio()` 映射板级 MMIO → `VirtualMemoryEnable()` 开分页。
**日志**：`vmm: setup` / `VMM: identity map 0-…MB (2M pages), PML4=…` / `vmm: mapfb` / `vmm: enable`
**失败**：任一步返回非 0 → 停机。**这是全链第一个会因为板级差异挂掉的地方**。
**位置**：Video 之前——后缓冲要先能映射。

### 9.4 Video —— Logo 出现（`BringUp/Initialize/Video.c:25`）

字体、主题、`HalVideoSet` 接住 Boot 传下来的 GOP 信息、开 WC、建后缓冲、注册绘制函数、`HalSerialGopEnable()` 把串口日志镜像到屏；然后**后缓冲铺黑 + `DiscardDirty`**（PMM 给的页是脏的，不铺黑会在第一次翻页时把垃圾像素拷上屏），最后 `DesktopBootLogoShow()`。
**用户看到**：**Logo 出现**，清屏后 280 ms 才开始画。
**失败**：几乎不会——`DisplayHardwareInitialize()` 的返回值被显式忽略（核显探不到也照样用 GOP 的帧缓冲）。
**位置**：紧跟 VMM。

### 9.5 Cpu —— 中断、定时器、系统调用（`BringUp/Initialize/Cpu.c:10`）

`HalInitialize()`（IDT/GDT/LAPIC）→ `HalTimerInitialize()` → `HalSyscallInitialize()`；virt 下顺带挂 virtio-input；然后**再探一次 COM1**（`HalSerialRetryIfMissing`）并开 RX 中断；最后做 FPU 岛自检。
**日志**：`Boot: COM1 after Cpu` / `Boot: COM1 Ready|Miss` / `Boot: fpu island ok|skip`
**失败**：`HalInitialize()` 非 0 → 停机；其余（COM1、FPU）只告警不拦。
**位置**：**必须早于 Driver**——绑 MMIO 前要有 IDT 和定时器；也要早于 Smp，因为拉 AP 前 BSP 必须自检完。

### 9.6 Driver —— 枚举设备，只探块设备（`Core/Driver/Driver.c:192`）

`DeviceInitialize` + `DeviceEnumerateAll` 枚举平台/PCI 设备 → `HalDriverRegister` 注册驱动表 → 核显探针 → **只 `Probe(DRIVER_CLASS_BLOCK)`**。
**为什么只探块设备**：注释写得很直白——「勿 ProbeAll：ps2-kbd 会跑 Ps2InitHw；真机无 8042 时 STATUS 浮空 → 死循环」。最值钱的一条注释。
**日志**：`Boot: Device Enumerate Done` / `Boot: Driver Register OK` / `Boot: Driver Block Probe Done`
**位置**：VMM 之后（要绑 MMIO）、USB 之前。

### 9.7 Smp —— 拉起其它核（`HAL/*/SmpBoot`，X64 见 `SmpBoot.c:131`）

解析 MADT 拿到 APIC ID 表，初始化 ACPI 电源（关机要用），把 BSP 排到第一位，逐个 `CPU_ON`，统计 AP 的 hello 数。
**日志**：`Smp: No RSDP (Single CPU)` / `Smp: MADT CPUs=… bsp_apic=…` / `Smp: APs Started=… hellos=…` / `Smp: Continue Single-CPU (AP Failed)`
**失败**：**不致命**——拉不起来就单核继续，这是刻意的（那种机器上多核本来就不可靠）。
**位置**：Cpu 之后（中断已就位）、USB 之前。

### 9.8 USB —— 键鼠活过来（`BringUp/Initialize/Usb.c:43`）

`HalUsbInitialize()` 探 USB/PS2，`DriverInputReady()` 判断有没有输入后端；真机上再 `HalInputArmIrq()`、把鼠标摆到屏幕中心（`HandoffMouse`）、`DrainHid()` 清空事件队列。
**日志**：`Boot: Input Probe (USB Then PS/2)` / `Boot: Input Backend Ready` / `Boot: Input NONE (Continue)`
**失败**：没有键盘也继续——`Input NONE (Continue)` 是明确的策略，不是遗漏。
**位置**：**必须在 FileSystem 前**（U 盘要被 MSC claim）；`DrainHid` 是为了防「事件环塞满 → 桌面后键鼠假死」（`Modules.c:174-180` 有注释）。

### 9.9 Scheduler —— 登记调度，但先不跑（`Core/Scheduler/Scheduler.c:87`）

注册调度策略（编译期在轮转/优先级之间选）、初始化运行队列、把任务表所有 slot 置为 `TASK_UNUSED`。
**日志**：无。
**失败**：不会失败。
**位置**：Console / Gui 之前——「会话」要在 FS/Gui/Net 前登记，长画时才能让出 CPU（`IoBreath`）。

### 9.10 Console —— 命令表就位（`Services/Shell/Console/Console.c:366`）

`ConsolePublishAll()` 发布命令与日志槽（Gui 早于 Console 就要用，所以 `ModulesRun` 一开始也调了一次）、`LocaleInitialize()`、注册内建命令与 shell 命令表（串口-only 走精简版 `ShellCommandsRegisterVirtMin`）、加载别名、`gConsole.Initialize()`。
**用户看到**：这一项**不画东西**；它的效果要到后面 `Blocks>` 提示符出现才被感知。
**位置**：Gui 之前、FS 之前。

### 9.11 FileSystem —— 挂盘，必要时认领 U 盘（`Services/FileSystem/FileSystem.c:327`）

注册 FAT 与资源文件系统，把「读文件」能力交给驱动层；`HalBlockInitialize()` + `MountAllVolumes()` 挂内置盘；根据有没有 `BLOCKS.ID` 决定要不要 claim U 盘；claim 时 **Logo 落到 79**，逐口扫描再 bump 到 91。
**日志**：`FS: No Primary Volumes Yet (Live USB Path Ok)` / `FS: msc/2 boot-claim begin|ok|empty|abort`
**位置**：USB 之后（MSC 要能用）、Gui 之前（壁纸/字体/主题从这里读）。

### 9.12 Gui —— 桌面出现（`Services/Gui/WindowManager/WindowManager.c:238`）

Logo 推到 95 → 读数据库、加载字体与主题、初始化语言 → 100 → `DesktopBootLogoFinish()`（合成九格、停至少 1 秒）→ `GuiDesktopInitialize()` 把桌面盖上去。
**日志**：`Boot: Logo Done`
**顺序有个坑**：`FontFtInit` 必须在 `LocaleInitialize` 之前，否则开机时 stb 缓存占槽，Worker 再初始化会触发 DropCjkHits 风暴 → 鼠标死。这条原因写在代码注释里。
**位置**：FS 之后。

### 9.13 Network —— 可以最后（`Services/Net/Network/Network.c:17`）

初始化教学用的 UDP/TCP 栈；只有串口-only（Duo）或板载网口（`HalNetProbeAtModuleInit()`）才在这里真探网卡并 `HalWifiClaim()`；桌面 virt/X64 的网卡探测推迟到 Worker（`boot-net-defer`）。
**位置**：最后——它**不在硬脊上**，这一条本身就说明了「哪些能延后」。

**读完这一节应该能回答三个问题**：
1. 为什么 PMM、VMM、Video、USB、FS、Gui 六个有固定位置，其余可以调？（前者是后者的前提，后者只是通知）
2. 如果启动卡在 Logo 的 35%，应该是哪个模块？（`Driver`，因为 35 是它跑完时的百分比）
3. 为什么没有任何一步会因为「没有键盘 / 没有网 / 没有核显」而停机？（凡是可选的都只告警：`Input NONE (Continue)`、`Continue Single-CPU`、`DisplayHardwareInitialize` 返回值被忽略）

## 10 · 01.4 Logo 与日志：两条通道，一个屏幕

§3 讲 Logo 的节奏与百分比；本节讲它和日志为什么能同时看见、什么时候互斥。

### 10.1 一条日志，三个落点

`SerialLog.h:4-8` 把契约写死：`Log*` 始终进 ring；UART 看 `SERIAL_*`；屏看 `SCREEN_LOG_*` + Mirror/Mute。具体分派在 `HalSerialWriteChannel`：先 `RingAppend`（`HalSerialWrite.c:163-165`），再按 `ChannelUartOn` 走 `SerialWrite`（`166-168`），最后按 `ChannelGopOn` 走 `GopMirrorLine`（`169-175`）。默认 `SCREEN_LOG=0`（`SerialConfig.h:8-10`），课堂可用开关见 `SerialConfig.h:19-25`。

这解释了一个常见现象：没有 COM1 时，日志不是消失，而是只剩 ring（以及稍后的 `BOOT.LOG`）；开了 `SCREEN_LOG=1` 才上屏。

### 10.2 Boot 与内核的接缝

Boot 的前半段只有串口横幅（`Serial.c:130-141`）；GOP 还没设，屏上是固件画面。`SetVideoMode` 之后屏幕被铺成纯黑，但仍没有字。内核 `KernelAttachEarlyVideo` 调 `HalSerialGopEnable()` 把日志镜像接到帧缓冲，紧接着才打 `Boot: KernelMain Live`（`Kernel.c:102-116`）——顺序反了就会丢第一行。

之后模块表每条先打 `***** Module <名> *****` 再调 `Init`，失败补 `Failed`（`Modules.c:121-128`、`162-183`）。真机没串口时，**屏上最后一条横幅就是当前卡住的模块**；这也是模块名必须短、日志必须同步的原因。

### 10.3 Logo 与屏上日志是互斥的

两者都往同一块 boot GOP 帧缓冲写：日志要滚动，Logo 要原地画九格。代码的选择很直接——`SCREEN_LOG=1` 时 `DesktopBootLogoShow` 直接返回（`BootLogo.c:266-269`），`DesktopBootLogoFinish` 也返回（`BootLogo.c:315-318`），宁可没有 Logo，也不让两套绘制互相盖。

所以课堂默认 `SCREEN_LOG=0`、看 Logo；要排障才开屏上日志。二者不可兼得，不是 bug。

### 10.4 Logo 的状态机（只补 §3 没讲的点）

`VideoInitialize` 最后一行调 `DesktopBootLogoShow`（`Video.c:46`）；Show 先等 280ms（`LOGO_SHOW_DELAY_MS`，`BootLogo.c:23`）再画 0%，避免和 Boot 的 GOP 铺黑撞帧；`DesktopBootLogoSet` 把大跳拆成 1% 步进、每步至少 22ms（`LOGO_FRAME_MS`，`BootLogo.c:25`、`295-313`）；`DesktopBootLogoFinish` 推到 100、再停至少 1 秒（`LOGO_MIN_MS`，`BootLogo.c:27`、`315-335`），然后才 `GuiDesktopInitialize()` 把桌面盖上去（`WindowManager.c:261-263`）。

屏上两个可搜索的锚点：`Boot: Logo`（`BootLogo.c:289`）和 `Boot: Logo Done`（`BootLogo.c:326`）。前者出现说明后缓冲与呈现链已通，后者出现说明桌面即将接上。

## 11 · 01.5 从 `SchedulerStart` 到「点得动」

### 11.1 Start 之前：桌面已经画好，但没人跑事件循环

模块表走到 Gui 这一项时，桌面已经由 `GuiInitialize` 画出来了（`WindowManager.c:261-263`）；等整张表跑完，Shell/Gui/Worker **仍没创建**。`Modules.c:9` 的注释说得很清楚：`Create` 在 `ModulesRun` 返回之后，模块表只管 `Init`。

`KernelMainCommon` 这才按顺序 Create：Shell、Gui、Worker（`Kernel.c:150-152`），可选 Input（`Kernel.c:49-51`、`154`），最后 `SchedulerStart()`（`Kernel.c:155`）。`SchedulerCreate` 做的是：找空槽、把首入帧放在 32KiB 栈顶（`Scheduler.h:54-60`）、状态置 READY、挂进运行队列（`Create.c:38-96`）。任务此时只是「可运行」，没有核在跑它。

### 11.2 Start 做的四件事

`SchedulerStart`（`Start.c:133`）按顺序：

1. **每核一个 idle**：`CreateIdleForCpu`（`Start.c:57-77`、`145-153`）；
2. **钉核**：Input 名字以 `in` 开头 → `InputCpu`；Shell/Gui → `InteractiveCpu`；Worker → CPU0（`Start.c:157-195`）。策略值：≥`HAL_INPUT_CPU_MIN`（=4，`Hal.h:155`）时 Input@2、Shell/Gui@1；2–3 核时 Input 跟 Shell/Gui 同核；`ConsoleOnly` 或 `HalPinInteractiveToBootstrap` 时全部回 0（`Start.c:160-163`）；
3. **挑第一个任务**：按槽位顺序找 READY、且没有钉在 AP 上（`Affinity` 为 0 或 -1）的；找不到就用 CPU0 的 idle（`Start.c:198-225`）。≥2 核的桌面形态下 Shell/Gui 被钉到 CPU1，BSP 按槽位找到的第一个是 Worker；单核时 Create 顺序让 Shell 成为第一个；
4. **上线并进入**：`HalIrqDisable` → `ActivateTask(First)` → `gSchedulerOnline=1` → `HalTimerStart()` → `HalSchedulerEnter(Frame)`（`Start.c:227-244`）。**它不返回**；`Start.c:238-244` 的注释说明为什么保持 cli 直到 `iret`：过早开中断会让定时器在 `gEarlyStack` 上入 Shell，触发 `sched: corrupt resume`。

### 11.3 「点得动」到底接在哪

鼠标事件由 `GuiTask` 唯一泵：`GuiPollMouse()` → `YieldForPollInput()`（`Tasks.c:94-116`）；键盘由 `ShellTask` 每圈 dequeue（`Shell.c:45-67`）。这两个循环都要等 `SchedulerStart` 之后才第一次拿到 CPU。

所以「桌面已经出现」和「按钮能点」之间隔着：**GuiTask/ShellTask 被创建 → 被钉核 → SchedulerStart 选中 → iret 进入 → 定时器开始抢占**。在这之前，桌面只是后缓冲里的一张图；输入事件即使已经进了硬件队列，也没有人把它变成窗口动作。§1 第 11–13 步的「看得见 ≠ 点得动」，机制就落在这四步里。

一个可验证的推论：把 Shell/Gui 的钉核改到别的核，BSP 首入的任务会变，但「桌面先画、事件循环后跑」的顺序不变——因为绘制在模块表内，Create 在模块表之后，这是 `Kernel.c:14` 与 `Modules.c:9` 两处注释共同钉死的。

## 12 · QA

**Q1：为什么 Boot 只有 X64，ARM64 要另写入口？**
A：`Boot/BootPkg/Boot.dsc:7` 写死 `SUPPORTED_ARCHITECTURES = X64`；Pi 上事实标准的引导器是 U-Boot，直接装内核 ELF 并交 DTB。再写一个 ARM64 的 UEFI 应用只为对称，收益为零、维护成本翻倍。

**Q2：`KernelEntry.S` 为什么同时读 RCX 和 RDI？**
A：UEFI/Windows 约定第一个参数在 RCX，SysV 在 RDI。`JumpToKernel` 按 EDK2 的 MS ABI 编译（参数落 RCX），内核 C 代码按 SysV 编译（读 RDI）。入口两者都设，改任一侧都不易断。

**Q3：桌面已经画出来了，为什么还要等 `SchedulerStart` 才能点？**
A：绘制发生在 `GuiInitialize`（模块表内），而事件循环跑在 `GuiTask` 里；任务在 `KernelMainCommon` 里 `Create`，直到 `SchedulerStart` 才被调度。**看得见 ≠ 点得动**，中间隔着调度器启动。

**Q5：ROOT.CFG 为什么要先 `GetInfo` 再读，而不是把缓冲区加大？**
A：`EFI_FILE_PROTOCOL.Read` 在缓冲不足时**不报错**，而是把 `BufferSize` 夹到剩余长度并返回成功。所以「加大缓冲」只是把阈值往后挪，且要猜一个够大的数；先问大小才能做到「要么读全，要么明确拒绝」。上限 4096 只用来挡异常文件，不是容量设计。

**Q4：为什么 Boot 阶段屏幕是纯黑，而不保留固件 LOGO？**
A：`SetVideoMode` 末尾用 GOP 全屏填黑（`Video.c:335-347`），给内核一个确定的底色；内核的 Logo 是在**后缓冲**里画的，两者不能同时往 LFB 写，否则会撕屏。这也是 `VideoInitialize` 里「铺黑后缓冲 + DiscardDirty」那两句注释的由来。
