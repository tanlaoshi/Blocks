## 2 · 第一天：止血（4 个「日志正常、结果错」）

这四条的共同特征：**不报错、日志看着正常，但做错了事**。它们不改变任何设计，只让错误变成可见的错误。

### PR-01 · `mode=auto` 终止扫描

- 位置：`Video/Theme.c:75-77`
- 现状：`ParseAsciiModeLine` 对 `mode=auto` 返回 TRUE 且 `W=H=0`，调用处 `return (W>=640 && H>=480)` 于是**整个 `ParseModeFromDb` 立刻返回 FALSE**。`mode=auto` 写在文件靠前时，后面的 `mode=1920x1080` 永远读不到。
- 改法：把「解析成功但为 auto」与「解析失败」分开；auto 表示「无显式偏好」，应 `continue` 继续扫后面的行，全部扫完仍无显式值才返回 FALSE。
- 验收：`BLOCKS.DB` 写成 `mode=auto` 后再加一行 `mode=1280x720`，串口日志出现 `Boot: BLOCKS.DB Mode 1280x720`。
- 收益：`mode=auto` 的语义从「破坏整份配置」变成「只影响这一行」，用户改配置不会踩到隐性顺序依赖。

### PR-02 · ROOT.CFG 静默截断

- 位置：`Volume.c:356-363`
- 现状：`CHAR8 Buf[256]`，`Size = sizeof(Buf) - 1`，`File->Read` 在文件更大时**按 EDK2 语义夹到 255 字节并返回成功**。`disk=`/`part=` 若在 255 字节之后，认盘静默失效，日志只显示走了兜底路径。
- 改法：先 `GetInfo` 取 `FileSize`，按实际大小分配；或循环读到 EOF 并设上限（例如 4 KiB）后**明确报错**。
- 验收：ROOT.CFG 前置 10 行注释使 `disk=` 落在 300 字节处，仍能命中 `Boot: OS Vol Via ROOT.CFG`。
- 收益：配置文件的排版（加注释、调顺序）不再影响功能；「认盘失败」与「配置没读到」在日志上可区分。

### PR-03 · `FileInfo` 缓冲不足即硬失败

- 位置：`LoadKernel/Read.c:47-61`（`Theme.c:123-137` 是同一模式的第二份，**本 PR 不动**，见 1.3）
- 现状：`InfoSize = sizeof(EFI_FILE_INFO) + 128` 写死；`GetInfo` 返回 `EFI_BUFFER_TOO_SMALL` 时直接 `return Status`，调用方只看到笼统失败。
- 改法：收到 `EFI_BUFFER_TOO_SMALL` 后按回填的 `InfoSize` 重新分配并重试一次；仍失败则带 `InfoSize` 打印。
- 验收：把 `Kernel.elf` 改名成 100 字符长文件名，仍能正常加载。
- 收益：文件名长度不再是一个隐性上限；失败信息指向真实原因。

### PR-04 · xHCI 探测用未初始化值

- 位置：`FillXhci.c:32-49`
- 现状：`VendorID/DeviceID/ClassCode` 未初始化，三个 `Pci.Read` 的返回值全部丢弃；读失败时栈上垃圾参与 `Class==0x0C && Sub==0x03 && ProgIF==0x30` 判断，可能认出不存在的控制器并把垃圾当 BAR 交给内核。另外 `Uint32 @0x02` 读 `DeviceID` 依赖根桥把地址 bit1:0 清零，随后用 `>>16` 取 DID，能跑但属于「靠实现细节成立」。
- 改法：三个变量初始化；每次 `Pci.Read` 判返回值，失败 `continue`；VID/DID 改为 `Uint32 @0x00` 一次读再拆分（或 `Uint16 @0x00` + `Uint16 @0x02`），消除依赖。
- 验收：QEMU 下 `Boot: XHCI Found VID=0x1b36 DID=0x000d` 不变；人为让某个 handle 的 `PciIo` 读取失败时，不得再出现 BAR。
- 收益：把「碰巧对」变成「显然对」，同时排除了一类随机把错误 BAR 交给内核的可能。

### PR-17 · `build.sh DEBUG=1` 完全不可用（验证 PR-02 时发现）

- 位置：`Boot/build.sh:71`
- 现状：脚本先解析 `DEBUG=1`，随后 `source "$EDK2_ROOT/edksetup.sh"`；被 source 的脚本会读到**调用者的位置参数**，于是 `DEBUG=1` 被当成 `edksetup.sh` 的选项，打印 usage 后退出（exit 1）。结果是调试日志构建**根本走不到** `build -D BOOT_DEBUG=1` 那一行。
- 改法：source 之前 `set --` 清掉位置参数（DEBUG 已解析完，后面的代码不再用 `$@`）。
- 验收：`bash Boot/build.sh DEBUG=1` 输出 `Boot OK  BOOT_DEBUG=1`；`bash Boot/build.sh` 仍为 `BOOT_DEBUG=0`。
- 收益：`BootDbg` 这条日志线恢复可用。**它是 PR-08 验收的前提**（「保留固件模式」那条判据要靠 `BootDbg` 输出对照），不修的话后面几个 PR 都没法验。

**第一天收益**：四条都属「不做也不会立刻崩，但会在某天以奇怪现象出现」的缺陷。修完之后，Boot 的**日志与行为重新一致**——这对教学项目尤其重要，因为学生第一次排障靠的就是「日志说发生了什么」。全部四条都能用现有 QEMU + 串口验收，不需要新硬件。

## 3 · 第二天：边界与契约

### PR-05 · 短读未判定

- 位置：`LoadKernel/Read.c:79-93`
- 现状：读循环里 `Chunk == 0` 时 `break`，若此时 `Status` 仍是 SUCCESS，则 `*OutSize = Got < FileSize` 静默返回成功；后续以「截断的 ELF」继续校验，最终报的是 `CheckKernelFile Failed`，与真实原因（读盘不足）不符。
- 改法：循环结束后显式判定 `Got == Total`，不等则返回 `EFI_VOLUME_CORRUPTED` 并打印 `got/total`。
- 验收：人为把 `Kernel.elf` 截断到 4 KiB，串口出现短读字节数而不是「ELF 校验失败」。
- 收益：错误归因正确；这是排障里最贵的一类误导。

### PR-06 · PT_LOAD 页对齐相邻冲突无诊断

- 位置：`LoadKernel/Elf.c:199-206`
- 现状：每段按 `ceil(SizeInMemory/4096)` 页 `AllocateAddress` 精确钉在 `PAddress`。若两个 `PT_LOAD` 相邻且首段末页向上取整后盖住次段起点，第二次申请必然失败，报的是 `AllocatePages(...) Failed`，看不出是「段布局问题」。
- 改法：申请失败时打印段序号、请求地址、页数，以及**已被占用的区间**；`CheckKernelFile` 里增加「段区间两两不重叠」的显式检查。
- 验收：人为在链接脚本里把两段排成未页对齐相邻，报错信息直接指出两个段号与地址。
- 收益：换链接脚本（换架构、加 section）时不会被一条泛化错误卡住。

### PR-07 · 入口返回后走 `__builtin_unreachable`

- 位置：`JumpToKernel.c:53-60`
- 现状：`typedef` 写在函数体内；`Entry(BootConfig)` 之后接 `__builtin_unreachable()`。若内核入口真的返回（调试期常见），行为未定义。
- 改法：`typedef` 提到文件作用域；入口返回后 `for (;;) CpuDeadLoop();`，并可打一行 `Boot: Kernel Returned`。
- 验收：临时把 `EntryAddress` 指向一个 `ret` 桩，串口出现该行且机器停住而不是跑飞。
- 收益：调试期行为可预期；EDK2 风格一致性。

### PR-08 · 选模哨兵与魔数（轻量部分）

- 位置：`Video/Video.c:106-113, 164`
- 现状：用 `BestScore = 6000000000ULL` 表示「保留固件当前模式」，再用 `BestScore >= 6000000000ULL` 在打分里把它顶掉。哨兵与分值混在同一变量里。
- 改法：加一个 `BOOLEAN KeepCurrentMode`，哨兵从分值域里拿掉；分值常量本 PR 只做**具名**，优先级重排留给 PR-09。
- 验收：QEMU 与真机（有 EDID）两种路径的选模结果与改动前逐字节一致（对比 `Boot: GetVideoInfo Done (Pick WxH Mode N)`）。
- 收益：选模逻辑从「一个数字大于另一个数字」变成「一个开关加一组具名优先级」。

**第二天收益**：把「换介质 / 换链接脚本 / 调试期」这三种情况下会出现的玄学失败，变成有明确指向的报错。这一天的改动全部是**只加诊断、不改策略**，因此回归风险最低，适合放在止血之后立刻做。

## 4 · 第三天：可讲性（白皮书视角）

这一天的目标是让「选模」和「认卷」两节**能画成流程图讲**，而不是解释一串数字。

### PR-09 · 打分优先级做成具名常量表

- 位置：`Video/Score.c:88-110`、`Video/Video.c:149-170`
- 现状：`5e9 / 6e9 / 3e9 / 2e9 / 1e9 / 100000` 六个魔数散落两文件。真实优先级是：保留固件模式 > BLOCKS.DB 精确命中 > 同宽高比就近 > 就近。
- 改法：一组成员常量（`SCORE_KEEP_CURRENT / SCORE_CFG_EXACT / SCORE_SAME_ASPECT / SCORE_NEAREST / SCORE_DISTANCE_CAP`），文件头用一张表把「谁压谁」写成注释。
- 验收：所有分支的选模结果不变；`BootDbg` 打印分值时可读。
- 收益：白皮书这一节可以直接引用常量名讲，不必先解释 5e9 与 6e9 谁大。

### PR-10 · 13 个文件级静态变量收进上下文

- 位置：`Video/Video.c:16-29`
- 现状：`GetVideoInfo` 写 13 个 static，`SetVideoMode` 再读，签名上看不出「必须先 Get 再 Set」。
- 改法：定义 `VIDEO_SELECTION`（Gop / BestMode / BestW / BestH / InVm / Cfg… / Edid… / ModeCount），`GetVideoInfo(…, VIDEO_SELECTION *)`、`SetVideoMode(…, const VIDEO_SELECTION *)`。
- 验收：行为不变；`SetVideoMode` 传入空上下文时返回 `EFI_NOT_READY`（替换现有的 `sBestScore == 0` 判断）。
- 收益：依赖从「文件级隐藏状态」变成「参数」，这是模块能被替换的前提。

### PR-11 · ROOT.CFG 缓存改显式传参

- 位置：`Volume.c:415-416, 438-453`
- 现状：`sRootCfg` / `sRootTried` 是函数内静态，缓存 ROOT.CFG 的解析结果，隐蔽且不可重入。
- 改法：解析上移到 `BootSelectOsVolume`（或调用方）一次完成，作为 `const BOOT_ROOT_CFG *` 传入。
- 验收：认盘顺序与日志不变。

### PR-16 · 双副本一致性检查（不合并）

- 位置：`Boot/BootPkg/UefiBootConfig.h` 与 `Kernel/BringUp/X64/UefiBootConfig.h`
- 现状：两份副本靠人工同步；现有 size/offset 断言能挡布局漂移，挡不住「尺寸不变但语义变了」（例如把某个 `UINT32` 从宽改成高）。

- 收益：把「改一份必须改另一份」从**人的记忆**变成**构建期错误**，同时保留两份独立可编这一硬约束。

**第五天收益**：这一天不改任何逻辑，但把两个最容易在半年后咬人的地方（损坏的注释、跨生命周期的指针、双副本漂移）变成机器可检查的东西。对教学项目来说，这类「约定」比功能更值钱，因为它们决定了别人接手时的成本。

**推论**：16 扇区的「数据簇写」落进了 FAT 区，说明某条写入路径用的 `gDataStart`/簇几何与卷实际不符（或跨卷时沿用了别的卷的参数）。真机上后果就是 FAT 被覆盖 → 目录项变垃圾 → 卡死。

### 10.7 商店安装慢（已定性）

`Kernel/HAL/X64/Drivers/Bus/XHCI/Msc/BulkOnly.c` 的 `TransferSectors`：

```c
Cdb[8] = 1;                       /* 每次只传 1 个扇区 */
UINT8 Bounce[512];                /* 512 字节 bounce */
for (i = 0; i < Count; i++) { ... Bot(...) ... }   /* 每扇区一次完整 BOT 往返 */
```

→ 真机 U 盘（MSC）每次 USB 命令只搬 512 字节，理论速率 0.3~1 MB/s。
→ 开机 5000+ 次单扇区读，每次一个 BOT 往返，是 NUC 启动慢的主要嫌疑之一。
→ 与 FAT 无关，FAT 只是受害者。

**PR-F4（已落地 2026-10-29）**：`TransferSectors` 改为多扇区传输，每命令最多 64 扇区（32 KiB），`Cdb[7..8]` 填传输长度，bounce 由 512 B 栈缓冲改为 32 KiB BSS。

**但有个前提**：只有当调用方一次请求 >1 扇区时才生效。当前 QEMU 的 BLOCKS 镜像簇大小是 **1 扇区（512 B）**，FAT 层每次都只发 1 扇区 → 这条 PR 在本镜像上没有提速；真机 U 盘若簇更大（4K/8K/16K）则直接按倍数受益。

**PR-F4b（真正的杠杆）**：FAT 层合并连续扇区（`ReadFileClusters` / `StoreCluster` 按链上连续段发起多扇区 I/O）。开机 5000+ 次单扇区读的来源就在这里。



### 10.8 修复：FAT 分卷上下文 + FS 互斥（PR-F5，已落地）

**根因**：FAT 层的扇区/簇缓冲与几何量是**全局单份**；`FileSystemActivate` 靠重新 Mount 重置全局量。桌面 Worker（`Tasks.c:158 → FileSystemEnsureSecondaryVolumes → RemountVolumes`）在后台重挂卷时，会把前台正在写盘的「当前卷」切走、把它的扇区缓冲冲掉 → 写回脏目录项 → vvfat 断言 / 真机 FAT 损坏卡死。

**修法**：

1. `FAT_VOL` 结构按「盘号 + 起始 LBA」分卷保存缓冲与几何（`FatPrivate.h`），旧全局名用宏别名指向 `gFatCur->X`，FAT 各源文件不改；
2. `FileSystemLock/Unlock`（`Services/FileSystem`）包住 13 个公开入口，保证「切卷 + 操作」期间当前卷不被换走；不关中断，自旋用 `HalCpuRelax`。

**验证**：构造复现（KVM，`set effects low/high` 连切）**10 次 0 断言**（修复前 2〜4 次必崩）；`ls /`、`THEME.CFG`、`BLOCKS.DB` 内容完好；冒烟 PASS；真机手测通过。

**代价**：BSS +198 KB（4 卷 × 66 KB）。后续可做「全卷共用簇 scratch」，把卷表压到 ~1 KB。
