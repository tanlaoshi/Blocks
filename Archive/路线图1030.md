### 5.0 一次性采集（先跑这个，省事）

```sh
{
  echo "== 5.1 =="; uname -a
  ls -l /sys/bus/sdio/devices/ 2>/dev/null
  for d in /sys/bus/sdio/devices/*; do echo "$d v=$(cat $d/vendor 2>/dev/null) d=$(cat $d/device 2>/dev/null)"; done 2>/dev/null
  lsusb -t 2>/dev/null | head -20
  lsmod
  dmesg | grep -iE "aic|8800|8723|8189|cfg80211|sdio" | head -40
  echo "== 5.2 =="; ls -l /lib/firmware/ | grep -iE "aic|8800|rtl|brcm|fw"
  md5sum /lib/firmware/*8800* /lib/firmware/*aic* 2>/dev/null
  echo "== 5.3 =="; zcat /proc/config.gz 2>/dev/null | grep -iE "AIC|8800|CFG80211|MAC80211|MMC_SDIO"
  ls /lib/modules/$(uname -r)/kernel/drivers/net/wireless/ 2>/dev/null
  echo "== 5.4 =="; grep -i mmc /proc/interrupts; cat /sys/kernel/debug/mmc1/ios 2>/dev/null
  echo "== 5.5 =="; cat /proc/cmdline; free -m; head -3 /proc/cpuinfo
} > /tmp/duo-info.txt 2>&1
wc -l /tmp/duo-info.txt
```

sed -n '101,200p' /tmp/duo-info.txt

### 5.7 结论（2026-10-30 已由真机确认，不再是待填项）

- **是否 fullmac：是。** 802.11 状态机全在 `fmacfw` 里跑，主机侧只负责：下载固件、发 CFG 消息、
  搬数据帧。好处是管理帧不用我们实现；代价是**固件不跑起来就什么都做不了**（这也解释了
  为什么"通道打通"是整件事的分水岭）。
- **总线中断线：SDIO DAT1**（PLIC 38）。**当前没做中断，用轮询 `fn1 0x04`**；先通再快。
- **可复用的现有代码**：`Sdhci` 控制器层（`Command/Transfer/Card/Utility`）可直接用；
  `Ethernet` 与 WiFi 无关（不同 MAC）。SDIO 协议层是本轮新写的（`Sdio.c`），
  **PI 3B 那侧将来要把这一层抽公共**（见 §9.5）。
- **固件放哪：不放 rootfs，放 BLOCKS 卡的 `/Assets/Fw/aic8800/`**（见 §5.9）。
- **PR-30 实际工作量**：2026-10-30 一天，从"没有任何 SDIO 日志"到"双向消息通道 + 检查模式"。
  期间踩的坑按"归属判断错"归类最准：FBR 在 fn0 空间、IOEx 位映射、RX 三分支漏 fn1。

### 5.9 手册确认 + 固件搬运

**TRM 已确认**（`Source/SG2000_TRM_V1.0-alpha.pdf`）：

- **SD1 控制寄存器 @ `0x04320000`**（64KB）—— 就是设备树里的 `4320000.wifi-sd`，
  与 `SD0 @ 0x04310000`（SD 卡槽）、DMA @ `0x04330000` 相邻。
- 第 **18.4 节「eMMC/SD/SDIO 控制器」**（Page 542 起）有指令/响应格式、1/4/8-bit
  数据封包，是我们写 SDIO 层的第一手依据。
- 芯片原生「2 个 SDIO 接口」，SDIO 3.0。

**固件搬运（已定：走 SD 卡，不走串口）**：

> 2026-10-30 决定并已落地：固件放**同一张启动卡的 BLOCKS 分区** `/Assets/Fw/aic8800/`
> （`fw_adid.bin` / `fw_patch.bin` / `fw_patch_table.bin` / `fmacfw.bin`，外加短名别名），
> 内核经 `FileSystemReadFileAt` 4 KB 分块读。理由：560 KB 走 115200 至少一分半且易丢字；
> 卡本来就要插拔，`cp` 一次即可，还能换固件不重编内核。
> 校验方式：`wififw stat` 只 stat 不读；读完对账 `1708B / 1048B / 30040B / 331348B`。

### 5.11 写固件（最后的不可逆步骤）

**前置**：B1（表解析）+ B2（46 条写）都通过，且 `wififw write confirm` 不再被拒。

**顺序**（厂商 `aic_bsp_main.c:27-56`）：

| 阶段 | 文件 | 落点 | 必需 |
|---|---|---|---|
| 1 adid | `fw_adid.bin`（1708） | `0x00201940` | 是 |
| 2 patch | `fw_patch.bin`（30040） | **`0x001E0000`（取表值）** | 是（D80 强制 `info_len!=0`） |
| 3 fmacfw | `fmacfw.bin`（331348） | `0x00120000` | 是 |
| 4 start | `DBG_START_APP_REQ`（boottype=1） | — | 是 |

**判据**：`start` 之后必须收到 boot 消息并打出芯片侧信息；**只有 `state=done` 不算通过**（评审 W5）。

**已明确不可接受的三种"绿"**：
1. `enum ok (cis)` 与 CIS 结果无关（已修）；
2. `fw state=done` 与芯片是否启动无关（B2 必须补 boot 消息判据）；
3. `write` 声称 `NOTHING WRITTEN` 却写寄存器（已修）。

**失败恢复**：写 RAM 阶段失败可用 `wifiprobe` 的 GPIOA15 断电脉冲复位；**start 之前失败一律安全**。
`start` 之后若起不来，需要重新上电再从头写（不接受"半启动"状态下继续）。

## 八、字体：FreeType 内存池 free-list（已完工）

**为什么排进来**：字体 4/7 回归（`fa887000`）修完后，真因之一暴露出来——FreeType 端口是
**256 KiB 静态 bump arena、`FtFree()` 空实现**（`Kernel/ThirdParty/freetype-port/ftsystem_blocks.c`），
开机第 **24212** 个字形就 OOM（日志 `FONT ft oom cp=24212`），此后 FT 对所有码点返
`FT_Err_Out_Of_Memory(0x40)`，全部退到 stb。所以 `fa887000` 的「OOM 后整会话确定走 stb」
是**止血**，不是治本：字号纹理变糙、FT 那条更快更好的路径整场没用上。

**要做的**

1. `ftsystem_blocks.c` 实现**首次适配 + 相邻块合并**的 free-list（静态 arena、无系统 malloc、
   8/16 字节对齐、失败返 NULL 不返回重叠块）；
2. 加 `FtArenaStats(total, used, peak, fail)` 供串口打印；
3. 验证判据：**连续栅格 5000+ 字形不再 OOM，且 arena 用量在稳定区间波动**（证明在回收，
   不是靠放大 arena）；
4. 可靠后去掉 `FreeTypeRaster.c` 的 `gFtDead`（或降级为「连续 N 次失败才停用」），恢复 FT 优先。

**风险 / 注意**

- arena 是内核静态数组，**碎片**是主要敌人：字形 bitmap 大小差异大，纯首次适配容易留下
  无法合并的缝。必要时按 size-class（如 32/64/128/256/512/1K/2K/4K 桶）分配；
- 必须能承受 `realloc`（FreeType 会用它扩 bitmap）；
- 出问题时的退路很干净：`gFtDead` 逻辑还在，OOM 自动回 stb，不会崩。

**验收**：QEMU 跑自检 + 真机进设置翻页滚动，看 `FONT ft oom` 不再出现、`FtArenaStats` 的
`used` 回落。

### 8.1 并发构建会互踩（已两次发生）

`Build/` 是共享目录，arch-stamp 清理会删掉别的架构/模块的中间产物：

- 一次是 `can't create .../HubCompanion.o`（x86 两 agent 同时编）；
- 一次是 `can't create TrueTypeLoad.o`（x86 编字体 + riscv 编 DUO 同时进行，riscv 的 stamp 清掉了 x86 的 Fonts 目录）。

**规矩**：同一台机器上同时只允许一个 agent 跑 `build.sh`；确需并行时先 `pgrep -af build.sh`，或给不同 agent 分配不同 `BUILDDIR`。撞上时**重试即绿**，但不要误以为是代码坏了。

### 8.2 SDIO 协议测试台

`Tools/SdioTest/sdio-harness.c`：把真实的 `Sdio.c`/`Io.c` 编到 x86，配一台按 SDIO 规范解码的假卡

## 九、PI 3B WiFi 开发路径（BCM43430 / CYW43438）

> 定这条路径的直接依据：**DUO 用「先埋点、再改」的方法，四轮从「零日志」走到 SDIO 枚举成功**。
> PI 上次失败（固件全灌完、双核出复位，卡在 HT 时钟 `csr=0x50`）不是因为难，而是因为
> **当时没有对照物、也没有埋点**，只能盲试。
>
> 这一轮的原则：**资料不齐不动代码；每一步先有串口判据，再有实现。**

### 9.0 与 DUO 的异同（决定哪些能直接复用）

| 维度 | DUO S（AIC8800D80） | PI 3B（BCM43430） | 复用 |
|---|---|---|---|
| 总线 | SDIO，SDHCI @ `0x04320000` | SDIO，**SDHCI（Arasan）@ `0x3F300000`**，mmc1 | ✅ 同一套 `Sdhci*` |
| 枚举 | CMD5 / CCCR / 4-bit / HS | 完全相同 | ✅ `Sdio.c` 直接可用 |
| 内核态 | 无（裸机） | 无 | ✅ |
| 唤醒/供电 | GPIOA15 | `BT_REG_ON`/`WL_REG_ON`（dts 有） | 🔁 换 GPIO 号 |
| 厂商驱动形态 | vendor 私有 `aic8800_bsp` | **brcmfmac（Linux 主线，代码干净）** | ✅ 更好对照 |
| 固件加载 | 私有协议（adid/patch） | **标准 Broadcom backplane 窗口写 RAM** | ❌ 全新，本路径核心 |
| 对照实现 | AIC SDK | **`cyw43_ll.c`（Pico SDK，C，无 OS）** | ✅ 极佳对照物 |
| 现有失败 | 无 | HT 时钟 `csr=0x50` | ⚠️ 必须先解释这个值 |

**结论**：PI 的 P1（枚举）几乎白捡；真正的难点集中在 **P2 backplane 访问** 与 **P3 ALP/HT 时钟**，
也就是上次卡住的位置。所以本路径把 80% 的篇幅放在这两步。

### 9.1 七步（每步一个串口判据，不到判据不往下走）

| 步 | 目标 | 关键动作 | 验收字符串（串口） |
|---|---|---|---|
| P1 | SDIO 枚举 | 复用 DUO 的 `SdhciHostAt(1)` + `Sdio.c`，换基址/IRQ | `Pi: SD1 init ok clock=50MHz width=4bit`<br>`Pi: CIS manfid=02d0 device=a9a6` |
| P2 | **backplane 访问** | 写 `SBSDIO_FUNC1_SBADDRLOW/HIGH`（`0x1000A/0x1000B`）定位窗口，再经 F1 读写 | `Pi: chipcommon chipid=43430 rev=..`<br>`Pi: backplane rd/wr ok`（先写后读回同值） |
| P3 | **ALP / HT 时钟** | 置 `SBSDIO_ALP_AVAIL_REQ`(0x08) 等 `ALP_AVAIL`(0x40)；置 `HT_AVAIL_REQ`(0x10) 等 `HT_AVAIL`(0x80) | `Pi: ALP ok`<br>`Pi: HT ok csr=..`（**必须解释上次的 `0x50`**） |
| P4 | 固件下载 | 按 brcmfmac `download_firmware`：写 RAM → 校验 → 释放 ARM core → 等 HT | `Pi: fw 400447B loaded`<br>`Pi: firmware up` |
| P5 | SDPCM / BCDC | SDPCM 头、控制通道、`get/Set IOVAR`（`cur_etheraddr`、`country`） | `Pi: mac=..:..`<br>`Pi: iovar ok` |
| P6 | 802.11 管理 | escan → auth → assoc | `Pi: scan n=..`<br>`Pi: assoc ok` |
| P7 | 数据路径 | SDPCM 数据帧 ↔ lwIP netif，DHCP | `Pi: DHCP ip=...` |

**P1→P2 之间不允许跳步**：P2 的「写后读回」如果不成立，后面所有寄存器语义都是假的——
这正是上次 `csr=0x50` 的教训（读到的值可能是窗口没对齐导致的垃圾）。

### 9.2 P2 细节（最容易做错的一步）

Broadcom 的 backplane 不是内存映射，而是**经 F1 函数窗口间接访问**：

1. 把目标 backplane 地址拆成低/高字节写进 `SBADDRLOW`/`SBADDRHIGH`；
2. 之后对 F1 的固定地址（如 `SBSDIO_FUNC1_CHIPCLIP`/`SBDATA`）做 CMD52/53，就会落到该 backplane 地址；
3. **写高位地址会重置窗口**，所以「设置窗口 → 读」必须紧邻，中间不能插别的 F1 访问。

判据要写成「写 `0xDEADBEEF` 到某个 scratch 再读回」，而不是「读到非零就算通」——
**非零不代表读对了地址**。

### 9.3 P3 细节（解释上次的 `csr=0x50`）

`0x50` = `ALP_AVAIL(0x40) | HT_AVAIL_REQ(0x10)`，即**ALP 已就绪、HT 请求已发出但从未就绪**。
这说明：固件没跑起来（core 没释放或释放后没启动），而不是「时钟配置写错」。

所以 P3 的正确做法是**先确认 chipcommon 能读、再确认 core 复位状态**：

- 若 `chipcommon` 的 `chipid` 都读不出 → 问题在 P2（窗口），不在时钟；
- 若 chipid 正确、`HT_AVAIL` 不来 → 问题在 P4（core 没释放/固件没写对）。

**把「时钟等不到」和「固件没起来」区分开，是这一轮必须补上的判断力。**

- `Sdio.c` 里前缀混用：`SdioReadCisPointer`、`DuoWifiPowerOn`、`SdhciMark*`、`gWifiSdioState`；
- `ftsystem_blocks.c` 里既有 `FtArena*` 又有 `FtAlloc*`，看名字分不清谁调谁；
- 日志字符串里 `WiFi:` 与 `wifi:` 两种大小写并存（`wifiprobe` 命令行是 `wifi:`）。

**规矩**：

1. **函数前缀 = 模块名**：`Sdio*`（协议）、`Sdhci*`（控制器）、`Duo*`（板级）、`Ft*`（FreeType 移植）。
   一个函数只能有一个家主，跨层调用要**显式**（谁来调谁写在注释里）。
2. **类型全大写+下划线**：`SDHCI_HOST`、`SDIO_CIS_INFO`；**不要**混用 `SdhciHost`。
3. **全局变量 `g` + 模块前缀**：`gWifiSdioState`（✓）、`gState`（✗）。
4. **日志前缀统一小写模块名 + 冒号**：`wifi:`（板级）、`sdio:`（协议）、`sdhci:`（控制器）。
   **串口里出现大写前缀就算不规范**——它会让人以为来自不同模块。
5. **布尔用 `int` 但名字带 `Is/Has/Ok`**：`gScanOk`、`gPresent`（✓）；`gFlag`（✗）。
6. **禁止拼音缩写、禁止 `tmp/temp/data2/buf2`**：要么说明内容（`CisBuffer`），要么说明位置（`FifoRead`）。
