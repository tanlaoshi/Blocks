## 厂商对照 · 规划前必读（避免再踩）

### STA 模式组播 **不是** AP 的 BCMC 建站

`rwnx_select_txq`（`rwnx_tx.c`）：

- **`NL80211_IFTYPE_STATION`**：一律 `sta = rwnx_vif->sta.ap`（**含组播 DA**），**不**看 `ap.bcmc_index`。
- **`AP` / `MESH`**：组播才 `sta_table[ap.bcmc_index]`；`bcmc_index` 来自 `apm_start_cfm` / `mesh_start_cfm`——**STA 关联路径不会走这条**。

`rwnx_get_tx_priv` 里 `sta_idx = NX_REMOTE_STA_MAX(32) + vif` **仅当** `ndev_idx == NX_BCMC_TXQ_NDEV_IDX`。STA 正常 QoS/非 QoS 帧走的是 **AP sta 的 ndev 队列**，不是 BCMC 队列。

**推论（规划口径）**：

1. Docs/14 已否：`mcast=32` 等 → 固件 **不发**；`mcast=ap_idx` → 发得出但 **KeyID=0**。与「STA 应填 ap_idx」一致——**问题不在「漏填 32」本身**，而在「填了 ap_idx 仍用 PTK 加密组播」。
2. 下一刀主线应优先：**GTK 默认钥是否真正挂到固件的 TX 选钥逻辑**（及 control port / 装钥序），而不是再盲扫 staid。
3. BCMC 建站调研降为 **备选**：仅当发现固件/D80 对 STA 组播另有隐藏 BCMC 表项、且有规格/抓包证据时再开刀。

### 已排除（勿重做 · 摘 Docs/14）

| 尝试 | 结果 |
|---|---|
| GTK keyid/cipher/pairwise/长度矩阵 | 全无 OFFER |
| 广播 staid = ap_idx | 上空气 KeyID=0 → AP 丢 |
| 广播 staid = 0xFF / 32 / 8 / … | 固件不发 |
| ac / tid / M4 install 位 / 再 `ME_SET_CONTROL_PORT` | 无变化 |
| 单播 ARP→AP | 无回；`decrypted=0` |

## dwifi-data · 装钥后数据加密（拆刀） <a id="dwifi-data"></a>

> **总判据**：课网下 DHCP Discover（或等价组播）空口 **KeyID=2（GTK）**；单播数据帧可被 AP 理解（ARP/DHCP 有回应线索）。  
> **协议**：AIC LMAC `txdesc` + `MM_KEY_ADD`；对照厂商 **STA→sta.ap**，禁止启发式乱改超时。  
> **一次一刀**；能 `probe.cfg` / ksend 证伪的优先于重刷。  
> **战场**：`Kernel/HAL/RiscV/Board/milk-v-duo-s/Sdhci/WifiEapolTx.c`、`WifiKeyAdd.c`、`WifiHandshakeInstall.c`、`WifiDhcp.c`、`WifiControlPort.c`（及直接调用链）。  
> **勿动**：`rpi-3b/**`；勿为 Duo 弄坏 arm64 编过；`Commands.c` 只弱注册。
