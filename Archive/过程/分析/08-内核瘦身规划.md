# 08 · 内核瘦身与核外更新 · 规划

> **状态**：规划稿，**未动任何代码**。
> **起因**：用户提出「Kernel 只保留读 FAT + 执行 ELF 的能力，业务代码抽成文件，以后只更新 BLOCKS 分区上的文件」。
> **原则**：先量化现状，再定边界，再分阶段；**每个阶段都有判据与回滚方式**，不一次动全身。

---

## 1 · 目标与非目标

### 目标

1. **内核变更频率下降**：日常改动（WiFi 协议、GUI 布局、应用）不再需要重刷内核；
2. **迭代时间下降**：从「刷卡 + 上电 ≈ 5 分钟且要人」降到「传文件 + 重启程序 ≈ 30 秒且无人」；
3. **内核变小、变稳**：把改动最频繁、耦合最松的代码移出内核。

### 非目标（明确不做）

- **不做用户态驱动**（见 §4.1：今天的内核没有设备内存映射与中断投递到用户态的能力，代价远超收益）；
- **不追求微内核纯度**：不为了"干净"而拆掉性能关键路径（中断、调度、页表、块设备）；
- **不动第三方**（`ThirdParty/lwip` 131k 行、FreeType）：它们要么编进核，要么整块搬，不做内部改造。

### 2.1 一个必须先纠正的说法

我此前说过「应用层、GUI、socket 早就是核外可更新的」——**错了两块半**：

- ✅ **用户 App** 确实核外：`Core/Process/Load.c:187` 的 `ProcessLoadPath()` 走
  `VfsServiceReadFile(Path, …)`，**exec 时从 BLOCKS 分区读 ELF**；
- ❌ **GUI 在核内**：`Services/Gui/**`；
- ❌ **socket/lwIP 在核内**：`ThirdParty/lwip`；
- ❌ **所有驱动在核内**：`HAL/**`。

**而且连"App 核外更新"这半也有前提没满足**：我们没有"往卡上放任意文件"的命令
（`ksend` 的板级实现写死 `Kernel.elf`）。所以**今天实际上一块业务代码都还不能核外更新**。

## 3 · 目标架构

```
┌───────────────────────────────────────────────┐
│ 用户态（可热更新，文件在 BLOCKS）              │
│   应用：Hello / Snake / TaskMgr …（已有）      │
│   服务：wifid（扫描/关联/WPA2）、将来 gui 服务 │
│   ↓ 系统调用（文件/进程/内存/网络/窗口/设备通道）│
├───────────────────────────────────────────────┤
│ 内核（稳定，尽量不改）                          │
│   内存管理 / 调度 / 中断 / syscall / ELF 装载   │
│   块设备 + FAT（要它才能读文件）                │
│   串口控制台 / 定时器                           │
│   驱动：SDHCI、SDIO 传输、消息通道、网卡、显示   │
└───────────────────────────────────────────────┘
```

### 内核必须保留的（不可协商）

| 能力 | 为什么 |
|---|---|
| 页表 / 内存管理 / 物理页 | 用户态一切的基础 |
| 调度 / 进程 / 地址空间 | 同上 |
| 中断 / 定时器 | 用户态拿不到 |
| syscall 分发 | 同上 |
| ELF 装载 | "执行 ELF" 的前提 |
| **块设备 + FAT 读** | **要它才能把 ELF 从盘上读出来**（自举依赖） |
| 串口控制台 | 出问题时唯一的救命通道 |
| 驱动（寄存器/DMA/中断） | 见 §4.1 |

### 可移出的（按收益/代价排序）

1. **WiFi 协议层**（3,271 行，改动最频繁）——最值得搬；
2. **GUI / Desktop / Look**（20,145 行，改动中等，但每帧跨进程调用，性能风险最大）；
3. **lwIP 与 socket 服务**（已有 `SYS_NET_*` 系统调用，搬出去相对自然）；
4. **Store / Apps UI**（4,889 + 5,176 行，业务性质，天然适合搬）。

## 4 · 关键约束与代价（这一节决定可行性）

### 4.1 用户态驱动：今天做不到，且不建议做

内核当前**没有**：

- 把设备物理内存映射进用户地址空间的接口（`ProcessMmap` 只做匿名/文件映射，无 DEVICE 语义）；
- 把设备中断投递到用户态的机制（无 IRQ→事件/等待队列）。

要做这两件事，等于自造一个微内核的驱动模型：**收益（少数驱动可热更新）远小于代价（内核最复杂部分的改动）**。

**结论：驱动留在核内，不做用户态驱动。**

### 4.2 性能

GUI 是**每帧**路径（60 Hz）。若窗口合成跨进程，每帧几十次 syscall + 数据拷贝，风险很高。
**所以 GUI 搬运排最后，且必须先做一次"跨进程合成"的可行性验证（P3 之前）。**

WiFi 不是每帧路径（扫描/关联是低频），**跨进程代价可接受**。

### 4.3 系统调用 ABI 冻结

新增"设备通道"类系统调用（例如 WiFi 的消息收发）会成为长期接口。
按仓里既有约定，**改 ABI 要先进 `Include/Abi/SyscallABI.h` 并同步速查卡**。
一个粗糙的 ABI 会比"内核里多 3 千行"更难改——**这一刀的设计要评审后再落地**。

### 4.4 调试复杂度

现在一次串口日志能看完"从扫描到关联"。搬到用户态后是"内核日志 + 进程日志"两条线。
**必须先把用户态日志通道做顺**（`ConsoleIo` 已有，但要确认长驻服务进程的输出不会互相覆盖）。

## 5 · 分阶段路线

> 每阶段都要求：**判据达成才进下一阶段**；任何阶段都可独立回滚（都是增量提交）。

### P0 · 通用文件传输（0.5 天，零风险）

**做什么**：`ksend` 参数化——PC 端 `--path`，板端接受目标路径（现在是写死的 `Kernel.elf`）。

**判据**：
- `python3 Tools/ksend.py --port /dev/ttyUSB0 --file /tmp/SNAKE.ELF --path BLOCKS:SNAKE.ELF` 成功；
- 板上 `exec SNAKE.ELF` 跑的是新传上去的那份（改个字符串能看出来）；
- 全文件 CRC 校验通过、失败可回滚。

**收益**：**立刻**让"应用层核外更新"从口号变成事实（虽然 App 改动频率低，但这条通路是后续一切的基础）。

**注意**：这只解决 App，**内核仍然要刷卡**（`boot.sd` 才是被启动的东西）。

### P1 · 服务进程骨架（2–3 天，低风险）

**做什么**：

- 一个**长驻用户进程**的框架（启动、退出、崩溃重启）；
- 一条**服务↔内核**的通用通道（先用最简单的：一块共享内存 + 事件计数，或 socketpair 语义）；
- 把一件**低风险的小业务**搬过去做样板：建议取 **Store 的 UI 逻辑**或**某个 shell 命令**（不取 WiFi，避免与主线抢）。

**判据**：该服务的日志、退出、重启都正常；内核不因此多一行 WiFi 逻辑；`ssh`/串口都能看到它的输出。

**回滚**：服务不启就不启，内核回到原状（代码保留在核内直到 P1 判据通过）。

### P2 · WiFi 协议层搬用户态（3–5 天，中风险，**收益最大**）

**前置**：P1 的服务通道可用；WPA2 已在核内跑通（**先通再搬**，否则同时改两件事）。

**做什么**：

- 内核保留：SDHCI 枚举、SDIO 命令、**LMAC 消息收发**、流控、固件下载（3,271 行里的传输侧 2,290 行里的一部分）；
- 新增设备通道 syscall（**设计要点**）：
  - `send(msg_id, param_buf, len)` —— 发一条 LMAC 消息；
  - `recv(timeout, &frame)` —— 收一条消息**或**一帧数据（含 EAPOL 数据帧）；
  - 不做"读寄存器"这种原始接口（那会把驱动语义泄漏给用户态）。
- 用户态 `wifid`：扫描、关联、WPA2 四次握手、`MM_KEY_ADD` 触发（密钥由用户态算好后经 syscall 交给内核转发）。

**判据**：
- `wifid` 能完成扫描（与核内版本输出一致）；
- 能连上 `Apple`（与核内版本相同的判据）；
- **改一次 WiFi 代码的时间**：从「刷卡 5 分钟 + 人在场」降到「传文件 + 重启 wifid ≈ 30 秒」——**这是本阶段唯一真正的验收指标**。

**回滚**：核内版本保留为默认，`wifid` 作为可选路径（编译开关），出问题切回。

### P3 · GUI 搬用户态（1–2 周，高风险，**收益不确定**）

**前置**：先做一次"跨进程合成"的**性能可行性验证**（把一帧合成放到用户态，量出每帧开销）。

**若验证不过，就地停止**——GUI 留在核内不是失败，是理性选择。

### P4 · 更彻底的内核瘦身（不排期）

用户态驱动、lwIP 外移、按需加载驱动。**在没有明确收益前不做。**

## 6 · 判据与度量（怎么知道真的变好了）

| 指标 | 现在 | 目标 |
|---|---|---|
| **改 WiFi 代码的迭代时间** | 刷卡 5 分钟 + 要人 | **≤30 秒 + 无人** |
| 一周内内核改动次数 | 每天数次 | P2 后 ≤1 次/周 |
| 内核镜像大小 | 2.98 MB（x64） | 不设目标（大小不是目的，稳定性才是） |
| 因改内核导致的"起不来"事故 | 今天已发生多次（坏 HEAD、刷错架构） | 0 |

**度量方式**：`git log --since` 统计内核路径改动次数；每次迭代记录时间戳（串口日志已带时间）。

## 7 · 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| **系统调用 ABI 设计粗糙** | 比现在更难改 | P2 前单独评审 ABI；先做原型不合并 |
| **调试变难**（两套日志） | 排障时间变长 | P1 先把服务日志通道做顺，再搬 WiFi |
| **性能回退**（GUI） | 卡顿 | P3 前做可行性验证，不达标就停 |
| **双份代码漂移**（核内 + 用户态两份 WiFi） | 修一边忘一边 | P2 期间核内版本冻结（只修致命 bug），判据通过后**删除核内协议层** |
| **用户态先崩溃** | 看起来像"WiFi 坏了" | 服务自动重启 + 明确日志「wifid restarted」 |

## 8 · 建议的下一步（等你拍板）

```
现在 → P0（半天，零风险，立刻见效）
接着 → 回到主线：WPA2 在核内跑通
然后 → 若 WPA2 改动次数 > 10，则做 P1+P2；否则保持现状
```

**一句话**：**P0 立刻能兑现一小步；P2 才是你想要的那一步；P3 及以上先别碰。**
