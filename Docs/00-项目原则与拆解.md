# Blocks 项目原则与工作拆解

本文档是长期工作的纲领。第 1 节逐字保留原始需求，第 2 节起是拆解与执行约定。
后续所有 review 记录、白皮书、QA 都以本文档为总纲。

## 2. 七条原则与落地动作

| 原则 | 含义 | 落地动作 | 产出 |
|---|---|---|---|
| 1. 通透理解 | 你要能从第一行讲到最后一行为什么这么写 | 按启动顺序逐段 review，先讲「为什么」再讲「是什么」 | 白话白皮书（翔实）+ 视频脚本 |
| 2. 对标标准 | 当初为省事走了最短路径 | 每段标注「业界标准做法」与「当前做法」，差异写成待办 | 差异表 + 收敛计划 |
| 3. 还技术债 | 已知的妥协要一点点清 | 每段 review 结束时产出「债务条目」，编号、定级、可验证 | 债务清单 |
| 4. 可读性 | 现在读不懂 | 边 review 边改，改完必须能构建能启动 | 提交级改动 |
| 5. 模块化 | 驱动、GUI 耦合过重 | 定义模块边界与接口；先文档化边界，再动代码 | 接口定义 + 替换示例 |
| 6. 0.1.0 | 现在只是半成品 | 见第 4 节的验收清单 | 发布清单 |
| 7. 注释与命名 | 注释极度缺乏、命名不一致 | 每个函数写「为什么」，不是「是什么」；命名用完整单词 | 注释规范 |

## 3. 工作方式（执行约定）

1. **顺序**：从 OVMF 上电开始，沿真实启动路径推进，不按目录跳读。
2. **粒度**：一次只 review 一个可独立讲清的单元（一个阶段、一个子系统、一个接口）。
3. **每单元固定四步**：读代码 → 讲清设计意图与取舍 → 记录（白皮书 + QA）→ 改代码并验证。
4. **验证**：任何代码改动后必须能 `build` 且能启动到与改动前相同的位置；否则回退。
5. **不猜**：不确定的地方标 `TODO(待确认)`，绝不写进白皮书当成事实。
6. **只动一件事**：一次改动只解决一个问题，便于定位。
7. **提问即资产**：你的每一个「为什么」都进 QA 文档，含问题、答案、涉及文件与行号。
8. **原文不可改**：本文件第 1 节不得修改。
9. **改完即编译**：每次改完代码立即编译，产物必须落到 `Runtime/`——`bash Boot/build.sh` → `Runtime/Esp/X64/EFI/BOOT/BOOTX64.EFI`，`cd Kernel && ./build.sh x86_64` → `Runtime/RootFs/X64/`。用户验机直接 `sync usb`，不会替我编译，所以「源码改了、盘上没更新」是我这边的责任。
10. **一刀一放行**：每刀（一个 PR）做完即停，报告「改了哪里 / 要不要手测 / 收益」；等用户手测通过、由用户执行 TG（提交）与 TS（推送）之后，才开下一刀。我不自行提交、不自行开新刀。
11. **提交前先看 CI**：TG 之前先查 GitHub Actions，红了先修再提交。注意 Boot 不在 CI 覆盖面内（`build.yml:2` 明确「不在 CI 里编 Boot」），CI 只校验并冒烟**仓库里那份** `Runtime/Esp/X64/EFI/BOOT/BOOTX64.EFI`；因此 Boot 的改动必须连这颗重新编出的 EFI 一起提交，否则 CI 与 release 用的还是旧引导器。

## 4. 0.1.0 的验收清单（待你逐条确认）

- [ ] GUI：完善、可日常操作，不是演示级
- [ ] syscall / ABI：稳定，有版本策略与兼容约定
- [ ] 网络：可用（有实际联网能力，不只是驱动能加载）
- [ ] 商店：可用（能安装、能卸载）
- [ ] GUI 程序：常用程序齐备
- [ ] 真机：至少部分真机可跑
- [ ] qemu：必须可跑
- [ ] 教学性：有 C 基础的人能按文档读懂并改得动
