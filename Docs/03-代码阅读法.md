# 03 · 代码阅读法：从两次外部评审里提炼

> 读者画像：要给陌生代码做评审、或者自己读代码找根因的人。
> 目标：**读完能说出「这段代码是什么、不算什么、错在哪、改完该看到什么」**。
>
> 来源：2026-10-30 两次外部静态评审（`Archive/开机线Review.md`、`Archive/Duo-Sdhci-WiFi-代码Review.md`）
> 与其中的 FBR 地址空间结论。不抄通用方法论，只提炼**当天真的奏效的动作**。

---

## 0 · 一句话

**好的代码阅读不是"逐行看懂"，是"带着判据去找矛盾"。**

两次评审之所以有价值，都不是因为读得细，而是因为它们**先问了一句"你这套判据成立吗"**。

---

## 1 · 先划范围：这段代码**不是**什么

`Duo-Sdhci-WiFi-代码Review.md` 的第一条是：

> **R1 · 这是 SDIO 总线探针，不是 AIC8800 驱动。**

然后列了一张「已有 / 未有」表：有枚举和 CIS，没有固件下载、没有中断、没有 802.11。

**为什么这一步最值钱**：不划范围，评审就会拿"扫不到 AP"去骂总线层，全是无效结论。

**做法**：
- 读代码前先读它的**自述**（文件头注释、README、提交信息）；
- 列出「它承诺做什么」与「它明显不做什么」；
- 后续所有结论只在承诺范围内评价。

**我们踩过的反例**：把 `Host->Ready=1` 当成"网卡可用"，而它只表示"SDIO 枚举通过"。

---

## 2 · 审验收语义，而不是先审 bug

评审把「验收与状态」放在所有协议细节**之前**，三条：

| 结论 | 内容 |
|---|---|
| A1 | FIFO 自检把 TX/RX FIFO 当回环内存——**判据本身是错的** |
| A2 | 自检失败仍报 `probe ok`——**假绿** |
| A3 | 一次失败被闩死，重试只能靠 shell |

**这三条都不是"某个寄存器写错了"，而是"你怎么知道它成了"。**

**自问清单**：
1. 现在用来判成功的那一行日志，**真的能证明目标达成吗**？
2. 失败路径会不会把状态置成成功？
3. 这段代码为了自检，往真实通道里写了什么？（副作用）
4. 出错时只凭日志，能不能区分「参数错 / 门控错 / 硬件错」？

**判据错了比代码错了更贵**：代码错一次改一处，判据错会让人**朝错误方向优化很久**。

---

## 3 · 找对照物：不从头推，先找"别人怎么写的"

这是 Cursor 两次结论的共同来源。

### 例一：FBR 地址空间

现象：`fn1 + addr 0x110` 被卡回 `OUT_OF_RANGE`。

它的动作不是推理，而是**找对照**：

```c
/* Linux mmc 核心 */
mmc_io_rw_direct(card, 1, /* fn = */ 0, SDIO_FBR_BASE(num) + 0x10, ...)
```

**第三个参数是 fn=0**。于是结论：CCCR(0x00–0xFF)、FBR(0x100–0x1FF)、CIA(0x1000+) 全在
function 0 的地址空间，必须 `function=0 + 绝对地址`。

### 例二：验收语义词表

它引用时序表 §2.6「写长度 1536 是固件消息补齐后的线上长度」，直接判定 FIFO 回环判据无效。

**对照物的优先级**：

| 顺序 | 对照物 | 为什么优先 |
|---|---|---|
| 1 | **厂商驱动的调用行**（含参数） | 参数本身就是规范，且已验证过 |
| 2 | 厂商驱动同层实现 | 能看出"缺了哪一步" |
| 3 | 协议规范原文 | 判定"厂商是不是私有扩展" |
| 4 | 同仓库其它模块 | 判定"本仓惯例是什么" |

---

## 4 · 读参数，不只读流程

**今天最贵的一课。**

我们读厂商代码，读的是**顺序**（先写什么、后写什么），所以复现了顺序；
但没读**参数语义**（这个调用的 fn 传几、长度是字节还是块）。

结果：

```
流程对 → 顺序对 → 参数错 → OUT_OF_RANGE
```

**改法**：读厂商调用时，把每个参数列出来问一句「这个值为什么是它」：

```c
sdio_set_block_size(func, 512)
  → sdio_writeb(func, blksize & 0xff, SDIO_FBR_BASE(func) + 0x10, &ret)
                                    ↑ func*0x100，注意这是 fn0 空间里的偏移
```

**参数就是规范。** 流程只能告诉你"做什么"，参数才告诉你"对谁做"。

---

## 5 · 反例压力测试：这条结论错了会怎样

评审给每条结论都写「后果」，不是凑格式：

> L1：`SERIAL_BOOT=0` 时十六进制消失——**而 CIS/OCR/INT_STATUS 全是 Hex**，排障正好缺字段。

**做法**：对每条结论补一句「如果这条是错的/不修，用户会看到什么」。

三个好处：

1. 能排序（后果大的先修）；
2. 能被真机证伪（"你应该看不到 X" 比 "应该能看到 X" 更容易验证）；
3. 防止把"风格问题"和"会坏事"混在一起。

**分级用同一套**：⚠️ 会改外显行为 / 🟡 隐患 / ℹ️ 说明。

---

## 6 · 输出格式：结论先行 + 行号 + 写对的部分

一份能用的评审，结构固定：

```
0. 结论先行      —— 3~4 条，每条一句话
1. 范围          —— 这是什段代码不是什么
2~N. 按严重度    —— 每条：位置(文件:行) / 现状 / 为何错 / 建议
写对的部分        —— 防止下一刀误伤
修序             —— 先修哪个、为什么
硬门禁           —— 哪条判据不许被替代
```

**「写对的部分」这一节最容易被忽略，但最有用**：没有它，下一个改代码的人会把对的东西一起改掉。

**「硬门禁」是防回归的锚**：

> 进 S4 的硬门禁：串口必须出现 CIS manfid 目标行；**不要用 FIFO rw ok 替代。**

一句话就把"用错证据过关"这条路堵死了。

## 7 · 我的弱项与补法

诚实记录，避免下次重复：

| 弱项 | 表现 | 补法 |
|---|---|---|
| 容易顺着"我的实现"读 | 只验证自己的假设 | 先假设代码是错的，找反证 |
| 上下文有限，常重新读 | 反复翻同一段 | 读一段就写进 NOTES/Review，别留在脑子里 |
| 偏向"跑通即正确" | 假绿、假数据 | 每步先问"这行日志真能证明吗" |
| 不主动查厂商参数 | 流程对、参数错 | 见 §4 |

**今天三次"假数据"教训**（都写进 [`02-开机线契约.md`](02-开机线契约.md) §10 了）：

1. `FIFO write 1536B ok` —— fn1 根本没使能，可能是假绿；
2. `fbrblk=0000` —— 读错地址返回 0，不是卡内真值；
3. `Module Network` 后无 `WiFi:` —— SD0 就绪即 `return`，整段没跑。

**它们的共同点：读到的"值"是错的，而且错得很自然。**

## 8 · 实战：用这套方法读"写不进、没回应"

现象：`vendor init` 全绿之后，消息发出去，芯片不回。

### 步骤 1 · 审判据

现在的判据是「`mem read cfm timeout`」。但 timeout 只说明**没收到回应**，
不能区分「消息没发出去」和「发出去了芯片不理」。**判据不够细。**

### 步骤 2 · 找对照物（参数！）

`aicwf_sdio_bus_txdata`（D80 分支）：

```c
buffer_cnt = aicwf_sdio_flow_ctrl_msg(sdiodev);
while ((buffer_cnt <= 0 || len > buffer_cnt * BUFFER_SIZE) && retry < 10) { ... }
if (buffer_cnt > 0 && len < buffer_cnt * BUFFER_SIZE) send_pkt(...);
else { sdio_err("tx msg fc retry fail\n"); return -1; }
```

**结论：发送前必须读流控 credit，`buffer_cnt > 0` 才允许写。**

### 步骤 3 · 读参数（长度）

```c
if ((len % SDIOWIFI_FUNC_BLOCKSIZE) != 0) {
    len = (payload_len/SDIOWIFI_FUNC_BLOCKSIZE + 1) * SDIOWIFI_FUNC_BLOCKSIZE;
}
```

**消息必须补齐到 512 整数倍，再走块模式。**

### 步骤 4 · 反例压力测试

- 若 `fc` 一直为 0 → 不是格式问题，是**芯片没在监听**（回头查 `fn0 0xF2` 之后的时序）；
- 若 `fc>0` 但补块后仍无回应 → 是**帧格式**（4B 帧头、`hdr[2]&0x7f==0x11`）。

**两条假设，日志能区分** —— 这就是合格的下一次实验。

---

## 9 · 一句话总结

> **先问"判据成立吗"，再问"别人怎么写的"，最后问"参数对不对"。**
> 顺序反了，就会一直在"我的实现哪里写错了"里打转。
