# 05 · DUO 经验给 PI（BCM43430 / CYW43438）

> **写给**：在 PI 3B 上啃 BCM43430 的人（Cursor / 未来的我）。
> **怎么用**：先读 §2 的对照表，再按 §3 逐条查——**每一条都给了"DUO 上真实现象 → 真因 → 验证手段 → 对 PI 的映射建议"**。
> **边界**：DUO 是 AIC8800D80（私有 eoc/e2a 消息），PI 是 BCM43430（SBSDIO 背板窗 + SDPCM）。
> **协议完全不同，不要照搬结构体或消息 id**；能搬的是**排查手段**和**踩坑顺序**。
> 每节标了 **[DUO 实测]** / **[推断]**，`[推断]` 的不要当成 BCM 的事实去改代码。

---

## 1 · 两条线为什么是同一类问题

| 维度 | Intel 8265（NUC，已通） | BCM43430（PI） | AIC8800D80（DUO，已通到扫描） |
|---|---|---|---|
| 上游驱动 | mainline `iwlwifi`，同一颗芯片 | mainline `brcmfmac` | **没有**，只有厂商 BSP |
| 总线 | PCIe + MMIO + MSI-X | **SDIO** | **SDIO** |
| 固件加载 | DMA 到固定地址 | 背板写 SRAM（私有窗） | 私有 IPC + patch 表（100 条写 + 14 个 cfg） |
| 主机协议 | 寄存器 + 命令队列（标准化） | SDPCM | eoc/e2a 私有消息（CRC8、流控 credit、512 B 补齐） |
| 板级时序 | 基本没有 | WL_ON、32k LPO、时钟 | GPIOA15 上电脉冲、时钟门控 |

**结论**：Intel 快，是因为它三项都不占。**PI 和 DUO 卡的地方是同一类：SDIO 上跑私有固件协议。**
所以 DUO 上耗掉的调试时间，有相当一部分对 PI 是**可复用的排查资产**。

### 1.2 两条线当前位置对照

| 阶段 | PI | DUO |
|---|---|---|
| SDIO 枚举 / F1 / 块长 / 背板窗 | ✅ | ✅ |
| 固件真正写入 | ❌ SRAM 别名写不进 | ✅ 363 KB 全写并读回验证 |
| 固件跑起来 | ❌（`csr=0x50` 是后果） | ✅ `MM_VERSION` 回 `lmac=06090101` |
| 无线电配置 | — | ✅ ME_CONFIG / ME_CHAN_CONFIG / MM_START 三 CFM |
| 扫描出真实 SSID | — | ✅ `Apple` / `Sense` / `TP-LINK_YY` |

**意思是：PI 现在卡的那一步，DUO 已经跨过去了——而且跨过去靠的不是"硬件终于听话"，是"发现是我们自己的判断错了两次"。** 这大概是本文最有用的部分。

## 2 · 六条可直接搬的排查手段

### 坑 1：返回"成功"，但数据没落地 —— 先怀疑自己的解析，不是卡

**[DUO 实测]** 第一次真写固件，日志报：

```
WiFi: stage=adid FAIL write sent=00000000
```

看着像"卡拒绝写入"。**实际写成功了。** 真因：设备回的消息里有一个 `pattern` 字段（厂商当"有效消息戳"用，固定 `0xaddede2a`），我们把它当成了 `param[0]`，于是：

- 真正的 `wstatus=0`（成功）被读成 `0xaddede2a`（失败）；
- 读寄存器时，`memaddr` 被当成寄存器值（打出来 `chip rev raw=40500000`——那其实是**地址**）。

**怎么发现的**：同一个常量 `2a de de ad` 同时出现在"读回"和"写确认"两种消息里。**一个值不可能是两个语义** ⇒ 它只能是常量 ⇒ 我们的偏移错了。

**验证手段**：把收到的**整帧**按字节打出来（我们后来加了 `payload head N of M` 和 16 字节一行），再加一行自证：`payload_fc=XXXX ind_framectrl=XXXX : match`——**payload 的第一个字节是否等于消息头里记录的帧控制**，一行定案。

**对 PI 的映射建议 [推断]**：
> SRAM 别名写入"接命令、进传输、零字节"，先用同一套办法：**在同一个上电周期内**，
> 对**已知可写且可读**的地址（不是 SRAM 别名）写一个图案、立刻读回；
> 再把"我们实际发出去的字节"与"读回来的字节"逐字节并排打出来。
> 如果连"已知可写地址"都读不回，才是真·写不通；否则问题在**帧构造/长度/模式**。

---

### 坑 2：块大小没设对，写会"接受命令但静默丢数据"

**[DUO 实测]** 我们踩过：
- `fn1 blocksize write failed / r5=00001100 (OUT_OF_RANGE)` —— 原因：**FBR 的块大小必须用 function 0 + 绝对地址 `0x110/0x111` 写，且是两个单字节写**，不能按 fn1 的相对地址算。
- 另一个：`ioex wrote=03 now=02` —— 我们写了整个字节，实际只能 `|= 0x02`（位是别人也在用的）。

**为什么值得警惕**：SDIO 上"长度/块大小不匹配"的典型症状就是**命令被接受、数据悄悄丢**，和 PI 现在描述的现象高度同构。

**对 PI 的映射建议 [推断]**：
> 检查 F1 的 block size（FBR `0x110/0x111`，**按 function 0 + 绝对地址**读写）；
> 写 SRAM 别名时，**块大小必须能整除你要写的长度**，否则改字节模式（byte mode / incr）试一次。
> 一次只改这一个变量，别同时改时钟。

---

### 坑 3：跨上电周期比较内存 —— 无效证据

**[DUO 实测]** 我曾据"重启后读回不是我们写的内容"判定"写失败"，**这是错的**：SRAM 掉电即失，重启后内容必然不同。

**规矩**：任何"写→读回"的判据，**必须在同一个上电周期内**完成。跨 reboot 的对比只能证明"这块内存现在不是那个值"，不能证明"当时没写进去"。

**对 PI 的映射建议**：同为 SRAM，同一条规矩。

---

### 坑 4：先证明"总线真的能读写"，再谈协议

**[DUO 实测]** 我们的顺序是：
1. 读厂商/器件 ID（只读）→ 证明读通路；
2. **用两种不同方式读同一段数据**（CMD52 单字节 vs CMD53 块读），**结果必须一致** → 证明读路径自证；
3. 写单字 → 立刻读回 → 证明写通路；
4. 才开始搬固件。

第 2 条是最值钱的一步：**两种路径读同一地址必须相同**，否则任何后续结论都建在沙子上。

**对 PI 的映射建议**：PI 已有背板窗读写，建议补一条**双路径一致性自证**（例如 CMD52 与 CMD53 读同一个 EROM/寄存器），把"读通路正确"钉死，再攻 SRAM 写。

---

### 坑 5：任务/函数路由 —— 不同类型的功能，响应走不同 function

**[DUO 实测]** 我们一度收不到回应，真因是 **RX 分支只处理了 fn2，没处理 fn1**（`masked=0009`）。芯片把"命令响应"和"数据"分流到不同 function，主机必须两条都轮询。

**对 PI 的映射建议 [推断]**：BCM 的 SDPCM 在 F2，但**控制类响应未必都走 F2**；确认清楚"哪个 function、哪个中断位"承载哪类消息，再谈超时。

---

### 坑 6：板级时序与"别人的现场"

**[DUO 实测]** 我们是接手 U-Boot 留下的现场，所以上电序列是：

```
GPIOA15 拉低 100 ms（断电脉冲）→ 拉高 → 延时（厂商 500 µs，Linux 侧实际更久）
→ 再发 CMD5
```

另外还有**时钟门控必须先开**（Linux 由 CCF 代劳，我们得自己写寄存器）——这一条如果漏了，表现就是"命令有去无回"。

**对 PI 的映射建议**：交接文档里已经写了「WL_ON 后等 0.5 s → 3 s」和「与 Linux `mmc1 ios` 对齐（50 MHz / 4-bit / high-speed）」。**这两条我完全同意，而且 DUO 的经验支持它**：我们也是靠"时钟先对、再上电、再探活"才过的。

## 3 · 给 PI 当前卡点的三条具体动作（按顺序，一次一条）

PI 现在的现象：**背板 `0x18000000` 正常，SRAM 别名 `0 / 0x10000000 / 0x1e000000` 写不进（R5 无错位）**。

### 动作 A：把"写失败"的判据换成"同周期写后立刻读回 + 双路径一致性"

不要用 `csr=0x50` 当判据（那是固件没起来的**后果**）。先构造一条最小判据：

```
同一次上电内：
  1) 选一个已知可写的非 SRAM 寄存器地址 → 写图案 0xA5A5_5A5A → 立刻读回
  2) 若 1 通过 → 换 SRAM 别名首地址做同样的事（单块、512 B、块模式）
  3) 若 2 失败 → 换字节模式再试一次（其它一切不变）
```

**三种结果分别指向**：① 总线写就不通（回到 SDIO 层）；② 只有 SRAM 别名不通（地址窗/模式问题）；③ 模式问题。

### 动作 B：核对 F1 的 block size 与写长度是否自洽

见坑 2。**只改这一个变量**。

### 动作 C：用 Linux 侧做一次"最小探针"

交接文档里已提到这条但没跑。DUO 这边的对等经验是：**我们最终是靠"厂商驱动的同一段流程"当参照才走出来的**——PI 有 mainline `brcmfmac`，比 DUO 条件好得多：

- 在 Linux 下用 `ftrace` / 加 printk，把**同一块板子**上"背板写 SRAM 的那几笔 CMD53"抓下来（地址、长度、块模式、fn）；
- 与我们的实现逐字段对比。

**这一步的性价比最高**：它把"猜"变成"对"。DUO 没有这个条件（没有 mainline 驱动），PI 有。

## 4 · 方法论：DUO 上真正省时间的三件事

1. **先有判据，再写代码。** 每一步都先定义"串口上出现哪一行算过"。DUO 的每一步都有对应字符串
   （`CIS manfid=c8a1:0082`、`tx fc=04`、`sentinels 6/6 ok`、`SSID="Apple"`）。
2. **先出字节，再发命令。** 关键消息都先做 `dry`：只拼包、打总长 + 前 64 字节、**不发**。
   DUO 上 `mm_start` 的结构体长度靠这个抓出"文档写 70、实际 72（尾部对齐）"。
3. **一次只改一个变量。** 时钟、模式、块大小、地址，任何两项同时改，失败就无法归因。

## 5 · 不要从 DUO 照搬的东西

| 别搬 | 原因 |
|---|---|
| 消息结构体 / 消息 id | AIC 的 eoc/e2a 与 BCM 的 SDPCM 完全不同 |
| 固件文件格式与 patch 表语义 | AIC 的 adid/patch/patch 表是私有的 |
| 补齐规则（512 B、TAIL_LEN=4） | 是 AIC 的帧格式约定 |
| 流控 credit 语义（`len < fc*1536`） | AIC 的 TASK 流控，BCM 没有对应物 |

**能搬的只有：取证手段、判据设计、变量隔离、以及"先怀疑自己"这个习惯。**

## 7 · 一句话

> **DUO 上最大的两次突破，都不是"硬件终于配合了"，而是"发现我们自己的判断错了"。**
