## 11 · 2026-10-31 10:05 补充（本次暂停点）

### 新发现

1. **控制端口已修好**（`d616e350`）：`ME_SET_CONTROL_PORT_REQ 0x1404` 发出，`0x1405` CFM 收到，
   打 `control port open (vif=0 ap=0)`。
2. **新的卡点：数据接收会突然静默**。关联成功后只上来 **2 个 beacon**，之后 `eapol poll 15000`
   是 `frames=0 data=0` —— **接收停摆**，M1 自然收不到。同一个 AP 在 eMMC Linux 上一次就通，
   所以不是 AP/固件的问题。**怀疑方向**：接收流控没闭环（可能要回 `DATA_CFM 0x12` 或写信用计数）；
   或 EAPOL 上送还有前置条件。**该调查已中断，未写任何文件。**
3. **`wififw mmreset` 会让固件进入坏状态**：之后 join 一直回 `CFM status=0x04`，重新 scan 也救不回。
   **恢复办法**：跑一次 `ksend`（写同样内核）触发 RTC 复位，约 30 秒，不需要人动手。
4. **DUO 的启动顺序 = 看卡在不在**：卡在 → SD（Blocks）；卡不在 → eMMC（厂商 Linux）。
   Linux 跑在 eMMC 上时，SD 卡是外接块设备，**可热插拔挂载**。

### 三条“改内核”路线（待决策）

| 方案 | 每轮需要人做的动作 | 前提 |
|---|---|---|
| 现状：读卡器 | 拔卡 + 插读卡器 + 插回 + 上电 = 4 次 | 无 |
| Linux 当写入器 | 拔卡 + 插回 = 2 次 | 网线（Linux 从 PC wget）+ 一个 `reset` 命令 |
| **Blocks 自己写 `boot.sd`** | **0 次** | FS 增加“按卷打开”能力（约 1 天）+ 备份/校验/回滚 |

- `reset` 命令的实现路径已确认：`KsendReboot()` 是导出符号（走 RTC 温复位），
  而 shell 现有 `reboot` 在 RISC-V 上只是 `HalCpuReboot()`（停机等人拔电）。
- 方案三的安全机制可复用 ksend 已验证的那套：写前备份 → 写 → 读回全文件 CRC → 不符则回滚 → 才 reset。

### 恢复时第一步

按 §6 的思路继续查「数据接收为什么 2 帧后静默」，起点是厂商
`aicwf_sdio.c` 的 rx 线程/信用与 `aicwf_txrxif.c`、`rwnx_rx.c` 的上送条件。

### 已真机证伪（每条都刷过卡、跑过）

| # | 假设 | 做法 | 结果 |

| 8 | 一块多帧只解第一帧 | 已实现逐帧（`aggregate in one block=02`） | 修好了，但不是主因 |

### 当前确定的事实

- 关联成功（`SM_CONNECT_IND status=0x0000`，BSSID/ch/freq 都对）；
- 控制端口消息被固件接受（收到 0x1405；注意：**该 CFM 无状态字段**，只证明被吃下）；
- 固件醒着、无待收块；**3 秒窗口里除 beacon 外没有任何数据帧上送**；
- 同一 AP，eMMC Linux 一关联就收到 M1（说明 AP 会发、固件能交）。

### 为什么停

剩下只有两条路，都不是"再猜一次"能解决：
1. **空口抓包**（第二台设备同信道 monitor）——需要额外硬件；
2. **固件内部轨迹**（逆向/调试口）——工程远大于收益。
