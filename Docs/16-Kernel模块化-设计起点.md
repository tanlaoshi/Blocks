## 1 · 原话（逐句保留，不改一字）

### 第一轮（2026-11-01）

> 系统既然叫 Blocks，想必你也知道这是积木的意思，你知道乐高的那种积木底盘吗？
> 一个大平板底座，上面全是标准的乐高插座，也就是一个一个的小圆柱体。
> 我想把 Blocks 打造成那个底座，底座之下可能有无数的硬件，但是底座之上都是统一标准的，三架构都是一样的。这是第一点。

> 第二点，现在所有的东西都编译到 Kernel，太重了，随便改一点都要重编内核，
> 我不想重蹈 linux 的覆辙，驱动挂全盘挂。
> 我想把非各架构共性的东西都拿出去，最重的就是驱动。
> 三架构比较统一的都需要 CPU，内存初始化，然后是框架类的，X64 需要 PCIE，USB 栈，
> 这一条路下去切到具体驱动，到键鼠驱动。键鼠驱动就能拿出去了。
> 通用的 PCIE 和 USB 可以留着。ARM 和 RISCV 跟 X64 不一样，但是也有 CPU 和内存。

### 第二轮（2026-11-01）

> 我想的是内核模块做成 `.mod` 文件，Kernel.elf 编制流程，核心的串口、CPU、内存、FAT 等留在 Kernel.elf，
> 具体留哪些我们从开机到鼠标指针出现一点点抽。
> 目标是把三架构各自核心的流程抽出来，也就是只要是本架构下的电脑都有的部分。

## 2 · 判定规则（v2 定稿，后面所有取舍都用它）

```
留 Kernel.elf   ⟺  本架构下【任何一台机器】都必然有的东西
做成 .mod       ⟺  只有【某些机器/某些外设】才有的东西
```

**判定三问**（对每个模块依次问，任一"是"就做成 `.mod`）：

1. 换一块同架构主板，这个东西还需要改代码吗？→ 要 = `.mod`
2. 没有它，机器还能启动到串口提示符吗？→ 能 = `.mod`
3. 它依赖的硬件地址/引脚/协议，是同架构所有机器一致的吗？→ 不一致 = `.mod`

## 3 · 从开机到鼠标指针：实际链路（代码里的真顺序）

来源：`BringUp/Kernel.c`（KernelMain）+ `BringUp/Modules.c`（三张模块表）。
`gModulesFull` 的顺序就是真机桌面路径：

| # | 阶段 | 模块 | 做什么 | 判定（留 / 走） | 依据 |
|---|---|---|---|---|---|
| 1 | EARLY | **Serial** | 串口初始化 + 日志 | **留** | 任何机器都有串口（x64 COM1 / Pi UART / Duo UART0） |
| 2 | EARLY | **PhysicalMemory** | 物理页管理 | **留** | 同架构必有 |
| 3 | EARLY | **VirtualMemory** | 页表/映射 | **留** | 同上 |
| 4 | DISPLAY | **Video** | 帧缓冲/字体/主题 | 待定 | 串口-only 机器没有（Duo 当前就无 GUI），但"本架构的电脑"都有显示能力 → **倾向留（做成可裁剪）** |
| 5 | PLATFORM | **Cpu** | HAL/定时/syscall/FPU | **留** | 同架构必有 |
| 6 | PLATFORM | **Driver** | 设备模型/块设备框架 | **留** | 框架类（不是具体驱动） |
| 7 | PLATFORM | **Smp** | 拉起 AP | 待定 | 单核机器（Duo）没有 → 但它是"框架能力"，**倾向留、运行期探测核数** |
| 8 | INPUT | **USB** | xHCI/DWC2 主机栈 | **留（栈）** / **走（类驱动）** | 你原话："通用的 PCIE 和 USB 可以留着" |
| 9 | INPUT | **HID 键鼠** | 解析报告/生成事件 | **走** → `hid.mod` | 你原话："键鼠驱动就能拿出去了" |
| 10 | SESSION | **Scheduler** | 任务/调度 | **留** | 框架 |
| 11 | SESSION | **Console** | 命令表/Shell 底座 | **留** | 框架 |
| 12 | — | **FileSystem（FAT）** | 卷/文件 | **留** | 你原话点名"FAT 等留在 Kernel.elf"；且 `.mod` 要从 FAT 读 |
| 13 | — | **Gui** | 窗口/桌面/光标 | 待定 | 指针出现靠它；但它是"会话层"不是"驱动" → **倾向先留，后续做成可裁剪服务** |
| 14 | — | **Network** | lwIP / 网卡 | 待定 | Duo 的 WiFi 属"某些机器才有" → **网卡驱动走，协议栈留** |

**鼠标指针出现的完整依赖**：`Video(帧缓冲) → Gui(桌面/光标绘制) → Input/USB(主机栈) → hid.mod(键鼠事件) → 调度(InputTask)`。

⇒ **第一块要拿出去的积木，就是第 9 行的 HID**。

## 4 · `.mod` 的形态（v2 初稿）

### 4.1 文件与加载

```
卡上：  BLOCKS:MODULES/HID.MOD
内核：  Services/FileSystem（已有，FAT 留在内核）
        Core/Elf（已有，可解析 ELF 段）
        Module Loader（新增，运行期加载）
```

**格式**：ELF（复用现有 `Core/Elf` 的解析与重定位），加一个 `.blocks` 段声明契约版本/名称/依赖。

### 4.2 插座契约（草案 v0）

```c
typedef struct BLOCKS_DRIVER {
    UINT32 ApiVersion;                 /* 插座版本；不匹配就拒绝加载 */
    const char *Name;                  /* "hid" */
    int  (*Probe)(BLOCKS_DEVICE *Dev); /* 认领设备；返回 0 = 我管 */
    int  (*Start)(BLOCKS_DEVICE *Dev);
    int  (*Stop)(BLOCKS_DEVICE *Dev);
    int  (*Read)(BLOCKS_DEVICE *Dev, void *Buf, UINT32 Len);
    int  (*Write)(BLOCKS_DEVICE *Dev, const void *Buf, UINT32 Len);
    int  (*Ioctl)(BLOCKS_DEVICE *Dev, UINT32 Cmd, void *Arg);
} BLOCKS_DRIVER;
```

**内核只认这张表**；`BLOCKS_DEVICE` 是内核给的"设备描述"（资源：MMIO 窗口、IRQ、类）。

### 4.3 驱动从哪来、怎么发现

```
枚举（内核，框架）→ 生成 BLOCKS_DEVICE 列表
  x64 ：PCIe 枚举 → xHCI → 端口
  Pi  ：DT/platform → DWC2
  Duo ：固定地址/platform → DWC2
       ↓
模块加载器：对每个"未被认领"的设备，依次问各个 .mod 的 Probe
       ↓
被认领 → Start → 该设备活了；没有任何模块认领 → 设备列表里标"无驱动"（不影响启动）
```

**这一步就是"底座 + 插座"的实体化**：设备由底座枚举，驱动是插上去的。

- B. 网卡（Duo WiFi 那摊，最复杂，不适合当第一块）

### Q3 隔离做到哪一步（"驱动挂全盘挂"的核心）
- A. 只做**契约**（驱动自己不能崩；崩了还是全挂）
- B. 模块级**异常捕获**（x64 可用 #PF/#GP 钩子；ARM/RISCV 用 trap），出错卸载模块

**我倾向：先 A 打通流程 → 紧接着 B；C 留作长期。你定优先级。**

### Q4 Video / Gui / Network 的归属
我倾向：**Video 留（可裁剪）、Gui 留（先不动，属会话层）、Network 的协议栈留、网卡驱动走**。
**你点头或否决。**

## 7 · 术语

| 词 | 含义 |
|---|---|
| **底座（baseplate）** | Kernel.elf：CPU/内存/中断/对象/设备模型/驱动契约/FS/调度 |
| **插座（socket）** | §4.2 的驱动契约（接口 + 生命周期 + 版本） |
| **积木块（block）** | 一个 `.mod` 文件（HID、网卡、存储…） |
| **底座之下** | `HAL/<Arch>/Board/<board>/**` 的板级实现 |
| **插座之上** | 统一标准：设备模型、驱动契约、文件系统、调度、会话层 |
