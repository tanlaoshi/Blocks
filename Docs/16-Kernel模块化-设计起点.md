## 1 · 原话（2026-11-01，逐句保留）

> 系统既然叫 Blocks，想必你也知道这是积木的意思，你知道乐高的那种积木底盘吗？
> 一个大平板底座，上面全是标准的乐高插座，也就是一个一个的小圆柱体。
> 我想把 Blocks 打造成那个底座，底座之下可能有无数的硬件，但是底座之上都是统一标准的，三架构都是一样的。这是第一点。

> 第二点，现在所有的东西都编译到 Kernel，太重了，随便改一点都要重编内核，
> 我不想重蹈 linux 的覆辙，驱动挂全盘挂。
> 我想把非各架构共性的东西都拿出去，最重的就是驱动。
> 三架构比较统一的都需要 CPU，内存初始化，然后是框架类的，X64 需要 PCIE，USB 栈，
> 这一条路下去切到具体驱动，到键鼠驱动。键鼠驱动就能拿出去了。
> 通用的 PCIE 和 USB 可以留着。ARM 和 RISCV 跟 X64 不一样，但是也有 CPU 和内存。
> 以上原话你先记下来，写个文档，我们会沟通很多。架构设计在沟通中打磨出来。

## 2 · 我理解到的诉求（拆成可讨论的命题）

| # | 命题 | 我的理解 |
|---|---|---|
| P1 | **底座隐喻** | Blocks = 标准插座面板。**插座之上必须完全一致**（三架构同一套接口/语义），插座之下随便什么硅片 |
| P2 | **插座是接口，不是实现** | 插座不是"某个驱动的代码"，而是"一个位置 + 一套契约"。插什么由底座之下决定 |
| P3 | **驱动不常驻内核** | 改一个驱动不该重编整个内核；驱动出问题不该让系统全挂 |
| P4 | **内核只留共性** | CPU 初始化、内存初始化、框架类（调度/对象/设备模型/文件系统）留在内核 |
| P5 | **X64 的 PCIE/USB 栈留在内核** | 因为它是"框架"；具体设备驱动（键鼠）才拿出去 |
| P6 | **ARM/RISCV 的差异** | 没有 PCIe，但有 CPU/内存；底座对它们同样成立 |

**一句话**：*内核 = 底座 + 插座标准；驱动 = 插上去的积木块。*

## 3 · 现状（事实，不是评价）

```
Kernel/
  BringUp/     9 个 .c    启动段：Entry/Handoff（分 arch）+ KernelMain + Initialize 模块表
  Core/       60 个 .c    调度/进程/内存/文件系统核心/syscall/ELF/设备
  Services/  213 个 .c    GUI/Shell/FS/网络/Tasks/Store…
  Library/    33 个 .c
  HAL/       484 个 .c    X64 / Arm64 / RiscV / Virtio / Common
  User/       49 个 .c    用户态示例
  ThirdParty/425 个 .c    lwIP / FreeType 等
```

**构建方式**：`Kernel/Makefile` 用 `$(wildcard …)` **把上面这些全部**编成一个 `Kernel.elf`，
链接期一次成型。所以：

- 改一行驱动 → 全量重编 → 生成新 ELF → 整机替换（Duo 上实测 2.3 MB 镜像，串口部署约 3 分钟）；
- 驱动里一个野指针 = 内核崩 = **全盘挂**（正是你说的 Linux 覆辙）；
- 三架构差异目前靠 `HAL/<Arch>/` 目录 + `BOARD_DIR` 区分，**但最终链接成同一个 ELF，没有运行期边界**。

**结论**：现在是"一个大 ELF"，不是"底座 + 积木"。

## 4 · 已有的"缝"（不用从零开始）

| 机制 | 位置 | 现状 | 可复用性 |
|---|---|---|---|
| **开机模块表** | `BringUp/Initialize/{Cpu,Serial,Usb,Video}.c` | 已有 4 个模块，按顺序初始化 | ★★★ 这就是"插座"的雏形 |
| **驱动回调槽** | `HAL/Common/Slots/{DriverFile,DriverSched}.c` | 驱动注册回调，内核调用 | ★★★ 已有"接口 + 实现分离"的形态 |
| **板级目录** | `HAL/<Arch>/Board/<board>/**` | 每板一套实现（如 `milk-v-duo-s/Sdhci/**`） | ★★ 已经是"底座之下"的样子 |
| **弱符号注册** | 如 `SdhciWifiJoin` / `Ksend` | 板级实现，壳命令弱引用 | ★★ 证明"可缺省"能工作，但目前仍是**链接期**决定 |
| **文件系统 + 串口传输** | `Services/FileSystem` + `Ksend` | 已能读写卡上文件、能从串口收文件 | ★★★ 运行期加载模块的**投送通道已经有了** |

**关键判断**：我们不需要发明"模块化"这件事，只需要把已有三条缝（模块表 / 回调槽 / 板级目录）
**升级成有契约、可裁剪、可隔离的标准**。

## 5 · 需要你拍板的问题（每一轮讨论收敛几条）

### Q1 插座的"形状"是什么？
- A. **函数指针表**（C 结构体 + 版本号）—— 最简单，和现有 Slots 一致
- B. **固定 ABI 的 ELF 模块**（导出 `ModuleInit(BlockApi*)`）—— 可运行期加载
- C. 两者皆有：编译期用 A，运行期用 B

**我的倾向**：A 先做（零风险），B 作为第二步。**待你定。**

### Q2 "拿出去"是拿成什么？
- A. 编译期可裁剪（同一次构建，开关决定编不编）
- B. 运行期可加载（独立文件，卡上放着，用时载入）
- C. 独立进程（有地址空间隔离）

**我的倾向**：先 A 再 B；C 是终极形态但代价最高（要进程间通信 + 授权模型）。**待你定。**

### Q3 底座之上"统一标准"具体包含哪几层？
我的候选分层（自下而上）：

```
① CPU/内存初始化      （三架构各自实现，接口统一）
② 中断/定时/原子       （统一）
③ 对象/内存分配/字符串 （统一）
④ 设备模型：设备树/枚举/资源（统一）
⑤ 驱动契约：Probe/Start/Stop/Read/Write/IOCTL（统一）  ← 插座
⑥ 文件系统/调度/进程   （统一，与驱动无关）
```

**问**：⑤ 的契约你想覆盖到多细？（只覆盖块设备/字符设备？还是也要网络/显示/输入？）

### Q4 X64 的 PCIe/USB 栈"留着"的边界在哪？
- PCIe 枚举/配置空间 → 内核（框架）
- xHCI 主机控制器 → 内核（框架）
- **HID 键鼠解析 → 模块**（你说的"键鼠驱动能拿出去"）

**问**：USB 类驱动（HID/存储/网卡）是不是都算"插上去的积木"？我倾向**是**。

### Q5 ARM/RISCV 没有 PCIe，底座怎么表达差异？
候选：底座提供"总线枚举器"抽象（x64 是 PCIe、Pi 是 platform/DT、Duo 是 platform/固定地址），
**上层驱动只认"设备 + 资源"，不认总线**。**问**：这个抽象够不够？

### Q6 "驱动挂了不能全盘挂"要做到什么程度？
- A. 只做**错误返回**（驱动自己不能崩，崩了还是全挂）
- B. **模块级异常捕获**（驱动跑在内核里，但出错能卸载）
- C. **地址空间隔离**（驱动进独立地址空间，崩溃只影响自己）

**这是"Linux 覆辙"的核心。** 我的判断：**A 是最低要求，B 是三架构可行的中间态，C 是长期目标。**
**待你定优先级。**

### Q7 模块从哪来、怎么加载？
我们已经有 `Services/FileSystem` + `Ksend`（串口投送）→ 可以直接从 `BLOCKS:` 卷加载 `.mod`。
**问**：模块文件格式用 ELF（现有 `Core/Elf` 可复用）还是自定义段格式？

## 6 · 三个候选方案（先摆出来，不急着选）

### 方案 A：静态模块表（编译期可裁剪）
```
底座（内核）：CPU/内存/中断/对象/设备模型/驱动契约/FS/调度
模块（同一次构建，可开关）：HID、存储类、网卡类…
```
- 优点：改动最小，和现有模块表一脉相承；今天就能开始
- 缺点：**达不到"改驱动不重编内核"**（只是把文件拆开、开关控制）
- 适合：作为第一步，先把**契约**定下来

### 方案 B：可加载 ELF 模块（运行期）
```
底座（内核）：同上 + 模块加载器 + 符号解析
模块（卡上 .mod 文件）：按需加载，可卸载
```
- 优点：真正满足 P3；驱动崩溃可卸载（若配合 B/C 隔离）
- 缺点：需要 ABI 稳定性、重定位、符号表、内存管理配合
- 我们已有的基础：`Core/Elf`（解析）+ `FileSystem`（读取）+ `Ksend`（投送）

### 方案 C：混合（我倾向的路）
```
第一阶段（A）：把契约定死，驱动搬进 modules/ 目录，编译期可裁剪 —— 验证"插座"形状
第二阶段（B）：加载器 + 运行期加载 —— 验证"改驱动不重编内核"
第三阶段（C）：隔离（先模块级异常捕获，再考虑地址空间）
```

## 7 · 建议的最小实验（一周内可验证）

**目标**：用**键鼠驱动**做第一个"拿出去的积木"，因为：
- 它是最典型的"具体驱动"（P5 里你点名的）；
- X64 走 USB HID、Pi 走 DWC2、Duo 走 USB——**三架构都能验证同一套契约**；
- 坏了只丢输入，不影响启动，**风险最低**。

**做法（方案 A 的切片）**：

1. 定义 `BlocksDriverApi`（v0）：`Probe / Start / Stop / Read / Write / Ioctl` + 版本号 + 名称；
2. 把当前 HID 键鼠实现改成"注册到插座"，而不是被内核直接调用；
3. 构建开关：`HID=0/1`，验证"不编它，内核照样启动、只是没键鼠"；
4. 判据：**同一份内核 + 打开/关闭开关，两次启动都成功**，且日志里能看到插座上有没有设备。

**这一步做完，我们就有了"插座"的真实形状**，再谈加载器和隔离才有依据。

## 8 · 术语（先统一叫法，避免后面各说各话）

| 词 | 含义 |
|---|---|
| **底座（baseplate）** | 内核里与硬件无关的那部分 + 板级适配层 |
| **插座（socket）** | 一套固定契约（接口 + 语义 + 生命周期），驱动插在这里 |
| **积木块（block）** | 一个具体驱动/服务模块 |
| **底座之下** | 各架构/各板子的实现（CPU、总线、中断控制器…） |
| **插座之上** | 统一标准：对象、设备模型、文件系统、调度、驱动契约 |
