# 18 · 底座之上下 —— Blocks 的稳定内核设计

> 目标（你的原话）：**最低目标是 Kernel 趋于稳定，新增功能和老功能修改，不动 kernel。**
> 这篇回答两件事：**板子之上怎么设计、板子之下怎么设计**，以及一个可能和你预期不同的结论：
> **内核不静的根因不是"接口在变"，而是"接入点在变"。**

---

## 1 · 先说结论

### 1.1 三条判断

1. **"不动 kernel" 不能靠纪律，要靠结构**：只要还存在"加功能必须改某个内核文件"的接入点，纪律一定被突破。
2. **稳定的不是内核代码，而是底座上那层契约**：内核可以换实现，契约不能换。
3. **接入点比抽象层更值得先消灭**：我们的数据（§2）显示，内核里改动最频繁的是 Makefile 和模块表，不是设备模型。

### 1.2 一句话设计

> **底座 = 一段"不会长大的内核" + 三张冻结的契约面。**
> 之上和之下都**只通过契约**接触底座，且**加东西只加文件、不改文件**。

---

## 2 · 数据诊断：内核为什么不静（近 300 次提交）

| 文件 | 改动次数 | 行数 | 性质 |
|---|---:|---:|---|
| `Kernel/Makefile` | **23** | — | **接入点**（每加一个 Services 子目录要补一行 wildcard） |
| `Kernel/build.sh` | **17** | — | **接入点**（构建编排） |
| `Kernel/BringUp/Modules.c` | **16** | 184 | **接入点**（每加一个模块要加表项） |
| `Kernel/Services/Shell/Commands/Wifi.c` | 16 | 551 | 业务（还超了 500 行上限） |
| `Kernel/HAL/RiscV/.../WifiFw.c` | 15 | — | 板级驱动 |
| `Kernel/Include/Hal/Hal.h` | 11 | 195 | **契约** |
| `Kernel/Services/Shell/Commands/Commands.c` | 8 | 41 | 接入点（已很薄） |
| `Kernel/Include/Driver/Driver.h` | **4** | 99 | **契约（最稳定）** |
| `Kernel/Include/Core/Device.h` | **3** | 114 | **契约（最稳定）** |

**读出来的三件事**：

1. **契约是仓库里最稳定的东西**（Device.h 3 次、Driver.h 4 次）。
   ⇒ 我们不需要发明新抽象，**已有的插座契约经住了考验**。
2. **接入点才是噪音源**（Makefile 23、build.sh 17、Modules.c 16）。
   ⇒ 每加一个功能就要改内核的"登记簿"，这就是"改一点都要动内核"的**真身**。
3. **内核核心区改动占比不低**（近 300 次提交里核心区文件被改 1126 次，服务/板级 2637 次）。
   ⇒ 目标不是把 1126 降到 0，而是**把"登记簿类"改动降到 0**。

## 3 · 板子之下（硬件面）：把"硅片"变成"设备"

### 3.1 只做六件事

| # | 职责 | 三架构差异 | 统一产物 |
|---|---|---|---|
| B1 | **启动交接**：解析 bootloader 给的东西 | x64: UEFI 表；ARM/RISCV: DTB 指针 | `BOOT_HANDOFF`（内存图/帧缓冲/DTB/RSDP） |
| B2 | **CPU 核心**：异常/中断/定时/MMU/SMP | 完全不同的指令与寄存器 | 统一 `Hal*` 接口 |
| B3 | **总线枚举**：把设备找出来 | PCIe / DTB-platform / fixed | `DEVICE_NODE` 树 |
| B4 | **引导必需驱动**：能读到模块文件 | AHCI/NVMe / SDHCI / virtio-blk | 一个 `BLOCK` 设备 |
| B5 | **控制台**：最早能说话 | COM1 / PL011 / 16550 | `gConsole` |
| B6 | **固件服务**（可选）：UEFI runtime、Pi mailbox | 各自实现 | 具名接口（无则空实现） |

### 3.2 板子之下的三条禁令

1. **不得向上暴露寄存器/引脚/地址**：上层只看到"设备 + 资源（MMIO 窗口、IRQ、DMA）"。
2. **不得决定策略**：不决定"用哪个驱动"、"要不要启动 GUI"，只提供事实。
3. **不得被上层 include**：`HAL/<Arch>/Board/**` 只被本架构 HAL 内部引用。

### 3.3 一条重要判断：引导必需驱动留在核内

`B4` 的驱动（能读到模块文件的那一个）**必须留在 Kernel.elf 里**，
否则"模块放在盘上"就变成鸡生蛋问题。

**这就是"哪些驱动留内核"的唯一标准**：**读完它才能开始加载模块**。
其余驱动（显示、输入、网卡、声卡）全部出核。

## 4 · 底座（Kernel.elf）：只留机制，不留业务

### 4.1 内核收口清单（10 项，不再增加）

```
K1 启动交接与自检        K6 设备模型 + 驱动宿主（Discover/Match/Bind）
K2 内存：物理 + 虚拟      K7 模块加载器（ELF + 重定位 + 契约校验）
K3 对象/分配/字符串       K8 文件系统（FAT，模块从这读）
K4 异常/中断/定时         K9 调度/进程/syscall
K5 控制台/日志            K10 IPC/事件（服务与驱动通信）
```

**判定"该不该进内核"的两问**：

- 没有它，还能加载第一个模块吗？→ 不能，则留。
- 换一个应用/驱动，它需要改吗？→ 需要，则出核。

### 4.2 三张契约面（真正要冻结的东西）

```
        ┌──────────── 之上：驱动 .mod / 服务 .mod / 应用 ELF ────────────┐
        │                                                                │
   契约面② 服务面（syscall + 对象 API）        契约面① 驱动面（BLOCKS_DRIVER）
        │                                                                │
        └──────────────────────  底座 Kernel.elf  ──────────────────────┘
                                   ↑
                         契约面③ 平台面（HAL：BOOT_HANDOFF / Hal* / DEVICE_NODE）
                                   ↓
                        之下：各架构/各板子的实现
```

| 契约面 | 给谁 | 现状 | 要做的事 |
|---|---|---|---|
| ① **驱动面** | 驱动 `.mod` | **已有**（`DRIVER`/`DRIVER_MATCH`/`DEVICE_NODE`，99+114 行，改得最少） | 把注册来源从静态改成加载器 |
| ② **服务面** | 服务 `.mod`、应用 | **弱**：服务现在直接调用内核函数（`gConsole`、`Scheduler*`、`FileSystem*`…） | 定义一层薄的、可版本化的对象 API（见 §5.3） |
| ③ **平台面** | 本架构实现 | 已有（`Hal*`），但 `HalDeviceEnumerate` 是枚举钩子 | 保留，`Discover` 阶段编排它 |

**关键洞察**：① 已经稳了，③ 也基本稳，**缺的是 ②** ——
这就是为什么"改一点内核就要动"：服务直接捏着内核的全局对象。

### 4.3 契约的三条冻结规则

1. **只增不改**：字段只能追加到结构体末尾；删/改字段 = 主版本升级。
2. **带尺寸握手**：每个契约结构第一个字段是 `Size`，第二是 `Version`；内核按 `Size` 判断调用方认识的字段范围。
3. **能力查询代替裸权限**：服务通过 `Api->Query(BlockCapability)` 询问能力，而不是直接读全局变量。

## 5 · 板子之上：两个生态，三种形态

### 5.1 形态

| 形态 | 例子 | 运行位置 | 隔离 | 何时可用 |
|---|---|---|---|---|
| **驱动 .mod** | HID、显示、网卡、声卡 | 内核空间（第一版） | 无（靠契约） | 本设计 |
| **服务 .mod** | GUI 合成、Shell、网络栈、设置 | 内核空间 → 以后用户态 | 无 → 有 | 本设计后期 |
| **应用 ELF** | 编辑器、文件管理器 | 用户态（已有 `Core/Elf` + `User/`） | 有 | 已有基础 |

### 5.2 成熟度阶梯（明确我们在第几级）

```
L0  全静态链接（今天）：加功能 = 改 Makefile + Modules.c + 驱动静态注册
L1  接入点消灭：加功能 = 只加文件；内核只认"自动收集到的表"
L2  驱动出核：驱动 = .mod；删文件不影响启动，只是没该设备
L3  服务出核：服务 = .mod（仍内核空间）；内核不再 include Services
L4  服务进用户态：服务 = 进程；崩溃只死一个服务
```

**建议目标**：这一轮做到 **L2**，设计上为 L3/L4 留好接口（不实现）。

### 5.3 服务面契约草案（这是缺口，必须补）

```c
typedef struct BLOCKS_SERVICE_API {
    UINT32 Size;
    UINT32 Version;

    /* 对象：文件/目录/流/窗口/事件 */
    int (*Open)(const char *Path, UINT32 Flags, BLOCKS_OBJECT **Out);
    int (*Read)(BLOCKS_OBJECT *Obj, void *Buf, UINTN Len, UINTN *Out);
    int (*Write)(BLOCKS_OBJECT *Obj, const void *Buf, UINTN Len, UINTN *Out);
    int (*Close)(BLOCKS_OBJECT *Obj);

    /* 事件与时间 */
    UINT64 (*Now)(void);
    int (*WaitEvent)(BLOCKS_EVENT *Ev, UINT32 TimeoutMs);

    /* 控制台/日志（只读能力） */
    void (*Log)(const char *Text);

    /* 能力查询（替代直接摸全局对象） */
    int (*Query)(UINT32 Capability, void *Out, UINTN Len);
} BLOCKS_SERVICE_API;
```

**注意**：这层薄得能一眼看完 —— 这就是目标。**服务看到的世界越小，内核越稳。**

## 6 · 三条铁律 + CI 守护

### 铁律 1：新增功能/驱动/服务 = 只加文件，不改内核既有文件

具体到接入点：

| 接入点 | 现在 | 改成 |
|---|---|---|
| `Kernel/Makefile` 的 `SERVICES_SRCS += wildcard Services/xxx/*.c`（每加一个子目录补一行） | 手工维护（改过 23 次） | `$(shell find Services -name '*.c')` + 显式排除表（`RoundRobin.c`、`Bitmap.c` 等） |
| `BringUp/Modules.c` 模块表 | 手工加表项（改过 16 次） | **自注册段**：模块用宏声明 `BLOCKS_MODULE(name, init, order)`，链接器收集到 `.blocks_modules` 段 |
| 驱动注册（各 `XxxInit` 里 `DriverRegister`） | 每个驱动一个 Init，且要有人调用 | 同上自注册段 + `Discover` 阶段统一扫描 |
| Shell 命令表 | 已很薄（41 行） | 保持，命令自注册 |

### 铁律 2：契约只增不改（§4.3 三条）

### 铁律 3：内核不得 include Services/**

```
允许方向：Services → Kernel/Core|Include    ✔
禁止方向：Kernel/** → Services/**            ✘
```

### CI 守护（可立即实现，几十行脚本）

```
对每个 PR：
  统计改动的"受保护路径"（Kernel/Core, Kernel/BringUp, Kernel/HAL/Common, Kernel/Include）
  若 >0 且提交信息无 [ADR] 标记 → 打警告/拒绝合并
  统计 Kernel/Makefile 与 Modules.c 的改动 → 单独高亮（接入点回归）
```

**这条 CI 比任何文档都管用**：它把"内核变更预算"变成可执行的数字。

## 7 · 落地路线（先消灭接入点，再谈模块化）

| 阶段 | 内容 | 为什么这个顺序 | 判据 |
|---|---|---|---|
| **P0** | 构建自动收集（`find` + 排除表）、模块自注册段、命令自注册 | **收益最大、风险最低**：这几处正是改动最频繁的"登记簿" | 新增一个 Services 子目录/模块/命令，**Makefile 与 Modules.c 零改动**，构建通过 |
| **P1** | `Discover` 阶段独立（把枚举从 `DriverInitialize` 抽出） | 为按设备加载铺路 | x64 行为完全不变，多一行设备清单 |
| **P2** | 驱动注册来源改为自注册段（仍在核内） | 验证"驱动不再被点名调用" | 删掉某个驱动文件，构建通过、启动正常、设备标"无驱动" |
| **P3** | 模块加载器 + `.mod`（先 `hello.mod`） | 契约面①已稳，可以试 | 串口出现模块输出；删文件不影响启动 |
| **P4** | HID → `hid.mod`（第一块积木） | 低风险、可感知 | 删/放 `HID.MOD` → 鼠标不动/恢复 |
| **P5** | 服务面契约（§5.3）落地，服务改为只调 `Api` | 补上缺口面 | `Kernel/**` 不再 include `Services/**`（CI 检查） |

**关键**：**P0 是这一整条路的"地基"**，而且它不需要动任何架构代码。
做完 P0，"改一点就动内核"的现象就已经消失了一大半。

## 8 · 反例与边界（这套设计什么时候不成立）

| 场景 | 应该怎么做 |
|---|---|
| 驱动需要极低延迟（如网卡收包零拷贝） | 契约里给"共享内存环"，不要让驱动直接操作内核结构 |
| 驱动需要和中断/调度深度耦合 | 说明抽象错了：应该是内核提供"中断服务回调"能力，而不是驱动自己挂 IDT |
| 模块 ABI 演化太频繁 | 说明契约粒度太细：合并成更高层的少数入口 |
| 内核 bug 导致全挂 | 模块化解决不了 —— 这是"内核要小而正确"的问题（§4.1 收口） |
| 单核小设备（Duo 32MB）吃不消模块机制 | 保留 `MODULES=0` 单 ELF 构建（已有 ADR-6） |

**一句提醒**：模块化降低的是"改动的耦合度"，**不是**"内核的复杂度"。
内核必须靠 §4.1 那 10 项收口来保持简单，否则只是把复杂搬了个位置。

## 9 · 怎么判断"内核真的稳了"（度量，而非感觉）

| 指标 | 目标 | 怎么测 |
|---|---|---|
| **内核变更预算** | 新增功能 / 修改功能 = **0 行** `Kernel/Core|BringUp|Include` 改动 | CI 统计受保护路径 diff |
| **接入点改动** | `Makefile` / `Modules.c` = **0 次/月** | CI 单独统计 |
| **契约稳定性** | `Device.h`/`Driver.h`/`BlocksApi.h` 主版本 12 个月不变 | git log |
| **无驱动降级** | 删任意一个 `.mod`，系统仍能启动到 `Blocks>` | 自动化：逐个删、逐个启动 |
| **内核规模** | `Kernel/Core` + `BringUp` 总行数不增长（只减不增） | 每次提交统计 |

**其中"内核规模只减不增"是最硬的约束** —— 它逼着所有新东西去之上。

## 10 · 一页总结（给未来的自己）

```
底座之下：六件事（交接/CPU/总线/引导驱动/控制台/固件），只产事实，不做策略。
底  座  ：十项机制 + 三张契约面；不许长大。
底座之上：驱动 .mod、服务 .mod、应用 ELF；只认契约，不认识内核。

铁律     ：加东西只加文件；契约只增不改；内核不许 include 服务业。
守护     ：CI 统计"受保护路径"的 diff，接入点单列。
度量     ：内核变更预算 = 0；内核规模只减不增。
```

> **乐高底板之所以能让人随便搭，不是因为它"抽象得好"，
> 是因为它把"接口"和"我该长什么样"定死了，并且**永不变**。**
> 我们缺的从来不是抽象能力，而是**把契约定死之后不再动它**。
