# 19 · X64 模块化：设备发现与模块加载

> 蓝本：[`18`](18-底座之上下-稳定内核设计.md)（底座之上下）。本篇只回答 X64 这一条线：
> **UEFI 阶段能不能拿到"这台机器有哪些非热插拔设备"，据此决定加载哪些 `.mod`。**

---

## 0 · 一句话答案

**能，而且我们已经在用** —— 引导器 `Boot/BootPkg/FillXhci.c` 里就是
`gBS->LocateHandleBuffer(ByProtocol, &gEfiPciIoProtocolGuid, …)` 找 xHCI。
把它从"只找 xHCI"扩展成"导出全部 PCI 设备的快照"，就得到了你要的设备清单。

**但有一个必须区分的概念**（§4）：**"非热插拔"不等于"全部设备"** ——
USB 键鼠本身是热插拔的，静态清单只能告诉你"有没有 USB 主控"。

---

## 1 · UEFI 阶段能枚举到什么（能力清单）

| 来源 | 能拿到 | 对我们的用途 | 现状 |
|---|---|---|---|
| **EFI_PCI_IO_PROTOCOL**（ByProtocol 句柄枚举） | 每个 PCI 功能的段/总线/设备/功能号、Vendor/Device、Class/Subclass/ProgIf、**已分配好的 BAR**、ROM | **主清单**：显卡、存储控制器、USB 主控、网卡、音频 | ✅ 已在 `FillXhci.c` 用到 |
| **EFI_DEVICE_PATH** | 设备路径（可读文本），能看出"这是哪个控制器下的什么" | 调试打印/人类可读 | 未用 |
| **ACPI 配置表指针（RSDP）** | RSDP 地址（`gEfiAcpiTableGuid`） | 内核解析 MADT/DMAR/MCFG | ✅ 已在 `FillRsdp.c` 用到 |
| **EFI_BLOCK_IO / EFI_SIMPLE_FILE_SYSTEM** | 固件认得的块设备与卷 | 交叉校验我们的块设备枚举 | 未用 |
| **EFI_SIMPLE_TEXT_INPUT / EFI_SIMPLE_POINTER** | 固件认得的键盘/指针（PS2 类） | 判断"有没有传统键鼠"，辅助调试 | 未用 |
| **EFI_GRAPHICS_OUTPUT** | GOP 帧缓冲 | 显示初始化（已用，handoff 里有 FB 信息） | ✅ 已用 |

**结论**：**PCI 设备可以完整拿到**（含固件已分配的 BAR），**ACPI 表指针也能拿到**。
ACPI 命名空间里的"平台设备"（EC、I2C、GPIO、电池、电源按钮）**不能**直接从 UEFI 协议拿到，
要么解析 AML（DSDT），要么先用"够用的子集"。

---

## 2 · 内核自己扫能拿到什么（现状）

| 项 | 现状 | 位置 |
|---|---|---|
| PCI 扫描 | 真扫：256 总线 × 32 设备 × 8 功能，走 **0xCF8/0xCFC**（IO 端口方式） | `HAL/X64/PCIe/PCIe.c:12`、`HAL/X64/DeviceEnum/DeviceEnum.c:131` |
| 设备节点 | `DEVICE_NODE`：Bus/Vendor/Device/Class/Subclass/ProgIf/PciBus/Dev/Fn/**Bar[6]/BarSize[6]/Irq/IrqMode** | `Include/Core/Device.h` |
| 驱动匹配 | `DRIVER_MATCH.Pci`（Vendor/Device/Class/Subclass/ProgIf + 掩码） | `Include/Driver/Driver.h` |
| ACPI | 只用了 MADT（CPU/IOAPIC）、DMAR、复位/关机；**没有 MCFG/ECAM，没有 AML** | `HAL/X64/Acpi/` |
| 引导交接 | 内存图、FB、GOP、磁盘 GUID、**RSDP**；**没有设备清单** | `Include/Core/BootHandoff.h` |

**⇒ 内核侧已经具备"扫出 PCI 设备并匹配驱动"的全部要素**，只差两件事：
① 设备清单没有从 UEFI 快照来（现在靠自己扫）；② 没有模块加载器。

---

## 3 · 两条路对比（UEFI 快照 vs 内核自扫）

| 维度 | UEFI 快照（引导器导出） | 内核自扫（0xCF8） |
|---|---|---|
| 覆盖 | 固件已枚举的 PCI 功能（**含多 segment**） | 只覆盖 **segment 0**（0xCF8 只到默认总线） |
| BAR | 固件已分配，直接可用 | 要自己分配或读固件留下的值（当前靠固件） |
| 依赖 | 依赖引导器配套（Boot 与 Kernel 同批构建） | **零依赖**，QEMU `-kernel` 直启也能用 |
| ACPI 能力 | 只能拿 RSDP 指针 | 同左（要 AML 才有平台设备） |
| 调试价值 | 可以做"固件看到的 vs 我们看到的"交叉校验 | 单一来源，无法交叉验证 |

**结论**：**两条都要，UEFI 快照优先、内核自扫兜底** —— 这不是妥协，而是：
- 主线 NUC 用快照（快、含多 segment、BAR 现成）；
- QEMU 直启 / 老引导器自动回退自扫；
- 两者不一致时**打印差异**，这是最好的 bug 发现器。

---

## 4 · 关键澄清：非热插拔 ≠ 全部设备

你要的是"知道该加载哪些模块"。设备必须分两类，加载策略不同：

| 类别 | 例子 | 什么时候知道 | 模块加载时机 |
|---|---|---|---|
| **静态**（启动时就在） | 显卡、SATA/NVMe 控制器、USB 主控、有线网卡、音频 | **启动时**（UEFI 快照/PCI 扫描） | **启动期**按清单加载 |
| **动态**（运行期出现） | **USB 键鼠**、U 盘、SD 卡、可热插拔 PCIe | 设备**插上时** | **运行期**按类加载 |

**这是本设计里最容易搞错的一点**：

> 静态清单能告诉我们"机器上有 xHCI 控制器" ⇒ 加载 `usb-host.mod`；
> 但**键鼠要在 xHCI 跑起来、枚举到端口之后才知道** ⇒ 那时才加载 `hid.mod`。

所以模块加载器要支持**两个入口**：

```
启动期：device list（静态）→ 按 class 匹配 → 加载
运行期：驱动/总线报告新设备 → 按 class 匹配 → 加载
```

**好消息**：`DRIVER.Probe` 本来就是"有设备则返回 0"，天然适配两次调用。

## 5 · 目标架构（X64 这条线）

```
┌─ UEFI（BootX64.EFI）───────────────────────────────┐
│ 已有：内存图 / GOP / RSDP / xHCI 基址                │
│ 新增：**设备快照**（PCI：段/总线/设备/功能/VID/DID/  │
│        Class/Rev/BAR[6]）→ 写进 BOOT_HANDOFF         │
└──────────────────────┬──────────────────────────────┘
                       │ ExitBootServices
┌──────────────────────▼──────────────────────────────┐
│ 内核 Discover（Core，三架构共用）                     │
│ ① 有快照 → 用快照建设备树；否则 → HalBusEnumerate()   │
│ ② 打印清单：bus vid:did class 有无驱动               │
│ ③ 对每个设备：查已加载模块 → 匹配 → Probe/Bind        │
│ ④ 未匹配 → 去 BLOCKS:MODULES/ 找 <class>.MOD         │
│ ⑤ 仍无 → 标记"无驱动"（不影响启动）                   │
└──────────────────────┬──────────────────────────────┘
                       │ 运行期
        总线/驱动报告新设备（如 xHCI 枚举到键鼠）
                       ↓
              同样走 ③④（动态加载）
```

---

## 6 · 接口改动（三处，都很小）

### 6.1 `BOOT_HANDOFF` 加"版本 + 设备快照"

**现状问题**：`BOOT_HANDOFF` 没有版本/尺寸字段，加字段后旧引导器 + 新内核会读越界。

```c
/* 追加到结构体末尾（不动已有字段） */
typedef struct {
    UINT16 Segment;
    UINT8  Bus, Device, Function;
    UINT16 Vendor, DeviceId;
    UINT8  Revision, Class, Subclass, ProgIf;
    UINT64 Bar[6];
} BOOT_PCI_DEVICE;

/* 尾部新增 */
UINT32 HandoffSize;      // = sizeof(BOOT_HANDOFF)，0 = 旧引导器
UINT32 PciDeviceCount;   // 快照条数（0 = 没有快照 → 内核自扫）
BOOT_PCI_DEVICE PciDevices[BOOT_PCI_MAX];
```

**内核侧判断**：`HandoffSize >= offsetof(BOOT_HANDOFF, PciDeviceCount) + 4` 才读快照，否则回退自扫。

### 6.2 `DEVICE_NODE` 加 `Segment`（多 PCI 段）

现有 `PciBus/PciDev/PciFn` 没有段号；多 host bridge 机器会撞车。加 `UINT16 PciSegment;`。

### 6.3 模块加载器（新增）

```c
int ModuleLoadForDevice(DEVICE_NODE *Dev);
```

匹配键优先级：`Vendor+Device` → `Class/Subclass/ProgIf` → `Compatible`（DTB 路径用）。

## 7 · class → 模块 映射表（启动期）

| PCI Class | 是什么 | 加载的模块 | 留核？ |
|---|---|---|---|
| `0x03`（Display） | 显卡/VGA | `gpu.mod` | 否 |
| `0x01`（Storage） | SATA/AHCI/NVMe | `storage.mod` | **引导用那个留核** |
| `0x0C/0x03`（USB 主控） | xHCI/EHCI/UHCI | `usb-host.mod` | 否（但 xHCI 在留核清单里？见下） |
| `0x02`（Network） | 有线/无线网卡 | `nic.mod` | 否 |
| `0x04`（Multimedia） | 音频 | `audio.mod` | 否 |
| `0x06`（Bridge） | PCIe 桥/ISA 桥 | 内核处理（枚举用，不装驱动） | **留核** |

**留核判据（Doc 18 §3.3）**：**读完它才能开始加载模块**。
⇒ 核内只留：**一个引导块设备驱动**（AHCI 或 NVMe 之一，或 virtio-blk）+ 串口 + 帧缓冲（若要用它显示加载信息）。
`usb-host` 是否留核？**否** —— 键鼠是动态设备，等模块起来再装完全可行。

## 8 · 分步计划（X64 主线，每步可回退）

| 步 | 内容 | 判据 | 风险 |
|---|---|---|---|
| **X1** | Boot 导出 PCI 快照（`FillDevices.c`）＋ `BOOT_HANDOFF` 加版本字段 | 串口打印 `Boot: 设备快照 N 个`，与内核自扫数字**一致** | 低（Boot 与 Kernel 同批构建） |
| **X2** | 内核 Discover 优先用快照、回退自扫；打印对照 | 两条路的设备数/VID:DID 完全一致 | 低 |
| **X3** | 模块加载器（只加载 + 校验，不绑定）+ `hello.mod` | 串口出现模块输出；删文件不影响启动 | 中（ELF 加载/重定位） |
| **X4** | 用 `gpu.mod` 或 `hid.mod` 做第一个真模块（二选一，见下） | 删/放模块 → 对应功能消失/恢复 | 中 |
| **X5** | 动态设备路径：xHCI 枚举到键鼠 → 加载 `hid.mod` | 插拔键鼠，模块按需加载 | 中高 |

**X4 选 `gpu.mod` 还是 `hid.mod`？**

- `hid.mod`：**热插拔**，要先有 xHCI 动态枚举 → 依赖 X5，链条长；
- `gpu.mod`：**静态**，启动期就能验，链条短。

⇒ **建议 X4 先做 `gpu.mod`（静态）**，`hid.mod` 放到 X5 之后。
（这与 Docs/18 里"先 HID"的建议不同，理由：X64 的 HID 必须先有 USB 动态枚举，而 GPU 是纯静态。）

---

## 9 · 风险

| # | 风险 | 缓解 |
|---|---|---|
| 1 | **引导器与内核对不上**（旧 boot.sd + 新内核） | `HandoffSize` 字段；不匹配就回退自扫并打日志 |
| 2 | **多 segment 只在内核自扫路径丢失** | 主线走 UEFI 快照；自扫路径打"仅 segment 0"提示 |
| 3 | **固件隐藏设备**（有些笔记本隐藏 ME/HECI） | 快照与自扫两者对比，差异打印；不追 |
| 4 | **BAR 是固件分配的**，模块拿到的地址不一定可用 | 第一版只读；需要重映射时再由内核处理 |
| 5 | **热插拔设备漏加载** | 动态入口必须实现（X5）；否则 U 盘/键鼠永远没驱动 |
| 6 | **ACPI 平台设备拿不到** | 明确推迟；将来要么解析 AML（工程量大），要么用 UEFI 快照补子集 |

---

## 10 · 直接回答你的问题

> **UEFI 阶段能否获取枚举的所有设备（非热插拔的）？**

**能**：`EFI_PCI_IO_PROTOCOL` 的句柄枚举可以拿到**全部 PCI 功能**（含多 segment、固件已分配的 BAR），
我们已经在 `FillXhci.c` 里用过同一套 API，扩展成导出全量快照是一天的工作量。

**但"非热插拔设备"只能决定"装不装总线驱动"，决定不了"键鼠装不装"** ——
键鼠在 USB 总线后面，是热插拔设备，必须在运行期由 USB 栈枚举后再加载。

**所以模块加载要有两个入口**：启动期（静态设备清单）+ 运行期（总线报告新设备）。
这一点定下来，X64 这条线的设计就闭合了。
